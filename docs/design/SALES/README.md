# Продажа: менеджер — источник правды, бот — модульный

Ответ на [P-09](../../issues/BILLING.md#p-09) и на К-6 из
[research/11-transition.md](../../research/11-transition.md): роль издателя
расщеплена между менеджером и внешним кабинетом. Здесь она сводится обратно
вниз — без демонтажа того, что уже работает.

## Рамка

Менеджер — **открытый продукт**: его скачивает кто угодно и продаёт доступ
через своего бота, ничего больше не поднимая. Базовая продажа обязана работать
из коробки.

Надстройка (мини-апп, кабинет, чужая CRM) — **частная**: своя касса, свои
клиенты, свой UI. Она не должна ни форкать менеджер, ни заводить второй
экземпляр каталога.

Отсюда три правила.

1. **Источник правды по продаже — менеджер.** Каталог, цены, длительности,
   устройства, опции, режим звёздной цены живут в `tariffs.conf` и `bot.conf`.
   Наверху копий и переопределений нет.
2. **API раскрывает продажу полностью.** Не только чтение каталога, но и
   правка: создать, изменить, удалить, переставить тариф, сменить режим и курс
   звёзд. Тогда любая надстройка может быть админкой тарифов, не заводя своих
   таблиц.
3. **Бот — набор модулей.** По умолчанию включены все: скачавший получает
   рабочий продукт. Оператору со своей витриной достаточно выключить `sales` —
   уведомления, привязка и админка при этом остаются.

## Модули бота

`bot.conf`: `BOT_MODULES=sales,notify,admin` (значение по умолчанию —
отсутствие ключа означает «все включены», старые установки не меняют поведение).

| Модуль | Что даёт | Выключен — что происходит |
|---|---|---|
| `sales` | витрина тарифов в боте, счета (Stars, провайдер BotFather, ЮMoney), выдача доступа по тарифному платежу | кнопки «Купить/продлить» нет, `buy:*` игнорируется, тарифный платёж не фулфилится. Продажа идёт только снаружи, через API |
| `notify` | напоминания об истечении срока, уведомления админам об оплатах | бот молчит, срок всё равно тикает (`lib/expiry.sh`) |
| `admin` | админ-меню в боте: пользователи, статус сервера, правка тарифов | админ работает через TUI или API |

**Не модули** — ядро, работает всегда:

- привязка `/start КОД` и `/code` — без неё бот бесполезен даже как уведомитель;
- фулфилмент пополнений `topup:<tg_id>` — счёт минтит надстройка, но апдейт
  `successful_payment` принимает демон бота: long polling у него, второго
  владельца токена быть не может;
- делегирование `/start` мини-аппу (`MINIAPP_API`) — уже существующий флаг.

Граница «модуль или ядро» проходит по вопросу: **сломается ли надстройка, если
это выключить.** Всё, чем пользуется надстройка, — ядро.

## Цена в звёздах: два режима

Сегодня XTR-цена жёстко записана в строке тарифа, а надстройка держит свой
множитель «рублей за звезду» и пересчитывает цену сама. Это и есть второй
источник правды по цене. Режим переезжает вниз:

`bot.conf`:

| Ключ | Значения | Смысл |
|---|---|---|
| `STARS_MODE` | `fixed` (по умолчанию) \| `rate` | откуда берётся цена в звёздах |
| `STARS_RUB_PER_STAR` | число, напр. `1.5` | курс для режима `rate` |

- `fixed` — как сегодня: цена XTR берётся из строки тарифа (`299/240|XTR/RUB`).
  Тариф без XTR-цены за звёзды не продаётся.
- `rate` — XTR считается из рублёвой цены: `ceil(RUB / STARS_RUB_PER_STAR)`.
  XTR-колонка в `tariffs.conf` игнорируется, и её можно не заполнять.

Считает **менеджер**, наружу отдаёт уже посчитанную цену: надстройка не обязана
знать про режим (но видит его — для админки).

**Курс пополнения баланса сюда не переезжает.** Пополнение — не тариф: это
деньги надстройки, её продукт и её касса. Менеджер про баланс не знает и знать
не должен — граница ровно та же, что в К-6: доступ и каталог внизу, деньги
покупателя наверху.

## API

Scope `tariffs` (новый; ключи без него читают каталог как раньше по `read`).

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/v1/tariffs` | каталог + блок `pricing` (`stars_mode`, `rub_per_star`); в `prices[]` цена XTR уже посчитана по режиму |
| `POST` | `/v1/tariffs` | upsert по коду: создать или заменить тариф целиком |
| `DELETE` | `/v1/tariffs/{code}` | удалить тариф |
| `POST` | `/v1/tariffs/{code}/move` | переставить в витрине (`up`/`down`/позиция) |
| `POST` | `/v1/pricing` | режим и курс звёзд |

Мутации идут через `webapi/dispatch.sh` — те же `tariff_add`/`tariff_update`/
`tariff_del`/`tariff_move` из `lib/tariffs.sh`, что зовут TUI и бот. Второй
реализации правки тарифов не появляется.

## Что меняется у надстройки

- удаляется переопределение цены (`Setting tariffs.prices`) и локальный
  пересчёт звёзд — цена берётся из `GET /v1/tariffs` как есть;
- админка тарифов делается формами поверх `POST /v1/tariffs` (задел; в этом
  документе не проектируется).
