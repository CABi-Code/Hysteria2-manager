# Классы потребления (вес профиля вместо штук)

> Надстройка над [размещением](README.md). Не делать раньше, чем размещение
> заработает по штукам и появится Фаза 0 (видимая нагрузка нод).

Место на ноде занимает не «профиль», а **нагрузка, которую он создаёт**.
Сначала научиться её мерить и показывать, только потом ею управлять.

## Новой телеметрии не нужно

Всё уже собирается ежеминутно и уже реплицируется по кластеру.

| Файл | Что внутри | Где производится |
|---|---|---|
| `stats.dat` (`lib/config.sh:22`) | накопленный TX/RX на юзера | `lib/traffic.sh` |
| `speed.dat` (`lib/config.sh:32`) | текущая скорость B/s | `collect_rates`, `lib/traffic.sh:151` |
| `activity.dat` (`lib/config.sh:40`) | флаг «активен по трафику в минуту», порог `ACTIVITY_THRESHOLD_BPS=4096` (`lib/config.sh:68`) | `lib/traffic.sh` |
| `ips.dat` / `subips.dat` (`lib/config.sh:23,170`) | уникальные IP и устройства | `lib/ip_tracking.sh` |
| `abuse.dat` (`lib/config.sh:77`) | `user\|score\|ts\|auto_hc_until\|peak_active\|viol_minutes` | `lib/antiabuse.sh:30` |
| кэш пиров | то же по кластеру, `_peer_stat_sum` | `lib/publish.sh:116` |

Классификация — слой агрегации поверх готовых данных, а не новый сбор.

## Схема

Файл `usage_class.dat`: `user|class|score|updated_ts`, пересчёт суточным кроном
(`lib/cron.sh`). Синхронизировать **не нужно**: исходные данные уже есть на
каждой ноде, каждая посчитает то же самое сама. Одной секцией синка меньше.

Класс определяется двумя осями за скользящие 30 дней: объём трафика (сумма
TX+RX по кластеру) и пиковая скорость / доля активных минут.

| Класс | Грубый критерий | Вес слота |
|---|---|---|
| `light` | нижние ~50% по трафику, мало активных минут | 0.5 |
| `medium` | середина | 1.0 |
| `heavy` | верхние ~15% по трафику **или** стабильно высокая скорость | 2.5 |

Тогда «21 профиль» становится «21 единицей веса»: либо 21 medium, либо 8 heavy,
либо 40 light.

Пороги — **перцентили по кластеру**, не абсолютные гигабайты: сеть растёт,
абсолютные числа протухают за квартал, перцентили нет.

## Что это даёт

- Тяжёлые юзеры разъезжаются по разным нодам вместо случайной кучи на одной.
- Видно, кто реально создаёт нагрузку → основа для честного «безлимита» и
  тарифов с приоритетом скорости.
- Ленивые профили пакуются плотнее: дешёвая нода вмещает втрое больше.

## Проблемы этого слоя

1. **Холодный старт.** У нового юзера нет истории → стартовый класс `medium`,
   первая переоценка через 7 дней.
2. **Класс мигает.** Один отпуск с торрентами — и `heavy` навсегда? →
   Гистерезис: переход только в соседний класс, не чаще раза в неделю и только
   при двух подтверждениях подряд.
3. **Переезды от переклассификации.** Смена класса **не** должна сама по себе
   отправлять профиль на другую ноду — пересчёт размещения только если нода
   реально перегружена. Иначе система будет непрерывно тасовать людей, а каждая
   такая тасовка это рестарт Xray/sing-box и обрыв чужих сессий
   (см. [PROBLEMS.md](PROBLEMS.md) I.4).
4. **Heavy ≠ плохой.** Тяжёлый юзер часто и есть главный плательщик. Класс —
   метрика планирования ёмкости, **не** повод резать скорость. Резать —
   работа антиабуза, с его собственными порогами (`lib/antiabuse.sh`).
5. **Пересечение с антиабузом.** Оба слоя смотрят в одни файлы, но делают
   разные выводы: `abuse.dat` про нарушение правил, `usage_class.dat` про
   планирование. Держать раздельно; одна функция, читающая оба, — гарантия
   путаницы.
6. **Приватность.** Хранится только агрегат (класс + score), не история
   посещений. Так и оставить: не «куда ходил», а «сколько прокачал».
7. **Цена пересчёта.** Перцентили по кластеру раз в сутки на bash терпимы на
   сотнях юзеров и не терпимы на десятках тысяч. Порог пересмотра — ~5000
   профилей.
8. **Что показывать юзеру.** Ничего. «Вы тяжёлый пользователь» — оскорбительно
   и провоцирует игру с системой. Класс виден только в админке.

## Связь с маркетом

В модели маркета (заметки в приватном репозитории) нода продаёт **полосу**, а тик
расчёта задаётся в байтах и масштабируется с полосой ноды. Вес профиля —
локальный предшественник этой же логики: и там, и там единица учёта не
«пользователь», а прокачанный объём. Класс потребления стоит считать так,
чтобы он потом переводился в байты, а не только в безразмерный score.
