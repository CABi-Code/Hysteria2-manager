# Демо-ключи: `demo_create()`, `DEMOS_DB` и выбор ноды

Демо-ключ — одноразовый рабочий профиль, который выдаётся анонимному гостю
**до регистрации и оплаты** (воронка надстройки). Он жёстко закапан сразу по
трём осям — скорость, трафик, время жизни — и живёт в отдельной таблице
`DEMOS_DB`, а не среди боевых клиентов.

Код: `lib/demo.sh` (весь жизненный цикл), `webapi/dispatch.sh` (verb
`demo-create`), `webapi/hy2-webapi.py` (`POST /v1/demo`, `GET /v1/demo/{name}`).

---

## 1. Почему демо устроено именно так

- **Экономику фарма ломает кап, а не фингерпринт.** Нафармить месяц доступа по
  500 МБ на 5 Мбит/с дороже, чем его купить. Отпечаток браузера (на стороне
  надстройки) отсекает только ленивых, и это нормально.
- **Но у ноды есть потолок числа живых демо** (`DEMO_MAX_ACTIVE`). Все барьеры
  надстройки стоят на данных, которые присылает сам клиент (секрет устройства,
  отпечаток) либо на его адресе (счётчик, капча) — первые скрипт не присылает
  вовсе, второй снимается прокси-пулом. Потолок на стороне ноды не обходится
  ничем: он считает то, что у неё уже лежит. Упёрлись — `demo_create` возвращает
  `2`, а `dispatch.sh` — `demo_capacity` (§7).
- **Только Hysteria2.** Фильтр `sub_filter_protocols` (`lib/sub_links.sh`)
  оставляет демо-профилю единственный ключ: аутентификация Hysteria читает
  `users.db` на каждом подключении, то есть профиль работает мгновенно и не
  требует трогать конфиги Xray/sing-box — иначе каждое нажатие гостевой кнопки
  рестартовало бы движки и рвало сессии боевых клиентов. У TUIC вдобавок нет
  пер-юзерного учёта трафика, квоту там не проверить.
- **Один профиль живёт на одной ноде.** В roster кластера демо не попадает и по
  нодам не публикуется: размазывать мусорную нагрузку сразу по всем локациям
  незачем. Но нода-приёмник выбирается на каждую выдачу — см. §4.

Параметры (env, значения по умолчанию в `lib/demo.sh`):

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `DEMO_RATE_MBPS` | 5 | потолок скорости профиля |
| `DEMO_CAP_BYTES` | 500 МБ | трафик, после которого доступ отбирают |
| `DEMO_TTL_MIN` | 60 | сколько минут живёт доступ |
| `DEMO_KEEP_SEC` | 86400 | сколько строка лежит после отбора (статистика) |
| `DEMO_REMOTE_TIMEOUT` | 15 | сколько ждём ноду-приёмник при выдаче |
| `DEMO_MAX_ACTIVE` | 50 | сколько демо держим живыми разом; `0` — без потолка |

Потолок считается по строкам `active` этой ноды, а TTL — час, поэтому то же
число задаёт и потолок выдач в час. Считать по кластеру нечем и не нужно: у
каждой ноды своя ёмкость, а выбор ноды и так размазывает выдачи (§4).

## 2. Таблица `DEMOS_DB`

`$DATA_DIR/demos.db`, строка на профиль:

```
user|state|created|expires|cap|base|used|node
```

| Поле | Смысл |
|---|---|
| `user` | имя профиля, всегда с префиксом `demo-` — видно в любом списке юзеров |
| `state` | `active` — доступ работает; `expired` — уже отобран, строка досиживает сутки |
| `created` / `expires` | unix-время выдачи и конца доступа |
| `cap` | лимит трафика в байтах (0 — без лимита) |
| `base` | общий трафик юзера на момент выдачи; расход = текущий минус `base` |
| `used` | расход, записанный в момент отбора доступа (для статистики) |
| `node` | домен ноды-приёмника. **Пусто = эта нода** — так выглядят все строки, выданные до появления выбора ноды |

Отдельная таблица, а не флаг в `USERS_DB`: у демо свой жизненный цикл (грейс-
сутки и авто-purge), своя статистика и своё состояние, переживающее удаление
самого пользователя. `GET /v1/demo/{name}` поэтому отвечает и тогда, когда
`/v1/users/{name}` уже 404.

## 3. Выдача профиля

`demo_create` — единственная точка входа (зовёт `dispatch.sh demo-create`):

0. `demo_at_capacity` — живых демо уже `DEMO_MAX_ACTIVE`? Тогда выход с кодом
   `2`, ноду даже не выбираем. Проверка стоит в `demo_create`, а не в
   `demo_create_local`, чтобы потолок действовал на обе ветки выдачи, и у
   ноды-приёмника при этом работает её собственный (её `POST /v1/demo` идёт
   через её же `demo_create`).
1. `demo_pick_node` выбирает ноду-приёмник (§4).
2. Выбрана эта нода → `demo_create_local`: имя `demo-xxxxxxxx`, пароль
   `bot_gen_pass`, `db_add_user`, лимиты (`1` устройство, демо-скорость),
   файл подписки только для этого профиля (`demo_write_sub` — без полного
   `regen_subscriptions`, гость ждёт ответа), строка в `DEMOS_DB`.
3. Выбрана чужая нода → `demo_create_remote` (§5).
4. Наружу печатается `user`, `sub_url`, `expires`, `cap`, `rate`, `node`.

Дорогое из горячего пути выкинуто сознательно: общекластерный
`write_authlimits` не зовём (его и так перестраивает минутный `--online-sync`, а
у демо всё равно одно устройство), HTB-класс под демо-скорость создаём только
если такого класса ещё нет.

## 4. Выбор ноды — `demo_pick_node`

Кандидаты берутся из `DEMO_NODES` в `node.conf` — список доменов нод через
запятую. **Пусто = только эта нода**, то есть до заполнения списка всё работает
ровно как раньше.

```
DEMO_NODES=node-a.example,node-b.example
```

Настройка **намеренно локальная** и не входит в `SETTING_KEYS`: её выставляет
та нода, что обслуживает кнопку «получить демо», остальным она не нужна, а
LWW-перезапись чужой рукой здесь только навредила бы.

Алгоритм:

1. Пир годится, если последняя синхронизация признала его живым и вердикт
   свежий (`peers/.health`, не старше `PEER_STALE_SEC`). Отдельного опроса не
   делаем: гость ждёт ответа, а probe по мёртвой ноде — это секунды таймаутов.
2. Своя нода в списке — кандидат без проверок.
3. Из кандидатов выбирается **случайный, равновероятно**.
4. Кандидатов не осталось (список пуст, все пиры мертвы) — выдаём у себя.
   Fail-open: гость не должен остаться без пробы из-за чужой ноды, это то же
   правило, что в [design/PLACEMENT](../design/PLACEMENT/README.md) §3.2.

Случайность — временная: по загрузке и географии выбирать нечем, пока нет
паспорта ноды ([P-06](../issues/CLUSTER.md#p-06), фаза 0 размещения). Когда он
появится, меняется ровно `demo_pick_node` — про поле `node` всё остальное уже
знает.

## 5. Демо на другой ноде

Активного удалённого CRUD в кластере нет: ноды обмениваются статикой по pull, и
завести профиль на соседе «за него» нельзя, а ждать его синхронизации (минуты)
гость не станет. Поэтому нода-приёмник заводит профиль **сама**, своим же
менеджером:

```
надстройка → POST /v1/demo (нода-выдающая)
              └─ demo_create_remote → POST https://<нода-приёмник>/api/v1/demo
                                       (заголовок X-Cluster-Auth)
                                       └─ demo_create_local у неё
```

- **Авторизация — общий секрет кластера**, тот же, которым ходит
  `cluster_call`. Раздавать по нодам ключи `webapi.keys` не требуется, и ничего
  нового секрет не открывает: с ним и так забирают манифесты, то есть ключи всех
  юзеров ([P-04](../issues/CLUSTER.md#p-04), [P-05](../issues/CLUSTER.md#p-05)).
  Пускают по нему **только** в `/v1/demo*` (`CLUSTER_AUTH_PREFIX` в
  `webapi/hy2-webapi.py`).
- **Ответ соседа проверяется как чужой ввод:** имя по маске `demo-…`, числа —
  числами, ссылка обязана вести на ту самую ноду, имя не должно уже быть занято
  нашей строкой.
- **Локально остаётся только указатель** — строка `DEMOS_DB` с полем `node`,
  нулевыми `base`/`used`. Трафик, TTL и отбор доступа считает нода-приёмник:
  кросс-нодового учёта демо не появляется.
- **Сосед не ответил или ответил мусором** — профиль выдаётся у себя. Отказ
  гостю дороже неидеальной локации.

**Что требуется от ноды-приёмника:** версия менеджера с этим кодом и
**включённый Web API** (главное меню → Web API; Caddy сам добавит `/api/*`).
Ключи API ей заводить не нужно.

Следить за этим руками больше не надо: нода объявляет наличие демона у себя
сама — `WEBAPI=1/0` в её разделе `nodeinfo` (`publish_cluster_nodeinfo`), а
`_demo_peer_ok` не берёт в кандидаты ноду, объявившую `0`. Раньше её домен в
`DEMO_NODES` просто сжигал `DEMO_REMOTE_TIMEOUT` (15 с) на каждую выдачу, пока
гость смотрел на крутилку. Ключа `WEBAPI` в разделе нет (старая нода, раздел не
доехал) — нода считается годной: терять локацию из-за неприехавшего раздела
хуже, чем изредка потратить таймаут.

**Выдача — единственное, что между нодами всё ещё идёт по Web API**, и это
осознанно: завести профиль может только сама нода-приёмник, статика ничего не
исполняет, а гость ждёт ответа сейчас. Критерий выбора канала —
[CLUSTER-CHANNELS.md](CLUSTER-CHANNELS.md#коротко).

### Состояние такого профиля — из файлового канала

`GET /v1/demo/{name}` смотрит поле `node`. Своя нода — считает по своим файлам.
Чужая — **берёт уже посчитанное состояние из раздела `demos`**, а не
переспрашивает ноду-владельца.

Почему не запросом (так было раньше): ответ зависел от **включённого Web API у
соседа**, то есть кабинет и лендинг не работали для такого гостя вовсе, если на
ноде-владельце демон не поднимали; а когда демон был, но нода лежала, гость
получал `502` вместо шкалы лимита ([P-73](../issues/CLUSTER.md#p-73)).

```
владелец: demo_tick (раз в минуту)
            └─ publish_cluster_demos -> $WEBROOT/cluster/demos
                 user|state|created|expires|cap|used|alive|online|ts
любая нода: cluster_online_sync (раз в минуту)
            └─ peers/<нода>.demos
                 └─ demo_peer_status (wa_users.py) -> ответ /v1/demo/{name}
```

Решения, зашитые в этот путь:

* **Публикуется посчитанный расход, а не база.** Считать расход умеет только
  владелец: у остальных нет ни его трафика, ни базы на момент выдачи. Указатели
  на чужие профили владелец не публикует — иначе выдал бы за факт нули.
* **Каденс — минута**, вместе с `demo_tick` и в том же цикле `--online-sync`,
  что `stats`/`userlimits`. Пятиминутная `cluster_sync` для шкалы часового демо
  слишком грубая. Публикация идёт в конце тика: состояние на диске к этому
  моменту уже актуально, иначе сосед минуту показывал бы живым только что
  отобранное.
* **Поиск по кэшам глобом**, а не по имени ноды из `demos.db`: имя файла кэша
  строится из имени пира в реестре, и повторять это правило в Python значило бы
  вторую копию формулы. Имя демо уникально в кластере и живёт на одной ноде,
  поэтому поиск по имени однозначен.
* **Поле `stale_sec`** — сколько секунд назад владелец это посчитал. Клиенту
  ручка и остальные поля не меняются.
* **Раздел ещё не доехал** (профиль выдан секунды назад, первая публикация
  впереди) — отвечаем по своему указателю: срок и кап там настоящие, расход
  отдаём нулём. Занизить расход на экране не опасно: доступ отбирает владелец
  по своим цифрам, экран на это не влияет ([правило «экран не решает»](../../../CLAUDE.md)).
  Отдать `502` в момент, когда гость только получил ключ, было бы хуже всего.
* **`refreshed` всегда `false`** для чужого профиля: пересчитать трафик может
  только владелец, а мы его больше не дёргаем. Врать в этом поле нельзя — на нём
  строятся решения вызывающего.

Пустой ответ соседа прошлый кэш **не затирает**: устаревшая шкала полезнее
пропавшей, а насколько она устарела, видно по `stale_sec`.

## 6. Отбор доступа — `demo_tick`

Прогон раз в минуту из `--online-sync` (TTL демо меряется минутами, суточной
прогонки `check_expired_users` тут мало):

| Строка | Что делает тик |
|---|---|
| своя нода, `active` | считает расход (`текущий трафик − base`); вышло время **или** выбран кап → `cluster_delete_local` (доступ отбирается целиком, демо не продлевают) + пометка `expired` с записанным расходом |
| своя нода, `expired` | через `DEMO_KEEP_SEC` убирает строку |
| чужая нода | **юзера не трогает** — его отбирает нода-приёмник. По времени помечает указатель `expired` (чтобы UI и API не показывали живым то, чего уже нет), затем убирает строку в свой срок |

Регрессии закрыты `tests/test-demo.sh`: TTL, кап от базы, уборка, невмешательство
в чужие профили, выбор ноды и потолок живых демо.

Тик же и освобождает место под потолком: `expired` в счёт не идут.

## 7. Коды отказа `demo-create`

| Код `dispatch.sh` | Ответ Web API | Когда |
|---|---|---|
| `3` `demo_capacity` | `409` | живых демо уже `DEMO_MAX_ACTIVE` |
| `3` `sub_disabled` | `409` | подписка на ноде не настроена — гостю отдавать нечего |
| `1` `demo_failed` | `502` | профиль не завёлся (имя, пароль, запись в базу) |

`demo_capacity` отдаётся кодом `3`, а не отдельным: по контракту `dispatch.sh`
это «конфликт состояния» → `409`, и код ошибки доходит до гостя как есть.
Заводить новый код возврата ради одного случая значит менять контракт всем
verb'ам сразу.

## 9. Как расширять

- **Умный выбор ноды.** Загрузка, метка локации, ёмкость — всё это появляется
  вместе с паспортом ноды; правится одна функция `demo_pick_node`.
- **Больше протоколов в демо.** Ключи всех протоколов производны от пароля,
  так что профиль уже мультипротокольный на своей ноде — достаточно ослабить
  фильтр `sub_filter_protocols`. Ценой рестарта движков на каждую выдачу.
- **Анти-фарм сверх капа** (капча/PoW) — на стороне надстройки и только если в
  статистике виден ботовый вал. Не в менеджере.
- **Потолок по кластеру вместо ноды.** Сейчас `DEMO_MAX_ACTIVE` считается по
  своим строкам, и фармер, которого размазывает `demo_pick_node`, получает сумму
  потолков всех нод. Общий счётчик потребует спрашивать пиров в горячем пути
  выдачи (гость ждёт) — делать это стоит только вместе с уже агрегированным
  состоянием кластера, а не отдельным опросом.
