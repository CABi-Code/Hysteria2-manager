# Каналы связи между нодами

Ноды разговаривают друг с другом **двумя разными способами**, и путать их
дорого: на этой путанице кластер однажды потерял способность обновляться
([P-133](../issues/CLUSTER.md#p-133)). Документ отвечает на три вопроса: как
устроен каждый канал, что по какому ходит и почему, и что будет, если канал
взломают.

Код: `lib/cluster.sh` (транспорт, синхронизация, применение), `lib/publish.sh`
(выкладка данных), `lib/caddy.sh` (раздача и проверка секрета), `webapi/`
(второй канал). Область действия настроек — [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md),
состояние протоколов — [CLUSTER-PROTOCOLS.md](CLUSTER-PROTOCOLS.md).

## Коротко

| | Файловый канал | Web API |
|---|---|---|
| Что это | статика Caddy: `file_server` на `/cluster/*` | демон `hy2-webapi` за `handle_path /api/*` |
| Направление | **pull**: сосед приходит и забирает | **push**: мы приходим и просим сделать |
| Кто исполняет | никто, это файлы на диске | процесс на той стороне |
| Когда | крон соседа: ~5 мин / 1 мин / 15 с | сразу |
| Включён | всегда, иначе кластера нет | **опционально** — на ноде без кабинета его не включают |
| Что несёт | **все данные и все объявления** | только «сделай сейчас» |
| Отказ означает | кластер сломан, это видно сразу | задержка |

**Главное правило: по Web API можно посылать только то, чей отказ означает
ЗАДЕРЖКУ, а не потерю.** Всё, что обязано доехать, едет файловым каналом.

## Файловый канал

### Как устроен

Односторонняя выкладка плюс опрос. Никакого удалённого исполнения в нём нет и
быть не может — на той стороне веб-сервер, отдающий файлы с диска.

```
нода A                                    нода B
publish_* ──> $WEBROOT/cluster/<раздел>
                     │
                     │  GET /cluster/<раздел>          cluster_call (curl)
                     └──────────────────────────────>  $DATA_DIR/peers/<имя>.<раздел>
                                                              │
                                                       cluster_apply_* ──> свои файлы
```

* **Публикация** — полтора десятка `publish_*` (`lib/cluster.sh`,
  `lib/publish.sh`). Каждая копирует свой файл состояния в `$WEBROOT/cluster/`
  и правит режим. Публикуется **только своё**: чужое перепубликовывать нельзя,
  иначе запись становится бессмертной (правило 3 в [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md)).
* **Опрос** — `cluster_sync` идёт по `CLUSTER_SYNC_SECTIONS` и складывает ответы
  в `peers/<имя пира>.<раздел>`. Ничего не применяя: кэш и применение разнесены.
* **Применение** — `cluster_apply_*` в фиксированном порядке. Забвение первым
  (иначе стёртого воскресят слиянием), обновление менеджера последним (оно
  подменяет файлы под работающим процессом).
* **Реестр пиров** ходит тем же каналом (`peers.list`) и работает как gossip:
  узнав про пира от соседа, мы добавляем его себе. Поэтому кластер сходится в
  полносвязный сам, без ручного перечисления на каждой ноде.

### Три каденса

Разделы тянутся не все и не всегда — цена опроса разная:

| Цикл | Период | Что тянет | Откуда |
|---|---|---|---|
| полный `cluster_sync` | ~5 мин | все `CLUSTER_SYNC_SECTIONS` | крон `--cluster-sync` |
| `cluster_online_sync` | 1 мин | `stats`, `userlimits`, `abuse`, `demos` | крон `--online-sync` |
| скорость | 15 с | `rates` | таймер `hy2-rates` |

Отсюда важное следствие: **фильтры, защищающие слияние, обязаны стоять во всех
трёх циклах**, а не только в полном — иначе быстрый цикл привезёт обратно то,
что медленный отфильтровал (так было с забвением, см. правило 6 в CLUSTER-SCOPE).

### Что по нему ходит

Полный список — `CLUSTER_SYNC_SECTIONS` в `lib/cluster.sh`, назначение каждого
раздела — в [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md). Разделы делятся на три вида:

* **Состояние** (`state`, `expiry`, `userlimits`, `freeplan`, `abuse`, `tgbind`) —
  сливается LWW по метке времени.
* **Объявления** (`erase`, `pwreset`, `ipforget`, `updatereq`) — «я это сделал,
  сделайте у себя». Не сливаются: получатель решает сам и своё решение не
  перепубликовывает.
* **Справка** (`manifest`, `subtokens`, `roster`, `ips`, `subips`, `stats`,
  `rates`, `nodeinfo`, `version`, `protocols`, `demos`) — читается как есть.

`nodeinfo` — единственный раздел, где нода утверждает факты **о себе**
(`LABEL`, `WEBAPI`), и слияния у него нет: сосед такое перезаписывать не должен.

### Как добавить раздел

1. Файл состояния в `lib/config.sh` с комментарием, зачем он кластерный.
2. `publish_<раздел>` — копия в `$WEBROOT/cluster/`, режим `640`.
3. Имя раздела в `CLUSTER_SYNC_SECTIONS` и метка в `_section_label`.
4. Вызов публикации в `cluster_sync`, применение — в блоке `cluster_apply_*`.
5. Правила 1–7 из [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md) — они про то, как не
   получить бессмертную запись и застрявшее расхождение.
6. Уборку кэша при удалении пира писать **не надо**: `cluster_remove_peer`
   идёт по `CLUSTER_SYNC_SECTIONS`. Поимённый список там уже отставал от состава
   разделов — это тот же класс ошибки, что [P-112](../issues/CLUSTER.md#p-112).

## Web API как канал между нодами

Второй канал — демон `hy2-webapi`. Между нодами по нему ходят **ровно две
вещи**, и обе проходят проверку «отказ = задержка или fail-open, а не потеря».

| Ручка | Что делает | Что если не дошло |
|---|---|---|
| `POST /v1/cluster/nudge` | «синхронизируйся сейчас, не жди крона» | сосед узнает на своём кроне — медленнее, но узнает |
| `POST /v1/demo` | завести демо-профиль на этой ноде | демо выдаётся у выдающей ноды (fail-open); ноду без демона `demo_pick_node` вообще не выбирает |

`nudge` ничего не передаёт: он лишь просит забрать. Данные всё равно поедут
файловым каналом, прежним путём и с прежними проверками. **Отказ стоит минут
задержки, а не потери** — поэтому он и зовётся в фоне, с подавленным выводом.
Ставить оплату в зависимость от доступности соседа нельзя.

Отдельно живёт `POST /v1/cluster/update` («обнови у себя менеджер»). Ручка
осталась рабочей, но **кластер от неё больше не зависит**: просьба обновиться
едет разделом `updatereq`. Почему так — ниже.

### Почему обновление ушло из Web API

Это была ошибка проектирования, и она дорого стоила. Web API — отдельный
компонент, который включают там, где он кому-то нужен (нода с кабинетом). На
остальных нодах его незачем включать: клиентам он не нужен, менеджер работает
и без него. А без него в Caddyfile нет блока `handle_path /api/*` — он
генерируется в `setup_caddy` под условием `webapi_enabled`.

Получился замкнутый круг: **нода отстала → крючок в неё не доходит → нода
отстаёт дальше.** Сама она не выздоровеет никогда, сколько ни жми
`--cluster-update`. Разбор — [P-133](../issues/CLUSTER.md#p-133).

Файловый канал этой болезнью не болеет **по построению**: если он не работает,
кластера нет вообще — и это видно сразу, а не только в момент обновления.

### Как теперь устроено обновление

Объявление, а не команда, форма как у `erase`:

1. `cluster_request_update` кладёт в `$UPDATEREQ_FILE` строку `версия|ts` и
   публикует её. Версия — та, что сейчас в репозитории; сеть молчит — своя.
2. Соседи забирают раздел обычной синхронизацией.
3. `cluster_apply_updatereq` берёт **самую свежую** просьбу и решает сам.
   Триггер — **сверка по факту**, а не дельта по `ts`: «просят версию новее
   нашей» остаётся верным, пока дело не сделано. Одной метки «этот `ts` я видел»
   тут категорически мало — обновление может не доехать, и повторить было бы
   нечем: новой метки времени взяться неоткуда (правило 7 в
   [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md)). Ограничители при этом обязательны:
   * **пауза между попытками** (`UPDATEREQ_RETRY_SEC`, 30 мин) — иначе сверка по
     факту превратится в переустановку на каждой синхронизации;
   * **срок годности просьбы** (`UPDATEREQ_TTL_SEC`, сутки) — объявление с
     недостижимой версией (опечатка, откат репозитория) иначе стало бы вечным
     поводом переустанавливать менеджер;
   * метка попытки пишется **до** запуска: `install.sh` подменяет файлы под
     работающим процессом, «запишу после» здесь не выполнится;
   * просьба до версии, которая уже есть, работой не считается (`_ver_gt`);
   * чужая просьба **не перепубликовывается**.

Объявляемая версия — **максимум из версии репозитория и своей**.
`raw.githubusercontent.com` отдаёт из CDN и первые минуты после пуша показывает
предыдущую версию; поймано на живой ноде — просьба ушла на версию, которая у
соседей уже стояла, то есть в никуда.

Версия из просьбы никуда, кроме сравнения, не идёт: адрес источника берётся из
`config.sh` самой ноды, и `install.sh` запускается в режиме `manager_only`.
«Обновись» не может превратиться ни в «выполни мой код», ни в «переустанови
всё» — полная переустановка стирает пользователей и удалённо недоступна.

**Известное ограничение.** Просьбу видит тот, кто напрямую синхронизируется с
объявившим: получатель её не пересылает дальше. В полносвязном кластере (а
gossip делает его таким) это не проявляется; в цепочке A→B→C нода C просьбу от A
не увидит. Лечится повторным объявлением с любой ноды.

## Безопасность

Раздел отвечает на прямой вопрос: **что будет, если канал обмена взломают.**
Ответ неприятный, и часть проблем не закрыта — это осознанное состояние, а не
недосмотр.

### Модель доступа

Аутентификация одна на оба канала: **общий секрет кластера** (`cluster.secret`,
48 символов) в заголовке `X-Cluster-Auth` поверх TLS. Проверяет его **Caddy**,
сравнением строки:

```
@cluster_noauth { path /cluster/*; not header X-Cluster-Auth "<секрет>" }
handle @cluster_noauth { respond 403 }
```

Отсюда три свойства, которые надо понимать:

* **Секрет один на весь кластер.** Личности ноды нет: кто знает секрет — тот
  «нода». См. [P-04](../issues/CLUSTER.md#p-04).
* **Содержимое не подписано.** Проверяется право прийти, а не право утверждать.
  Нода, получившая доступ, может опубликовать что угодно про кого угодно.
* **Секрет лежит в Caddyfile открытым текстом.** Иначе матчер не работает.
  Значит режим этого файла — часть периметра, а не мелочь оформления
  ([P-135](../issues/OPS.md#p-135)).

### Что даёт злоумышленнику чтение

Секрет открывает **все разделы всех нод**. Это не «метаданные»:

| Раздел | Что в нём | Чем это является |
|---|---|---|
| `manifest` | готовые ссылки подключения **с паролями** всех юзеров на всех нодах | полный захват доступа каждого клиента |
| `subtokens` | токены подписки | скачать чью угодно подписку |
| `ips`, `subips` | адреса клиентов и адреса скачиваний | деанонимизация — ровно то, за чем к сервису и приходят |
| `tgbind` | связка Telegram ↔ профиль | привязка трафика к личности |
| `stats`, `rates` | трафик и активность | поведенческий профиль |

То есть **компрометация канала на чтение = компрометация всех клиентов
сервиса.** Пароли в манифесте — осознанная плата за единую подписку без общей
базы ([P-05](../issues/CLUSTER.md#p-05)), но цена ошибки задаётся именно ею.

### Что даёт запись

Чтобы писать, надо попасть в чей-то реестр пиров — а туда попадают по gossip,
то есть с любой уже принятой ноды. Дальше доступно:

* **`erase`** — пометить кого угодно забытым. Разрушительно и **необратимо**:
  метка вечная и чистит данные по всему кластеру.
* **`state`, `expiry`, `userlimits`, `freeplan`** — отключать людей, раздавать
  себе бесплатный доступ, снимать лимиты. LWW принимает любую метку новее.
* **`roster`** — заводить профили на всех нодах.
* **`tgbind`** — перепривязать чужой профиль к своему Telegram.
* **`peers.list`** — **добавить свой хост в кластер навсегда**. Удаление пира на
  одной ноде не помогает: gossip вернёт его с остальных.
* **`updatereq`** — заставлять ноды переустанавливать менеджер. Код при этом
  берётся из репозитория самой ноды, так что это DoS, а не исполнение.

### Что уже закрыто

**[P-134](../issues/CLUSTER.md#p-134) — имя пира становилось путём записи от root.**
Имя приезжает из чужого `peers.list` и подставлялось в `$PEERS_DIR/<имя>.<раздел>`
без чистки: `../../../../etc/logrotate.d/pwn` уводил запись куда угодно, а
содержимое файла контролировал атакующий. Проверено в песочнице целиком, от
`peers.list` до пути. Санитайз теперь стоит в двух местах — на входе в реестр и
при чтении из него; хост проверяется на вид имени.

Чистятся **только разделители пути**: пробелы и кириллица в именах остаются как
есть. Иначе «Finnish Noda 2» стало бы «Finnish_Noda_2», файл кэша сменил бы имя,
старый остался бы лежать — а читаются они глобом `peers/*.stats`, и нода
считалась бы дважды. Косметика в имени не стоит сорванного учёта.

**[P-135](../issues/OPS.md#p-135) — Caddyfile с секретом был доступен всем на чтение.**
`cluster.secret` лежит `600`, но Caddyfile создавался по umask, то есть `0644`,
и тот же секрет читал любой локальный процесс — включая `www-data`, под которым
работает php-fpm кабинета. Любое чтение файлов из-под непривилегированного
пользователя превращалось в полный доступ к кластеру. Теперь `640 root:caddy`.

### Что НЕ закрыто

Это архитектурные вещи, каждая со своей записью в реестре:

1. **Один секрет на всех** ([P-04](../issues/CLUSTER.md#p-04)). Компрометация
   одной ноды = компрометация кластера, и ротация — ручной обход всех нод.
   Правильное лечение — подписывать **содержимое** разделов ключом ноды, тогда
   чужая подпись не пройдёт, даже если транспортный секрет утёк.
2. **Пароли в манифесте** ([P-05](../issues/CLUSTER.md#p-05)). Пока они там,
   стоимость любой утечки канала максимальна.
3. **Пир, добавленный по gossip, не убирается** (`cluster_remove_peer`). Нужен
   явный список доверенных хостов, а не «кого привезли, тому и верим».

### Рабочая гигиена

* `cluster.secret` — `600`, Caddyfile — `640 root:caddy`, `$WEBROOT/cluster` —
  `750`, файлы в нём `640` (`secure_web_files`). Проверка — в тесте
  `tests/test-cluster-channel-security.sh`.
* Разделы отдаются **только** за секретом: без заголовка Caddy отвечает `403`
  раньше, чем дело дойдёт до файлов.
* Своя нода в `cluster.conf` есть, но из опроса исключается (`cluster_peers`),
  поэтому её имя никогда не становится именем файла кэша.

## Что ещё стоит перенести на файловый канал

Разбор всех оставшихся межнодовых вызовов Web API:

| Вызов | Переносится? | Почему |
|---|---|---|
| `POST /v1/cluster/nudge` | **нет, и не надо** | смысл ручки — обогнать крон. Объявление в файле читается тем самым кроном, то есть превратилось бы в no-op. Отказ стоит задержки, а не потери — это законный push |
| `GET /v1/demo/{name}` на ноду демо | **сделано** | нода-владелец публикует раздел `demos`, любая нода отвечает из кэша (`demo_peer_status`). Закрыло [P-73](../issues/CLUSTER.md#p-73) и убрало зависимость кабинета и лендинга от Web API на соседях. Плата — возраст данных до минуты, отдаётся клиенту полем `stale_sec` |
| `POST /v1/demo` (завести профиль на соседе) | **нет, нельзя** | статика ничего не исполняет, а гость ждёт ответа сейчас — ждать чужой синхронизации он не станет. Отказ здесь fail-open: демо выдаётся у себя. Чтобы не жечь таймаут на ноде без демона, она объявляет `WEBAPI=0` в `nodeinfo`, и `demo_pick_node` её не берёт |

Больше межнодовых вызовов Web API нет. `cluster_post` зовётся из одного места
(`nudge`), а Python-хелпер `cluster_request` **удалён** вместе с последним
читающим вызовом: держать готовый «позвать соседа» значит приглашать следующую
сессию повторить ошибку [P-133](../issues/CLUSTER.md#p-133).

**Критерий на будущее, по которому выбирать канал:**

1. Данные или объявление, которое обязано доехать → **файловый канал**, всегда.
2. Ускорение того, что и так доедет → Web API допустим.
3. Живой запрос-ответ, без которого нельзя ответить прямо сейчас → Web API, но
   сначала честно спроси, нельзя ли ответить из кэша с оговоркой о свежести.
   Обычно можно, и тогда исчезает целый класс отказов.
