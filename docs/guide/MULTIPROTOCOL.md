# 08. Мультипротокол: VLESS+REALITY (TCP и XHTTP), Shadowsocks-2022, Trojan/WS, TUIC v5

Нода перестаёт быть «только Hysteria». Тот же пользователь из `users.db`
раздаётся сразу несколькими протоколами, и все они попадают в его подписку.
Клиент (Throne / Hiddify) при импорте видит один сервер как несколько
конфигов на выбор и подключается тем протоколом, который в его сети не
задушен цензором.

## Какие движки и почему

| Протокол | Движок | Причина |
|---|---|---|
| Hysteria 2 (obfs salamander) | `hysteria` (как было) | базовый, не трогаем |
| VLESS + REALITY, raw TCP + XTLS-Vision | **Xray-core** | основной ключ: самый совместимый и самый быстрый на выгрузку |
| VLESS + REALITY, XHTTP | **Xray-core** | резерв к предыдущему на другом порту, см. «Второй VLESS» ниже; XHTTP — изобретение Xray, sing-box его как сервер не умеет |
| Shadowsocks-2022 (+ gRPC API) | **Xray-core** | тот же процесс, hot-add юзеров через `xray api` без рестарта |
| Trojan / WebSocket + TLS | **Xray-core** | тот же процесс; классика, которую понимает любой клиент |
| TUIC v5 | **sing-box** | единственная живая серверная реализация TUIC в 2026 |

Итого рядом с `hysteria-server.service` появляются два опциональных сервиса:
`hy2-xray.service` (VLESS+SS+Trojan) и `hy2-singbox.service` (TUIC). Каждый включается
независимо; если ни один не включён — менеджер работает ровно как раньше.

## Единый источник правды по юзерам

База остаётся одна — `users.db` (`user:pass`). Ни один протокол не заводит
свой список пользователей руками: все креды **детерминированно выводятся** из
`user`, `pass` и узлового секрета `proto.secret`. Это даёт три важных свойства:

* подписка, манифест кластера и конфиги серверов всегда согласованы —
  пересчитать креды можно в любом месте, дополнительное состояние не хранится;
* добавление/удаление юзера в Hysteria (мгновенное, через `auth.type: command`)
  тем же хуком `sub_refresh` синхронизирует Xray и sing-box;
* кластер уже реплицирует `users.db`/roster — новые протоколы едут по тем же
  рельсам без изменений формата обмена.

Деривация (см. `proto_uuid` / `proto_upsk` в `lib/protocols.sh`):

```
UUID(user)  = uuidv5-подобный из sha1(proto_secret | user | pass)   # VLESS, TUIC, пароль Trojan
uPSK(user)  = base64( sha256(proto_secret | "ss" | user | pass)[:keylen] )  # SS-2022
iPSK(node)  = base64( sha256(proto_secret | "ipsk")[:keylen] )       # общий ключ инбаунда SS
TUIC-pass   = pass                                                    # пароль из users.db
```

`keylen` = 16 для `2022-blake3-aes-128-gcm` (дефолт), 32 для `-aes-256-gcm`.

## Параметры узла (`$DATA_DIR/protocols.conf`)

Отдельный от `node.conf` файл, чтобы не смешивать с кластерными настройками:

```
PROTO_VLESS_ENABLED=1
PROTO_VLESSX_ENABLED=0           # второй VLESS поверх XHTTP, по умолчанию выключен
PROTO_SS_ENABLED=1
PROTO_TUIC_ENABLED=1
PROTO_TROJAN_ENABLED=1
PROTO_VLESS_PORT=8443            # TCP
PROTO_VLESSX_PORT=8445           # TCP
PROTO_SS_PORT=8388               # TCP
PROTO_TUIC_PORT=2053             # UDP
PROTO_TROJAN_PORT=8444           # TCP
PROTO_TROJAN_WS_PATH=/           # путь WebSocket
PROTO_SS_METHOD=2022-blake3-aes-128-gcm
PROTO_REALITY_DEST=127.0.0.1:443  # свой же Caddy, НЕ чужой сайт
PROTO_REALITY_SNI=<домен ноды>   # A-запись обязана вести сюда же
PROTO_REALITY_PRIVKEY=...        # генерится xray x25519 при установке
PROTO_REALITY_PUBKEY=...         # pbk в подписку
PROTO_REALITY_SHORTID=...        # sid в подписку
PROTO_XHTTP_PATH=/               # path XHTTP
```

Порты по умолчанию не 443 — 443/80 заняты Caddy под HTTPS-подписку. REALITY
не требует именно 443; порт настраивается в UI.

## Второй VLESS: XHTTP как резерв, а не замена

`PROTO_VLESSX_ENABLED` поднимает **ещё один** VLESS+REALITY-инбаунд
(`vless-xhttp-in`) на своём порту, рядом с основным `vless-in`. Оба ключа лежат
в подписке одновременно, подписи различаются (`VLESS` и `VLESS-X`), дедуп в
`regen_subscriptions` их не схлопывает — он идёт по `host:port`, а порты разные.

**Зачем два инбаунда одного протокола.** Цензор ловит VLESS+TCP+REALITY не по
содержимому — REALITY нечего показать, — а по **поведению**: размеры первых
пакетов и тайминги между ними. Характерный симптом на клиенте: пинг проходит,
соединение устанавливается, а на передаче данных рвётся TLS-хендшейк. От такой
сигнатуры не спасают ни ключи, ни SNI, ни порт: рисунок трафика у транспорта
один и тот же. XHTTP даёт **другой рисунок** (кадры HTTP/2 вместо непрерывного
TCP-потока), поэтому существующее правило на него не попадает.

**Почему именно рядом, а не вместо.** Замену уже пробовали и откатили
(`c5f37a8`), причины никуда не делись:

| Что | Почему мешает сделать XHTTP основным |
|---|---|
| XTLS-Vision | с XHTTP **невалиден**: `flow` обязан быть пустым |
| Выгрузка | у XHTTP она отдельным POST-стримом и вставала в 0; Vision splice'ит uplink прямо в TCP |
| Строгие клиенты | Happ на `xhttp+reality` не идёт вовсе |

Резерв этих недостатков не лечит — он их **обходит по назначению**: клиент,
который XHTTP не умеет, просто берёт из подписки основной ключ. Отсюда
`mode=stream-one` в ссылке: один двунаправленный стрим вместо GET+POST, то есть
ровно та конструкция, из-за которой выгрузка вставала, здесь не используется. В
инбаунде при этом `mode: "auto"` — сервер принимает любой из
`packet-up`/`stream-up`/`stream-one`, режим выбирает клиент.

**Что общее, а что своё.** Ключи REALITY, `dest`, SNI и `PROTO_XHTTP_PATH` —
общие с основным инбаундом: это тот же маскарад на том же домене, отдельный
сертификат и отдельные ключи резерву не нужны. Своё у него только два: флаг и
порт. Порт по умолчанию `8445` (443/80 у Caddy, 8443 у основного VLESS, 8444 у
Trojan).

**`flow` расставляется по транспорту, а не константой.** Это единственное
неочевидное место. VLESS-клиент с `flow: "xtls-rprx-vision"` на XHTTP-инбаунде
для Xray невалиден, поэтому и генератор конфига
(`_proto_xray_vless_clients <flow>`), и заготовка для горячего добавления юзеров
(`_proto_xray_adu_json`, ветка по `.streamSettings.network`) выбирают `flow` по
транспорту того инбаунда, в который кладут клиента. Вбитая константа здесь
ломается тихо и дорого: `adu` вернул бы ошибку, откат увёл бы каждое добавление
юзера в полный рестарт Xray — то есть в разрыв живых сессий всех остальных
(ровно то, от чего избавлялись в «Состав юзеров Xray без рестарта»).

Проверка — `tests/test-vlessx-inbound.sh`: оба инбаунда рядом, `flow` по
транспорту в конфиге и в `adu`, настоящий `xray -test` на собранном конфиге,
совпадение ссылки с инбаундом, чистое выключение.

**Порт под лимит скорости.** Новый слушающий порт обязан попасть в
`_klimit_shape_ports` (`lib/perf.sh`), иначе резерв идёт мимо тарифа целиком —
см. [SPEED-LIMITS.md](SPEED-LIMITS.md).

## TLS

* VLESS+REALITY — отдельный сертификат не нужен: `dest` указывает на **свой
  же Caddy** (`127.0.0.1:443`), и REALITY заимствует его настоящий TLS.
  Чужой популярный домен в `dest`/`SNI` ставить нельзя — его A-запись живёт в
  чужой AS, а клиент идёт на наш адрес, и это несовпадение стоит бана всего
  адреса: [issues/PROTOCOLS.md P-129](../issues/PROTOCOLS.md#p-129).
* SS-2022 — без TLS.
* TUIC (QUIC) и Trojan/WS — нужен TLS, серт общий (`$DATA_DIR/proto/tuic.{crt,key}`).
* Hysteria 2 — свой серт по путям из её `config.yaml`.

**Серт берётся у Caddy, самоподписанный — только запасной вариант.**
`proto_sync_certs` копирует по движкам тот самый Let's Encrypt, который Caddy
держит на домен ноды ради HTTPS-подписки, и перезапускает только тот движок,
чей файл изменился (серт они читают лишь при старте). Зовётся из
`proto_bootstrap` и из крона `--collect`: перевыпуск бывает раз в ~60 дней, в
остальные разы это две `cmp` и выход. Внутренний CA Caddy (когда ACME не
удался) отсеивается по `subject == issuer`, протухший — по `checkend`.

Почему не оставили самоподписанный с insecure-флагом в ссылке: **половина
клиентов этот флаг уже не понимает**. Xray-core удалил `allowInsecure` совсем
(мигрировал в `pinnedPeerCertSha256`), у части клиентов его нет в схеме
`hy2://`, а серт без `subjectAltName` Go-стек отвергает ещё до проверки
цепочки. Живьём это выглядело так: в клиенте на Xray-core работал и пинговался
один VLESS (REALITY серт не проверяет), Trojan/TUIC/HY2 молча отваливались на
TLS. Подробности и замеры — [issues/PROTOCOLS.md P-50](../issues/PROTOCOLS.md#p-50).

Отсюда флаг `.tls.trusted` в `$DATA_DIR/proto/`, по которому строятся ключи:

| Есть настоящий серт | Нет (нода без домена) |
|---|---|
| ссылки без `allowInsecure`/`allow_insecure`/`insecure` | флаги на месте, как раньше |
| `hysteria2://` идёт с SNI **домена ноды** | SNI хоста маскарада |
| — | запасной самоподписанный серт, обязательно с SAN |

Старые сохранённые у пользователей ключи от смены серта не ломаются: они идут
с insecure-флагом, а такой клиент пропускает проверку целиком, включая имя.

**Ключ Hysteria2 выдаётся из ДВУХ мест, и TLS-параметры правятся в обоих:**

| Путь | Функция | Куда идёт |
|---|---|---|
| ссылка `hysteria2://` | `build_user_link` (`lib/sub_links.sh`) | подписка, манифест пирам, Web API, бот |
| JSON-конфиг sing-box | `generate_user_config` (`lib/users.sh`) | пункт 8 карточки юзера в TUI |

Правка только одного из них уже стоила [P-74](../issues/PROTOCOLS.md#p-74):
конфиг уходил с SNI маскарада и сервер рвал хендшейк, пока ссылка на тот же
ключ работала. Совпадение обоих путей сторожит `tests/test-client-config.sh`.

Важное свойство sniGuard: при чужом SNI хендшейк закрывает **сервер**, поэтому
`insecure` на клиенте такой конфиг НЕ спасает, а `sing-box check` его принимает —
ошибка видна только в логе подключения (`CRYPTO_ERROR 0x150 … tls: internal error`).

## Точки интеграции с существующим кодом

| Что | Где | Как меняется |
|---|---|---|
| Ссылки в подписке | `regen_subscriptions`, `subscription.sh` | после `hysteria2://` дописываем `proto_user_uris "$user" "$pass" "$ip"` |
| Манифест кластера | `publish_manifest` | те же доп. строки `user \t uri` на каждый включённый протокол |
| Синхронизация юзеров | `sub_refresh` | добавлен вызов `proto_sync_users`: в Xray состав едет на лету через `adu`/`rmu` (см. ниже), sing-box рестартует |
| Установка/настройка | новый `lib/protocols.sh` + меню Настройки | скачивание бинарников, ключи, конфиги, systemd, firewall |
| Трафик | `collect_traffic` | читает кумулятивы Hysteria и Xray БЕЗ сброса и докладывает в `STATS_FILE` дельту к базе `traffic_prev.dat` — звать можно сколько угодно часто |
| Онлайн | `refresh_online` | `proto_online_ip_lines` добавляет АДРЕСА Xray/sing-box к адресам Hysteria, устройства считаются по уникальным IP |
| Кик | — | отдельного кика по доп. протоколам нет, см. «Учёт трафика и онлайна» |
| Firewall | `ensure_proto_ports_open` | открыть TCP 8443/8388, UDP 2053 |

Дедуп в `regen_subscriptions` идёт по `host:port`; у каждого протокола свой
порт, поэтому строки не схлопываются и живут рядом.

## Что переиспользуется как есть

Срок действия, персональные лимиты/тарифы, токены подписки, платежи,
Telegram-привязки, каркас Web API, tc-шейпинг скорости (режет по IP+порт —
добавляются лишь фильтры на новые порты). Им нужно лишь скормить данные новых
протоколов, менять логику не требуется.

## Учёт трафика и онлайна

* **Трафик VLESS/SS-2022** снимается из Xray StatsService штатным CLI
  `xray api statsquery` — **без `-reset`** — и докладывается в тот же
  `STATS_FILE`, что и Hysteria: `collect_traffic` сводит кумулятивы обоих
  движков и прибавляет дельту к базе `traffic_prev.dat`. Сбрасывать счётчики
  нельзя: их же читают минутная активность и 5-секундный спидометр, и сброс
  крал у них интервал — при открытом TUI скорость падала в ноль (P-37). Пока
  сбор Xray висел только на 30-минутном кроне, VLESS-часть строки стояла на
  месте, а Hysteria-часть шла живьём (P-35). Докладывают все сборщики через
  общий `_stats_add`/`_stats_add_cum` (один awk под flock, P-21). Квоты и
  статистика в кабинете учитывают эти байты.
* **Трафик TUIC** — per-user счётчиков у sing-box нет (StatsService только за
  тегом сборки `with_v2ray_api`, которого в релизах нет; `metadata.user` clash_api
  не отдаёт). Считаем дельты байт по соединениям между минутными снимками, юзера
  берём по `sourceIP` и ТОЛЬКО для адресов, за которыми стоит ровно один юзер
  (`_proto_ip_sole_owner_lines`). Общий CGNAT-адрес не резолвится ни в кого — его
  байты не засчитываются никому, недосчитать безопаснее, чем списать чужую квоту.
  См. P-02.
* **Онлайн** сливается в `refresh_online`: Hysteria `/online` + online-статистика
  Xray + активные TUIC-соединения из `clash_api` sing-box (`proto_online_ip_lines`,
  best-effort — при сбое основной онлайн не ломается). Счётчики онлайна Xray
  заводит только при `"statsUserOnline": true` в `policy.levels."0"`, и лежат они
  в ОТДЕЛЬНОМ реестре: `statsquery -pattern online` отдаёт пустой `{}` даже при
  непустом трафике, читать их можно только командой `api statsonline -email` по
  одному юзеру за раз (при нуле сессий поля `value` в ответе нет). См. P-15.
  Онлайн TUIC — это соединения `clash_api`, разложенные по юзерам через
  `sourceIP` (`proto_tuic_activity_lines ips`), потому что `metadata.user`
  sing-box не отдаёт. См. P-17. Онлайн резолвит адрес в самого свежего юзера, а
  трафик — только однозначные адреса: ошибиться индикатором дешевле, чем квотой.
* **Состав юзеров TUIC** применяется рестартом (управления на лету у sing-box
  нет), но не сразу: `proto_tuic_apply` ждёт, пока по TUIC никого не останется,
  и не дольше `TUIC_APPLY_MAX_DELAY_SEC` (600 с); повторную попытку делает
  минутный крон. Пачка новых юзеров = один рестарт. Ждёт только состав: смена
  порта или инбаундов видна по структурному хэшу и применяется сразу. См. P-01.
* **Кик** отдельной командой не делается. Была функция `proto_kick`, но она
  никогда не вызывалась и не работала: `xray api rmu` принимает email
  **позиционно**, а она передавала его флагом `-email`, которого у команды нет
  — вызов падал в `/dev/null`. Удалена. Сессия юзера рвётся сама, когда он
  выпадает из состава (`rmu` в `_proto_xray_hot_apply`). Понадобится настоящий
  кик — это `rmu` по тегам из `_proto_xray_tags` плюс возврат через
  `_proto_xray_adu_json`, три строки. У sing-box per-user кика нет вовсе.

## Состав юзеров Xray без рестарта (`_proto_xray_hot_apply`)

Конфиги пересобираются из `users.db` на каждый `sub_refresh`, а
`_proto_apply_service` рестартует сервис, если хэш конфига изменился. Состав
юзеров — часть конфига, поэтому **каждый новый юзер рвал сессии VLESS/SS/Trojan
у всех остальных юзеров ноды**, и так на каждой ноде кластера. Hysteria не
страдала: у неё внешний auth-скрипт, состав читается на лету.

Xray умеет менять состав по gRPC (`HandlerService`, инбаунд `api` на
`127.0.0.1:$XRAY_API_PORT` — он уже был поднят). Поэтому рестарт нужен только
когда изменились **параметры узла**, а не состав.

**Как отличается одно от другого.** Два слепка вместо одного:

| Файл | Что в нём | Меняется от |
|---|---|---|
| `.xray.struct` | sha256 конфига **без** списков клиентов (`jq 'del(.inbounds[].settings.clients)'`) | портов, ключей REALITY, состава инбаундов |
| `.xray.users` | отсортированные строки `user<TAB>uuid<TAB>upsk` | состава юзеров и их паролей |

Совпал `struct` — правим состав на лету. Не совпал — обычный рестарт.
Строка юзера включает производные ключи, поэтому **смена пароля видна как
удаление + добавление**, а не как «ничего не изменилось».

**Дельта.** `comm` по двум отсортированным спискам (`LC_ALL=C`, иначе локаль
вызывающего меняет порядок и сравнение врёт): пропавшие строки → `rmu` по
каждому включённому тегу, новые → `adu`.

**Формат `adu`.** Команда разбирает аргумент как **полный** конфиг, а не как
кусок: инбаунд без порта отвергается с `Listen on AnyIP but no Port(s) set`.
Поэтому `_proto_xray_adu_json` берёт живой `xray.json` и подменяет в нём только
списки клиентов — порты, `method`/uPSK и `streamSettings` тогда заведомо
валидны. Инбаунд `api` отсеивается сам: у него нет `clients`.

**Откат.** Любой сбой (нет `jq`, сервис не запущен, первый запуск без слепков,
`adu` вернул ошибку) — возврат 1, и вызывающий делает обычный рестарт. Конфиг
на диске к этому моменту уже правильный, поэтому частично применённая дельта
безопасна: рестарт приводит всё в порядок. При сбое слепки **не** обновляются —
иначе юзер остался бы без доступа при «свежем» состоянии.

Проверки — `tests/test-xray-hotapply.sh` (дельта, гейт по `struct`, откат).

## Известные ограничения (осознанные, задокументированы)

1. **Побайтный трафик TUIC** (sing-box) считается ПРИБЛИЖЁННО и не для всех
   (`proto_collect_tuic_traffic`, раз в минуту). Per-user счётчиков движок не
   даёт: StatsService собран только с тегом `with_v2ray_api`, которого в
   официальных релизах нет (в бинарнике 1.13.14 лежит «v2ray api is not included
   in this build»), а `metadata.user` у clash_api отсутствует (проверено на
   1.13.14: 44 соединения подряд, поля нет ни у одного). Поэтому: дельты байт
   соединений между минутными снимками + резолв юзера по `sourceIP`, но ТОЛЬКО
   для адресов с единственным владельцем — общий CGNAT-адрес не засчитывается
   никому. Плюс теряются хвосты соединений, закрывшихся между снимками.
   Точный per-user учёт возможен через per-IP nftables-счётчики на порту TUIC
   (см. паритет лимитов, docs/guide/SPEED-LIMITS.md). Hysteria + VLESS/SS —
   точно. См. P-02/P-17.
2. **Онлайн/активность** теперь считаются по ВСЕМ протоколам
   (`collect_activity` + `proto_activity_cum_lines`: Hysteria + Xray + TUIC), флаг
   `active` синкается по кластеру; Web API `online` и live-SSE берут его
   (docs/guide/ONLINE.md).
3. **Активностный жёсткий лимит устройств** (`enforce_active_node_limit`,
   анти-абуз) строится на активности Hysteria. Отдельного per-протокол kick одного
   устройства нет; лимит на число ссылок подписки и удаление/бан работают для всех
   протоколов (через регенерацию конфига).
4. **Применение изменений состава юзеров** для VLESS/SS/TUIC — перезапуск сервиса
   при реальном изменении конфига (сравнение хеша). Hysteria остаётся горячей;
   доп. протоколы кратко переподнимаются только когда состав/параметры меняются.
