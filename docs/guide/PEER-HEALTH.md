# Здоровье пиров: видимая недоступность нод

## Зачем

`cluster_sync` всегда умел определять недоступного пира, но сообщал об этом
**только** в `verbose`-режиме, то есть при ручной синхронизации из TUI. Cron
гоняет `hy2-manager.sh --cluster-sync >/dev/null 2>&1` — и текст, и код возврата
уходили в `/dev/null`.

Итог: нода могла сутками не отдавать ключи клиентам, а главное меню менеджера
всё это время показывало `Подписка: 💚 нода «…» · нод в кластере: 3`. Число нод
читается из `cluster.conf` (реестр), а не из факта доступности — реестр же не
меняется от того, что пир умер.

Разбор конкретного инцидента — `docs/issues/CLUSTER.md`, P-31.

## Как устроено

### Диагноз пира — `peer_probe()` (`lib/cluster.sh`)

Порядок проверок принципиален:

1. **Сначала реальный запрос** `cluster_call "$host" /cluster/manifest` — он
   единственный судья доступности. Ответил — пир здоров, дальше не смотрим.
2. Только если запрос **упал**, выясняем причину — проверками, которые ничего
   не решают, а лишь классифицируют уже случившийся отказ:
   - `getent hosts` не резолвит → `домен не резолвится (нет A-записи / DNS)`;
   - `openssl s_client :443` не встаёт → `нет TLS на :443 (сертификат/нода лежит/файрвол)`;
   - иначе → `TLS есть, но данные не отдаёт (секрет кластера/Caddy)`.

> **Почему не наоборот.** DNS-претест перед запросом выглядит логичнее, но даёт
> ложные срабатывания: после смены NS апстрим-резолвер держит негативный кэш
> (`SOA minimum`, часто 1800 с) и отдаёт `NXDOMAIN` через раз. Живой пир,
> до которого `curl` достучался бы сам, помечался бы мёртвым. Проверка-судья
> должна быть одна, остальные — объяснение.

### Хранение — `peer_health_set()`, `$PEERS_HEALTH_FILE`

`$PEERS_DIR/.health`, строки `host|name|ok|ts|причина`. Пишется **на каждом**
прогоне `cluster_sync`, включая молчаливый cron-прогон — в этом весь смысл
правки. Одна строка на хост, перезапись по `host`.

### Отчёт — `cluster_health_report()`, `cluster_health_banner()`

Проблемным считается пир, у которого:

- последний вердикт `ok=0`, **или**
- последняя успешная синхронизация старше `PEER_STALE_SEC` (900 с). Это ловит
  случай «cron не отработал вовсе»: свежего вердикта нет, и молчание само по
  себе является симптомом.

Из отчёта исключены своя нода и хосты, которых уже нет в `cluster.conf` (иначе
удалённый пир тревожил бы вечно).

`cluster_health_banner()` — одна строка для шапки, пусто = всё хорошо.

### Показ

`hy2-manager.sh`, блок предупреждений главного меню (рядом с «ожидают
перезапуска»): баннер + построчная расшифровка по каждому проблемному пиру.
Вызов через `declare -F`, чтобы старый `lib/` не ронял меню.

## Проверка

`tests/test-cluster-health.sh` — сеть не трогает, проверяет разбор `.health`
против `cluster.conf`: битый, протухший, живой, своя нода, пир вне реестра.

## Как дополнять

- **Новый вид отказа** → ветка в `peer_probe()`. Держите порядок: судья первым,
  классификаторы после.
- **Новый потребитель** (бот, Web API) → зовите `cluster_health_report()`,
  не парсьте `.health` сами.
- **Порог протухания** → `PEER_STALE_SEC`; он должен быть заметно больше
  периода cron (`*/5`), иначе один пропущенный прогон даст ложную тревогу.
