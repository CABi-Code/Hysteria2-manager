# Устройства: как число закрепляется за юзером и как оно ограничивает

Документ описывает **то, что реализовано сегодня**, без предложений. §5 —
измеренные возможности движков (что можно и чего нельзя в принципе),
§6 — известные расхождения. Реестр проблем — [../issues/LIMITS.md](../issues/LIMITS.md).

Надстройка (`надстройка`) теперь **продаёт устройства** сверх тарифных и
возвращает за них деньги (`надстройка/docs/DEVICES.md`). Для менеджера это
значит: число устройств стало платным атрибутом подписки, и от того, как оно
хранится, синхронизируется и применяется, зависят чужие деньги.

## 1. Что менеджер называет «устройством»

Не физический аппарат и не сессия, а **уникальный IP-адрес, с которого юзер
сейчас в сети**. Считает `refresh_online()` (`lib/online.sh`): со всех
протоколов собираются строки `user|ip`, дубли схлопываются. Один телефон,
держащий подписку одновременно на Hysteria, VLESS и TUIC, — это одно
устройство, потому что IP один ([ONLINE.md](ONLINE.md)).

Следствия, которые надо помнить при продаже:

- **CGNAT и общий Wi-Fi**: несколько телефонов за одним внешним адресом
  считаются одним устройством. Продажа устройств — продажа *адресов*, а не
  аппаратов.
- **Роуминг**: телефон, сменивший сеть, ненадолго может дать два адреса сразу
  (старая сессия ещё не отвалилась) и выглядеть как два устройства.
- Адрес Hysteria-сессии берётся не из API (его там нет), а из `authmap.dat`,
  куда пишет auth-скрипт на каждое подключение. Нет записи — юзеру засчитывается
  одно устройство, а не ноль.

Отдельно есть **справочное** число `devices_seen` в API — уникальные IP за
последние сутки (`user_ip_count`, `webapi/wa_users.py`). Оно ни на что не
влияет и с лимитом не сравнивается: величины несопоставимы (сутки истории
против «сейчас в сети»).

## 2. Где живёт само число

`userlimits.dat`, строка `user|devices|hardcheck|rate` (`lib/limits.sh`):

| Поле | Смысл |
|---|---|
| `devices` | Персональный лимит. `0` — «нет персонального, действует глобальный `POOL_LIMIT`». Значение по умолчанию, если строки нет вовсе, — `DEFAULT_DEVICES=1` |
| `hardcheck` | `0/1` — ручная «жёсткая проверка» (см. §4) |
| `rate` | Тариф скорости, Мбит/с ([SPEED-LIMITS.md](SPEED-LIMITS.md)) |

Рядом `userlimits_ts.dat` — `user|ts`, метка последнего изменения.

**Число закреплено за подпиской, а не за нодой.** `cluster_apply_userlimits`
(`lib/cluster.sh`) сливает файлы нод по правилу LWW-по-`ts`: побеждает более
свежая запись, и она разъезжается по всему кластеру
([CLUSTER-SCOPE.md](CLUSTER-SCOPE.md)). Поэтому лимит нельзя «поднять только на
своей ноде» — правка либо уедет всем, либо будет перезатёрта чужой более свежей.

Запись всегда идёт через `set_user_limits()`; обёртки `set_user_devices` /
`set_user_hardcheck` / `set_user_rate` меняют одно поле и сохраняют остальные.
Пустой `ts` = «изменение наше» → ставится текущее время и вызывается
`publish_cluster_userlimits`. Непустой `ts` = «применяем чужое», публикации нет
(иначе синхронизация зациклилась бы).

## 3. Кто меняет число

| Кто | Что делает | Файл |
|---|---|---|
| TUI, меню устройств | `+1` / `−1` / ввод числа вручную | `lib/ui_devices.sh` |
| Web API `POST /v1/users/{u}/limits` | ставит `devices` (и `rate`), **сохраняя текущий `hardcheck`**; принимает `0…1000` | `webapi/hy2-webapi.py` → `dispatch.sh set-limits` |
| Бот менеджера, оплата тарифа | `tariff_raise_devices` — поднимает до тарифного, но **не опускает** (P-42) | `lib/tgbot_client.sh`, `lib/limits.sh` |
| Бот менеджера, создание юзера админом | ставит указанное в команде число | `lib/tgbot_daemon.sh` |
| Демо-профиль | всегда `1` | `lib/demo.sh` |
| Синхронизация кластера | применяет запись пира, если её `ts` свежее | `lib/cluster.sh` |

Надстройка ходит только через Web API и считает себя источником правды по
**оплаченным** устройствам: на каждой покупке она заново ставит
`тарифные + докупленные`. Поэтому ручная правка лимита у её пользователя живёт
до его ближайшей покупки. Оплата тарифа в боте менеджера докупленное больше не
стирает: `tariff_raise_devices` поднимает лимит, но не опускает (P-42).

## 4. Как число ограничивает

Сначала два эффективных потолка (`lib/devlimits.sh`):

```
pool_cap(user) = devices(user), если > 0; иначе POOL_LIMIT   # 0 = ∞
node_cap(user) = min(NODE_LIMIT, pool_cap)                   # NODE_LIMIT=0 → pool_cap
```

`POOL_LIMIT` — потолок подключений подписки по всему кластеру, `NODE_LIMIT` — на
одну ноду; оба в `node.conf` и синхронны по кластеру. **Персональное число
приоритетнее глобальных.**

Дальше — три механизма, и ни один из них не отказывает в подключении.

### 4.1. Аутентификация НЕ режет

`hysteria-auth.sh` проверяет только пару `user:pass` по `users.db` и пишет
`user|ip|ts` в `authmap.dat`. Никакой проверки лимита там нет **намеренно**:
на этапе auth она ломала бы переподключения и переезд на другую ноду.
`authlimits.dat` (`write_authlimits`) остался снимком для диагностики и на
решение о пуске не влияет.

### 4.2. Счётчиковый кик — раз в минуту

`enforce_device_limits()` (`lib/devlimits.sh`), вызывается из
`cluster_online_sync` по крону `* * * * * --online-sync`:

1. считает уникальные адреса юзера на этой ноде и по кластеру
   (`cluster_user_connections` = свои + сумма из `*.stats` пиров);
2. если по кластеру больше `pool_cap` **или** локально больше `node_cap` —
   шлёт `POST /kick` на API Hysteria и пишет строку в `limit.log`;
3. жёсткая проверка от этого кика **не освобождает** (P-41, до 4.15.51
   освобождала): §4.3 ограничивает число нод, адреса внутри ноды держит только
   этот кик.

Кик рвёт **все** Hysteria-сессии юзера на этой ноде, а не лишние. Клиент
переподключается сам, и через минуту, если адресов снова больше лимита, его
кикнет снова. То есть лимит не блокирующий, а «пилообразный»: лишнее устройство
работает урывками, а не получает отказ.

С 4.15.52 кикаются и доп. протоколы (`proto_kick_user`), каждый своим
способом — одной командой «разорвать сессии юзера» не умеет ни Xray, ни
sing-box:

* **Xray** — «заморозка»: юзер снимается из инбаундов (`api rmu`) на
  `XRAY_KICK_FREEZE_SEC` (10 с) и возвращается (`api adu`). Установленные
  соединения при этом **не рвутся** (проверено, см. §5), но ни одно новое в
  это окно не проходит — для браузера это равносильно обрыву. Возврат делает
  отдельный процесс; если он не доживёт, юзера вернёт `proto_xray_repair` на
  ближайшем прогоне энфорсера (он же чинит любой другой рассинхрон состава).
Выключается на ноде: `PROTO_KICK=0` в `node.conf` возвращает поведение до
4.15.52 (кик только на Hysteria). Включение стоит делать осознанно: те, кто
годами сидел над лимитом с клиентом на VLESS/TUIC, впервые это почувствуют.

* **TUIC** — точечное закрытие соединений через clash API
  (`DELETE /connections/{id}`). Юзера в API нет (`metadata.user` всегда null,
  P-17), поэтому берутся соединения с адресов, принадлежащих ему
  **однозначно** (`_proto_ip_sole_owner_lines`): за общим CGNAT-адресом может
  сидеть чужой. Креды остаются валидными — клиент откроет новые потоки.

Гейта «включён ли глобальный лимит» здесь нет: при `POOL_LIMIT=0` персональные
числа (тарифы, демо) продолжают действовать.

### 4.3. Жёсткая проверка — по активным НОДАМ, а не по устройствам

`enforce_active_node_limit()` работает только для юзеров, у которых
`get_user_hardcheck_effective = 1` (ручной флаг ИЛИ окно анти-абуза). Она
сравнивает с `pool_cap` **число нод, на которых юзер сейчас реально гонит
трафик** (скорость за минуту ≥ порога), и, если нод больше лимита, кикает
сессии на «лишних» — тех, что стали активны позже. Число устройств ВНУТРИ ноды
она не ограничивает вовсе — это работа §4.2, и с 4.15.51 они складываются.

### 4.4. Анти-абуз — детект шаринга, не лимит

`abuse_observe()` каждую минуту считает, на скольких нодах юзер активен
одновременно; превышение `pool_cap` копит баллы (0…100, сами угасают).
Часовой `abuse_correct()` (`0 * * * * --antiabuse`) при балле ≥ 60 включает
**авто-жёсткую проверку** на 6 часов — то есть переводит юзера из §4.2 в §4.3.
Баллы и окно разъезжаются по кластеру (LWW / максимум), сам по себе анти-абуз
никого не кикает.

## 5. Что движки умеют на самом деле (измерено)

Проверялось на изолированных инстансах (свой порт, свой конфиг), боевые сервисы
не трогались. Даты — 4.15.5x, версии: Hysteria 2.9.2, Xray 26.3.27,
sing-box 1.13.14.

**Hysteria**

| Вопрос | Ответ |
|---|---|
| Может ли auth-скрипт вернуть id, не равный логину? | **Да.** Вернули `user.1` — под этим id пошли и `/online`, и `/traffic`, и `/kick`. Это делает возможными «слоты»: отдельный кред на устройство внутри одного аккаунта |
| Видно ли два устройства за ОДНИМ адресом на одном креде? | **Да.** Два клиента с одного адреса дали `{"user.1": 2}` — считаются соединения, а не адреса. NAT не мешает |
| Кик по id трогает соседние слоты? | **Нет.** Соседний слот того же юзера продолжал работать |
| Можно ли выбрать, какое соединение оборвать? | **Нет.** При двух соединениях кик закрыл одно, и какое — не выбирается (проверено в обоих порядках подключения) |
| Можно ли вытеснить занявшего в момент подключения нового? | **Нет.** Кик, вызванный из auth, убивает и новичка тоже — слот остаётся пустым |
| Работает ли отказ в auth? | **Да, чисто.** Второй клиент получает `authentication error`, занявший слот не шелохнулся |

Вывод: жёсткий лимит на Hysteria делается **отказом** в auth-скрипте, а не
вытеснением.

**Xray**

| Вопрос | Ответ |
|---|---|
| Что считает `api statsonline`? | **Уникальные адреса, не сессии.** На боевой ноде `online` в точности равен размеру `statsonlineiplist` у всех проверенных юзеров |
| Видно ли два устройства за одним адресом на одном креде? | **Нет.** Два независимых клиента с одного адреса дали `online=1` |
| Рвёт ли `api rmu` установленные соединения? | **Нет.** Идущая загрузка пережила снятие юзера; новые соединения при этом не проходят |
| Есть ли хук на подключение (отказ)? | Нет |
| Прочее | Реестр онлайн-адресов — история с TTL (встречаются метки двухсуточной давности), поэтому энфорсер фильтрует их окном 120 с. Адреса loopback в реестр не попадают вовсе — грабли при локальном тестировании. `api rmu`/`adu`/`inbounduser` требуют `HandlerService` в `api.services` |

**TUIC (sing-box)**

| Вопрос | Ответ |
|---|---|
| Атрибуция соединения к юзеру | Нет: `metadata.user` всегда null (P-17), резолвим по адресу |
| Гранулярность списка соединений | Отдельный поток, а не клиент (в метаданных `network`/`destinationPort`) — считать по нему устройства нельзя |
| Точечный разрыв | Есть: `DELETE /connections/{id}` |

**Итог по продаже устройств:** число устройств можно сделать жёстким только на
Hysteria (отказ по слоту). На Xray и TUIC два устройства за одним адресом
неразличимы в принципе — там ограничение остаётся мягким.

## 6. Известные расхождения

- **`P-16` — кик доп. протоколов** (частично закрыт в 4.15.52): Xray и TUIC
  теперь кикаются, но у Xray нельзя оборвать уже установленную сессию, а у TUIC
  закрытие потока не отзывает кред. Полностью «как у Hysteria» не будет.
- **`P-07`** — детект шаринга слепнет, если нод в профиле меньше `pool_cap`.
- `P-41` и `P-42` закрыты в 4.15.51.

## 7. Что это значит для продажи устройств

- Число из `userlimits.dat` — единственное, что менеджер понимает под лимитом,
  и оно же приходит в API как `limits.devices`. Надстройка строит на нём
  ползунок и проверку возврата, поэтому **любая ручная правка этого числа у
  платящего пользователя двигает его платный баланс прав**.
- Правка через TUI не отзывается в надстройке никак: она узнаёт новое число при
  следующем открытии витрины и просто перестанет считать «лишние» устройства
  оплаченными (продать их человек не сможет). Деньги при этом не теряются —
  на стороне надстройки возврат ограничен уплаченным.
- Обратный случай — админ **поднял** лимит руками: надстройка не даст продать
  подарок, нижняя граница ползунка считается от её собственной записи о
  докупках.
- Ограничение применяется на всех протоколах, но с разной строгостью (§5):
  Hysteria — по соединениям, Xray и TUIC — по адресам, то есть домашние
  устройства за одним роутером там считаются за одно.

## 8. Файлы

| Файл | Что в нём |
|---|---|
| `lib/limits.sh` | Хранение `user\|devices\|hardcheck\|rate`, метки времени, сеттеры |
| `lib/devlimits.sh` | `pool_cap`/`node_cap`, `enforce_device_limits`, `enforce_active_node_limit`, `write_authlimits` |
| `lib/protocols.sh` | `proto_kick_user`, `proto_xray_kick` (заморозка), `proto_xray_repair`, `proto_tuic_kick` |
| `tests/test-device-limits.sh` | Тариф не опускает лимит, жёсткая проверка не освобождает, выбор соединений TUIC-кика |
| `lib/online.sh` | Уникальные адреса «сейчас в сети» — то, с чем сравнивается лимит |
| `lib/antiabuse.sh` | Баллы шаринга, окно авто-жёсткой проверки, `get_user_hardcheck_effective` |
| `lib/cluster.sh` | `cluster_apply_userlimits` (LWW), вызов энфорсеров раз в минуту |
| `lib/ip_tracking.sh` | `authmap.dat` (живой `user→IP`) и `ips.dat` (история для `devices_seen`) |
| `lib/ui_devices.sh` | Правка числа устройств из TUI |
| `webapi/hy2-webapi.py`, `webapi/dispatch.sh` | `POST /v1/users/{u}/limits`, сохранение `hardcheck` |
| `lib/tgbot_client.sh` | Установка тарифных устройств при оплате в боте |
| `/etc/hysteria/manager/hysteria-auth.sh` | Auth без проверки лимита + запись адреса |
