# Ссылку-подписку открыли браузером

Ссылка `https://<домен ноды>/sub/<token>` предназначена клиенту (Hiddify, Happ,
v2rayTun, sing-box). Но её регулярно вставляют в адресную строку браузера — из
любопытства, по ошибке, или потому что «ссылка же, надо открыть». До сих пор
человек получал в ответ простыню base64: технически верно, на вид — сломалось.

Теперь такой заход уводится на страницу подписки в кабинете: там срок, расход,
устройства и продление. Ключи браузеру не показываются вовсе.

Код: `lib/node.sh` (настройка `SUB_WEB_URL`), `lib/caddy.sh` (матчер и редирект),
`lib/ui_subscription.sh` (меню «Оформление подписки» → «Кнопки и ссылки»),
`webapi/wa_payload.py` + `webapi/hy2-webapi.py` (кто владелец токена).

## Как отличается браузер от клиента

Единственный признак, который не надо ниоткуда выводить: **`Sec-Fetch-Mode:
navigate`**. Его ставит сам браузер — переход по адресу, а не запрос за файлом,
— и подделать его страница не может (заголовок в списке запрещённых для
`fetch`). Ни один клиент подписки его не шлёт: клиент делает обычный HTTP-запрос
за содержимым.

Почему не `User-Agent`: он приходит от кого угодно и каким угодно, а половина
клиентов честно пишет туда своё имя только иногда (см.
[SUB-CLIENTS.md](SUB-CLIENTS.md)). Признак, которым можно управлять из запроса,
для развилки «показать секрет или нет» не годится.

Что этим НЕ ловится: браузеры без `Sec-Fetch` (Safari до 16.4, Firefox до 90) и
встроенные webview некоторых приложений. Они получат старый ответ — список
ключей. Это осознанный размен: добавлять сюда второе условие (`Accept:
text/html`) стоит только если такие заходы окажутся заметны, потому что каждое
лишнее условие — это риск увести в браузер настоящий клиент, а это уже потеря
доступа, а не косметика.

## Конфигурация

Настройка **`SUB_WEB_URL`** — база адреса кабинета, общая для кластера
(`SETTING_KEYS`, last-write-wins, см. [CLUSTER-SCOPE.md](CLUSTER-SCOPE.md)):
задаётся на одной ноде и разъезжается на все, `cluster_apply_settings` сам
перепекает Caddyfile.

Пусто (значение по умолчанию) — **редирект не генерируется вовсе**, поведение
ровно прежнее. Это важно для обновления: нода, которой адрес не задали, ничего
не меняет в своей раздаче.

Блок в Caddyfile появляется ПЕРЕД `handle /sub/*` — `handle`-блоки
взаимоисключающие и проверяются по порядку:

```
    @sub_browser {
        path /sub/*
        header Sec-Fetch-Mode navigate
    }
    handle @sub_browser {
        redir "<SUB_WEB_URL>{uri}" 302
    }
```

`{uri}` — путь запроса целиком (`/sub/<token>` и строка запроса), поэтому у
кабинета тот же адрес, и токен ему известен. Хвостовой слэш у настройки
срезается (`sub_web_url`), иначе получалось бы `//sub/…`.

Код ответа **302, не 301**: адрес кабинета может смениться, а 301 браузеры
кэшируют навсегда — включая тот, где кабинета ещё не было.

## Кто владелец токена

Кабинету нужно знать, чью подписку открыли. Отдаёт это

```
GET /v1/users/by-subtoken/<token>     scope: read
```

— тот же payload, что `GET /v1/users/{name}` (см. [API.md](API.md)).

- Обратный поиск идёт и по своей базе токенов, и по кэшам токенов пиров
  (`*.subtokens`): у каждой ноды для одного человека **свой** токен, и ссылка
  могла быть выдана любой из них.
- Токен — секрет самого человека: предъявивший его и так скачивает по нему
  ключи. Новых прав ручка не открывает, поэтому и scope у неё `read`.
- Формат токена проверяется до поиска (латиница и цифры, 16–64) — в файлы и
  команды значение не попадает, но мусор незачем гонять по базе.

## Как дополнять

- **Другая цель редиректа** — только `SUB_WEB_URL`, кода это не касается.
- **Ещё один признак браузера** — второе условие в `@sub_browser` делает матчер
  строже (условия внутри — «И»). Нужен «ИЛИ» — это второй матчер и второй
  `handle` перед ним; помните про цену ошибки, описанную выше.
- **Страница, куда уводим** — не в этом репозитории: нода знает только адрес.
