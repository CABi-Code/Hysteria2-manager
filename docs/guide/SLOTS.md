# Слоты: устройство = своя ссылка со своим паролем

Документ описывает **то, что реализовано**. Замысел целиком, включая ещё не
написанные фазы, — [../design/SLOTS/README.md](../design/SLOTS/README.md).
Как устройства считаются и ограничиваются сегодня —
[DEVICE-LIMITS.md](DEVICE-LIMITS.md).

Реализовано: у каждой доп. ссылки подписки свой пароль и **свой id в движке**,
поэтому сессии считаются отдельно по каждой ссылке — включая устройства за одним
домашним адресом. Занятый слот **отказывает** второму устройству
(`SLOT_REJECT=1`, по умолчанию выключено).

## 1. Зачем

«Устройство» в менеджере — уникальный адрес, и одну ссылку можно раздать кому
угодно. Слот привязывает ссылку к **своему креду**, а креды выдаются по числу
оплаченных устройств.

Занятость меряется **сессиями слота**, а не адресами, поэтому телефон и ноутбук
в одной квартире на одной ссылке различаются: второй получит отказ. Что при этом
всё же не ловится — §6.

## 2. Что такое слот

Слот = **токен подписки**. У юзера может быть несколько ссылок
(`sub_link_add`), и их число уже ограничено количеством устройств
(`sub_links_allowed`). Слоты доводят это до конца: ссылка отдаёт свой пароль.

```
пароль слота = sha256("<пароль юзера>|<токен>")   первые 32 символа
```

Ни номеров, ни отдельного хранилища: пароль юзера и токен уже синхронны по
кластеру, поэтому любая нода получает то же значение. Добавление ссылки не
сдвигает пароли остальных — токен уникален и не меняется.

**Основной токен остаётся на базовом пароле** юзера: его печатает меню «получить
ссылку», и уже розданные ключи не должны протухнуть.

## 3. Что отдаёт подписка

`regen_subscriptions` подставляет пароль слота в `hysteria2://`-ключи — во все,
включая ключи ДРУГИХ нод из их манифестов. Формат обмена между нодами при этом
не менялся: пиры считают тот же пароль из тех же данных.

Подменяем пароль только в **своих доп. токенах**. Основной токен и токены,
выданные другими нодами, отдают базовый пароль как раньше: чужой токен у нас
доп., а у выдавшей ноды — основной, и подставь мы туда свой пароль слота,
устройство пришло бы к ней с кредом, которого она для этого токена не ждёт.
Слот живёт на ноде, которая его выдала.

Доп. протоколы (VLESS/Trojan/SS/TUIC) слотов **не получают** — во всех ссылках
у них общие креды. Причина не в лени: их движки всё равно не умеют отказать на
занятом слоте ([DEVICE-LIMITS.md](DEVICE-LIMITS.md) §5), а пер-слотовые креды
размножили бы юзеров в конфигах Xray и сломали бы учёт трафика, который ведётся
по имени юзера.

## 4. Как это принимает аутентификация

`slotpass.db` — строки `user|пароль|токен`, пересобирается в
`write_slotpass_db` там же, где пишутся подписки, и при создании новой ссылки.
Права как у `users.db` (читает процесс Hysteria).

В справочник идут **все токены кластера, включая свой основной**: в подписке
слота лежат ключи всех нод, и принимать пароль обязана каждая из них.

`hysteria-auth.sh` сверяется со справочником **только если базовый пароль не
подошёл** — на обычном подключении лишней работы нет. Наружу скрипт
печатает **id слота** — `<юзер>.<8 hex>` (`sub_token_slotid`). Именно по этому id
движок ведёт сессии и трафик, и только так два устройства за одним адресом
различимы. Базовый пароль остаётся под именем юзера, поэтому накопленный трафик
и история не рвутся.

Наружу слотов нет: `/online` и `/traffic` сворачиваются обратно в юзера
(суффикс срезается регуляркой `\.[0-9a-f]{8}$` — имена юзеров точек не
содержат), а кик развёрнут в обратную сторону — `hy_kick_user` бьёт по имени и
по всем id слотов сразу, иначе доп. ссылки пережили бы отключение юзера.

Проверено живым клиентом на боевой ноде: подключение с паролем слота прошло,
трафик пошёл, в журнале `id: "<юзер>"` — учёт не тронут.

## 5. Отказ на занятом слоте

Включается на ноде: `SLOT_REJECT=1` в `node.conf`. **По умолчанию выключено** —
это единственное место, где менеджер отказывает в подключении.

Скрипт спрашивает у движка живые сессии **своего id** и отказывает, если их уже
`SLOT_MAX_SESSIONS` (по умолчанию 1). Минутный снимок тут не годится: своё же
переподключение упиралось бы в собственную устаревшую запись. API молчит —
пускаем (fail-open), аутентификация не должна падать из-за него.

Занявшего слот **не трогаем**. Кик отсюда пробовали — он не срабатывает вовсе
(движок занят нашим же вызовом auth), и это оказалось к лучшему, измерено на
изолированном инстансе:

* занявший продолжает работать, отказ получает только пришедший вторым;
* «проверка пинга» в клиенте, которая дёргает подключение при живом туннеле, не
  рвёт этот туннель — просто не проходит.

**Цена**: после обрыва без закрытия сессии слот держится ещё ~20–30 с (таймаут
QUIC), и всё это время своё же устройство переподключиться не может. Замерено:
сессия числилась живой ~25 с, дальше вход открывался сам. Если это мешает —
`SLOT_MAX_SESSIONS=2`.

`slotmap.dat` (`user|слот|ip|ts`) auth-скрипт дописывает для диагностики: по нему
видно, какое устройство на какой ссылке сидело. Чистит `slotmap_trim` (6 часов).

## 6. Что ловится, а что нет

Проверено на изолированном инстансе, два клиента с **одного адреса** (127.0.0.1)
по одной ссылке: первый работает, второй получает `authentication error`, в API
видно `{"t1":1,"t1.fd2909f1":1}` — сессии слота и базового пароля раздельно.

* ✅ одна ссылка на телефоне и на ноутбуке **в одной квартире** — второй не
  войдёт. Ради этого всё и делалось;
* ✅ ссылка, отданная другому человеку в другую сеть, — то же самое;
* ❌ **разные ссылки** работают независимо: юзеру с тремя ссылками никто не
  мешает раздать их трём людям. Число ссылок ограничено числом оплаченных
  устройств (`sub_links_allowed`), и это единственное, что удерживает лимит;
  лимит проверяется не только при выдаче: упал — лишние ссылки снимаются
  (`sub_links_prune`, см. §6.1);
* ❌ доп. протоколы (Xray/TUIC) слотов не знают вовсе — там креды общие;
* ⚠️ ссылка, выданная другой нодой, своего слота не даёт (§3).

Честная формулировка для продажи: **одна ссылка = одно устройство
одновременно**, а сколько ссылок выдано — столько устройств и оплачено.

## 6.1. Ссылка живёт ровно столько, сколько оплачена

Выданная ссылка сама по себе бессрочна: проверка лимита стоит в `sub_link_add`,
то есть в момент выдачи, а дальше ссылку никто не перепроверяет. Пока лимит не
резал токены, устройство, **проданное обратно** (лимит опустили) или снятое
руками, продолжало работать по уже розданной ссылке столько, сколько человек её
хранит — бесплатно и незаметно ([P-100](../issues/LIMITS.md#p-100)).

Поэтому каждое изменение лимита проходит через `sub_links_prune` — он вызывается
из `set_user_limits`, единственного места записи лимита, и потому действует
одинаково на TUI, бота, Web API и синхронизацию кластера:

- лишние ссылки снимаются с **самой новой**: старые розданы раньше и, скорее
  всего, лежат на живых устройствах;
- **основная** не снимается никогда — иначе человек остаётся без подписки;
- **чужие** токены (их выдала другая нода) не наши: их подрежет она сама, когда
  до неё дойдёт новая запись лимита (запись кластерная, LWW-по-`ts`);
- вместе со ссылкой сразу переписывается `slotpass.db`: файл подписки уже
  удалён, но у устройства ключ давно сохранён локально, и пускает его именно
  этот справочник — ждать общего `sub_refresh` значит подарить ещё минуту
  доступа.

Считается занятое, а не выданное: `sub_links_used` = свои токены + **доп.**
токены пиров. Основной токен пира — копия той же подписки, а не устройство
([P-101](../issues/LIMITS.md#p-101)).

## 7. Чего пока нет

- **Ссылка, выданная другой нодой, своего слота не даёт** (см. §3): у той ноды
  этот токен основной, и она ждёт по нему базовый пароль.
- **Пер-слотового учёта наружу нет**: сколько потратила каждая ссылка, в API не
  видно — id сворачивается в юзера. Данные для этого уже есть, если понадобится.
- **Базовый пароль** остаётся валидным всегда и работает как отдельный слот:
  отобрать его нельзя, не сломав меню «получить ссылку». Отсюда же
  [P-101](../issues/LIMITS.md#p-101): в кластере из N нод у юзера N основных
  токенов на базовом пароле, и это N ссылок, лимиту не подчиняющихся.
- **Экрана устройств в мини-аппе** (фаза C): ссылки создаются в TUI/через API.

## 8. Файлы

| Файл | Что делает |
|---|---|
| `lib/sub_links.sh` | `sub_token_password`, `write_slotpass_db`, подстановка пароля в `regen_subscriptions`; счёт занятых ссылок (`sub_links_used`) и подрезка лишних (`sub_links_prune`) |

| `lib/users.sh` | `secure_auth_files` — права на `slotpass.db` |
| `lib/config.sh` | пути `SLOTPASS_DB`, `SLOTMAP_FILE` |
| `tests/test-slots.sh` | разные пароли по ссылкам, приём в auth, содержимое подписки, чужой токен, отказ на занятом слоте и рубильник, подрезка ссылок при упавшем лимите |
