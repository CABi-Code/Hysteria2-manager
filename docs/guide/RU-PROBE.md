# Проба доступности из РФ

> Закрывает вторую половину [P-147](../issues/OPS.md#p-147): блокировку ТСПУ
> видно только изнутри российских сетей, а проба соседей
> ([PEER-HEALTH](PEER-HEALTH.md)) идёт из-за рубежа.

## Замысел

Отдельный сервер в российской сети, на котором **нет менеджера и нет
секретов**: обычный пользователь без sudo, вход по SSH-ключу. Каждые 5 минут
одна нода кластера (та, на которой лежит ключ) заходит на него, передаёт
скрипт проверки и список целей, читает ответ и решает, есть ли инцидент.

Почему так, а не проба со своим кроном и публикацией результатов:

| Вариант | Отказ |
|---|---|
| **Нода ходит на пробу по SSH (выбрано)** | Нода лежит — тревоги всё равно некому слать; проба не хранит ничего, ей нечего украсть и нечего обновлять |
| Проба по крону, результат забирают ноды | На пробе пришлось бы держать список целей и код, обновлять их; ради этого ей нужен свой канал к кластеру |
| Проба шлёт тревоги сама | На пробу пришлось бы положить токен бота — секрет на машине, которую мы контролируем хуже всего |

## Что проверяется

На каждую ноду кластера (список и порты — из `cluster_protocols`, то есть
живые данные кластера, ничего не прописано руками):

| Цель | Как | Что ловит |
|---|---|---|
| адрес ноды | `ping` ×3 | блокировка подсети/адреса целиком |
| сайт ноды :443 | HTTPS GET файла 64 КБ | замирание после ~16 КБ (так ТСПУ режет иностранный хостинг), блокировку домена по SNI |
| VLESS, VLESS-X | тот же GET через порт протокола | dest REALITY — Caddy ноды, поэтому порт протокола отдаёт тот же сайт: проверяется ровно дорога клиента |
| Trojan | TLS-рукопожатие на порту | порт и TLS живы (большой файл здесь не отдаётся) |
| SS | TCP-соединение | порт открыт |
| Hysteria, TUIC (UDP) | снаружи — никак | salamander намеренно молчит на чужой QUIC; проверяются только второй фазой |
| подписка | GET `/sub/<токен>` служебного профиля с домена **каждой** ноды | домен, Caddy и выдача подписки из РФ |
| **все протоколы ключом** | вторая фаза: ссылки из подписки поднимаются настоящими клиентами, через каждый туннель качается 64 КБ | рабочий ли ключ для клиента целиком: рукопожатие протокола, обфускация, замирание внутри туннеля. Итог перекрывает внешнюю проверку той же цели |

Файл 64 КБ (`assets/data.bin` в корне сайта ноды) создаёт
`nodepage_pad_ensure` (`lib/caddy.sh`) на каждой ноде из `--online-sync`.
Случайные байты: ничего не говорят о ноде и не сжимаются. Пока на ноде старая
версия менеджера, файла нет, и проба засчитывает только рукопожатие (`okt`) —
это «жив», но замирание на такой ноде не видно.

### Служебный профиль

Профиль `ruprobe` — обычный клиент кластера (без срока, 2 устройства), его
в `ruprobe.conf` записано только его имя (`RUPROBE_USER=`), токен подписки
берётся живым (`sub_tokens_all`) и уходит на пробу каждый такт через stdin SSH (не аргументом — аргументы видны в `ps`).
Клиенты на пробе — копии ядер ноды (`xray` для VLESS/Trojan, `sing-box` для
Hysteria/TUIC) в `~/bin`; конфиг собирается из подписки во временном каталоге
(700) и стирается в конце такта. Нет ядер — вторая фаза пропускается, остаётся
внешняя проверка. VLESS идёт через Xray, а не sing-box: у sing-box своя
несовместимость с REALITY ([P-178](../issues/PROTOCOLS.md#p-178)), проба
показывала бы её, а не блокировку.

Новый профиль TUIC подхватывает отложенным перезапуском (до 10 мин, см.
`proto_tuic_apply`) — сразу после заведения туннель TUIC может не подниматься.

Профиль тратит трафик (≈1 МБ за такт на весь кластер, ≈300 МБ в сутки) и
виден в статистике клиентов как обычный — это его цена.

Контроль: `ya.ru` (российский сайт) и `google.com`. Российский не открылся —
**проба слепа**: вердикты по нодам не меняются, о нодах ничего не известно.

## Лестница и сообщение

- Одиночный провал — шум, не сообщается. Тревога — со **второго подряд**
  провального такта (≈10 мин), `RUPROBE_FAILS`.
- Проба слепа три такта подряд (`RUPROBE_BLIND`) — строка «проба не на связи».
- **Одно живое сообщение на эпизод.** Эпизод начинается первой подтверждённой
  бедой и заканчивается, когда бед не осталось. Ключ сообщения — время начала
  эпизода: каждый такт сообщение **правится**, новое приходит только с новым
  эпизодом.
- Не видны адреса всех нод — одна строка «недоступен весь кластер», это и есть
  сценарий P-147 (блокировка хостера целиком).
- Закрытие: то же сообщение превращается в «✅ снова всё доступно, было с … по …:
  что лежало». Итог печатается ещё `RUPROBE_TAIL_SEC` (15 мин) — если доставка
  одного такта сорвалась, следующий её догонит.

```
‼️ Из РФ недоступно
Нода-2 · VLESS — обрыв после 16 КБ — так режет ТСПУ · с 14:32
проверено 14:47 из российской сети
```

## Доставка

`--ruprobe` печатает в stdout первой строкой ключ (`ruprobe:<ts>`), дальше —
HTML. Пусто — сказать нечего. Как и у [суточного отчёта](DAILY-REPORT.md),
менеджер не знает, куда это отправить: оператор вешает крон с пайпом в команду,
которая **правит сообщение по ключу**, а не шлёт новое. Чтобы не запускать
доставку каждые 5 минут впустую — пайп только при непустом выводе:

```
*/5 * * * * o=$(/path/hy2-manager.sh --ruprobe 2>/dev/null) && [ -n "$o" ] && echo "$o" | <команда доставки>
```

В строке крона нельзя `%` — cron считает его переводом строки и обрезает команду
(поэтому `echo`, а не `printf '%s\n'`).

## Настройка

1. На сервере пробы: пользователь без sudo, `curl nc ping`, ключ в
   `authorized_keys` с `from="<адрес ноды>"`. Пакеты ставит владелец сервера.
2. На ноде: хост в `~/.ssh/config` root, первый вход руками (ключ хоста
   ложится в `known_hosts`, дальше `StrictHostKeyChecking=yes`).
3. `echo RUPROBE_SSH=<хост> > $DATA_DIR/ruprobe.conf`. Нет файла — `--ruprobe`
   молчит. Проба нужна на одной ноде кластера, не на каждой.

## Данные

| Файл | Формат | Срок |
|---|---|---|
| `ruprobe.conf` | `RUPROBE_SSH=<хост>`, `RUPROBE_USER=<служебный профиль>` | постоянно |
| `ruprobe_state.dat` | `нода/proto\|провалов_подряд\|с_ts\|итог:байт`; строка `_blind` | только текущие беды |
| `ruprobe_episode` | `since\|closed_ts\|цели_за_эпизод` | до следующего эпизода |
| `ruprobe.log` | `ts\|нода/proto\|итог\|мс\|байт` | 8 суток (база для будущей статистики) |

Данных о клиентах нет ни в одном файле.

## Безопасность

**Что трогает:** голос сервиса (сообщения админам), ресурсы (один SSH-заход
раз в 5 минут), доступ ноды к чужому серверу.

| Угроза | Ответ |
|---|---|
| Проба скомпрометирована и врёт | Худшее — ложная тревога или ложное «всё хорошо» в админском чате. Клиентов и кластер ответ пробы не трогает: он ничего не меняет, кроме этого сообщения |
| Проба вставляет разметку или команды в ответ | Ответ — строки по белому списку (`host\|proto\|port\|итог\|мс\|байт`, итог из шести слов, числа ограничены по длине), остальное выбрасывается; в сообщение попадают только наши подписи и числа, имена нод экранируются; ответ обрезан по 64 КБ |
| Проба атакует ноду через SSH-клиент | Запрещены проброс агента, X11 и портов, TTY не выделяется; ключ хоста пробы закреплён (`StrictHostKeyChecking=yes`); общий таймаут 90 с |
| Утечка секретов на пробу | Секрета кластера и имён нод проба не получает. Получает токен подписки **одного служебного профиля** — это ровно один доступ клиента: потолок убытка — один профиль с лимитом 2 устройства, отзыв — `reset-subscription` или удаление профиля. Сознательно принято: без ключа не проверить Hysteria и сам протокол |
| Утечка ключа ноды | В `authorized_keys` пробы ключ привязан к адресу ноды (`from=`); на пробе у пользователя нет sudo |
| Файл 64 КБ как усилитель нагрузки | Отдаётся тем же Caddy, что и страница в 1 КБ; потолок — канал ноды, как у любого публичного файла. Принято |
| Спам админу | Одно живое сообщение на эпизод, правки вместо новых |

## Потолки и что дальше

- **SS не проверяется ключом** — в кластере выключен; включат — ветка в
  разборе ссылок второй фазы.
- **Ядра на пробе обновляются руками** (копия с ноды через `scp`). Разъедутся
  версии с нодами — проба может показать несовместимость, а не блокировку.
- **Одна точка, и она — хостинг.** Домашние и мобильные сети ТСПУ режет иначе;
  вторая проба — второй хост в `ruprobe.conf` (сейчас поддерживается один).
- **Тревога только у той ноды, где ключ.** Нода лежит — проба молчит; это
  видят соседи через [PEER-HEALTH](PEER-HEALTH.md).
