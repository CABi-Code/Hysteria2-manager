# 02. Архитектура: роуминг на подписях

## Расщепление роли

Сегодняшняя «нода» — это одновременно продавец, база юзеров и точка выхода. Всё
дальнейшее следует из того, что мы разрезаем её на две сущности с **разными
ключами и разными правами**.

**Издатель (issuer).** Ed25519-ключ. Продал подписку юзеру, владеет отношениями
с ним: биллинг, бан, квота, тариф, поддержка. Держит `users.db`. Минтит ваучеры.
Открывает каналы к операторам и платит им.

**Оператор (operator).** Ed25519-ключ. Держит сервер с Hysteria. Про юзеров не
знает ничего: ни имён, ни квот, ни того, сколько их. Знает только, что предъявлен
валидный ваучер, обеспеченный деньгами. Публикует анонс: хост, локация, цена за
ТБ, доступные тарифы скорости.

Один человек может быть и тем и другим одновременно — но это две сущности с
двумя ключами. Это не бюрократия: именно разделение ключей делает невозможным
«нода управляет чужими юзерами».

## Ваучер

Вместо пароля юзер получает подписанную capability:

```
payload = {
  v:     1,
  sub:   "u_9f3a2c",            # непрозрачный id, ничего не значит для оператора
  iss:   "ed25519:7f3a...",     # публичный ключ издателя
  aud:   "ed25519:c41b...",     # ПУБЛИЧНЫЙ КЛЮЧ КОНКРЕТНОЙ НОДЫ
  exp:   1752624000,
  tier:  200                    # тариф скорости, Мбит/с
}
voucher = b64url(payload) || "." || b64url(ed25519_sign(issuer_sk, payload))
```

Оператор при коннекте проверяет ровно четыре вещи:

1. подпись валидна ключом `iss`;
2. `aud` — это я;
3. `exp` не истёк;
4. у канала с `iss` есть непотраченный оплаченный остаток (см. 03).

Никакого общего состояния. Никакой синхронизации. Никакой базы юзеров на
транзитной ноде.

**Зачем `aud`.** Ваучер привязан к конкретной ноде. Даже если оператор A сольёт
ваучеры своих гостей — предъявить их оператору B нельзя. Без `aud` любой оператор
становится источником рабочих ключей ко всей сети.

**Что `sub` не значит.** Для оператора это просто строка для группировки сессий и
применения `tier`. Он не может по ней ничего узнать о юзере — и в этом смысл.

## Совместимость со стоковыми клиентами

Ed25519-подпись — 64 байта, payload ~60 байт, весь ваучер в base64url выходит
~200 символов. В поле пароля `hysteria2://` URL влезает спокойно.

Это значит, что **NekoBox, v2rayN и sing-box работают без единой правки**. Они
видят обычную подписку с длинными паролями и ничего не знают ни про какую
децентрализацию. Это, вероятно, главный практический аргумент за всю схему: ты
получаешь trustless-федерацию, не строя свою клиентскую экосистему.

Цена этой совместимости платится в `04-attacks.md`, A-04: у издателя нет
клиентской телеметрии, и он не может независимо мерить трафик. Компромисс
осознанный.

## Подписка переворачивается

Сейчас: нода агрегирует ключи со всех пиров → значит должна знать чужих юзеров.

Становится: подписку генерит **издатель**. Для каждой ноды, с которой у него
открыт канал, он минтит свой ваучер и собирает список:

```
hysteria2://<voucher_for_A>@node-a.example:443/?sni=...#🇩🇪 Frankfurt
hysteria2://<voucher_for_B>@node-b.example:443/?sni=...#🇯🇵 Tokyo
hysteria2://<voucher_for_C>@node-c.example:443/?sni=...#🇳🇱 Amsterdam
```

Ноды в этой схеме вообще не участвуют в раздаче подписок и не знают о
существовании друг друга. Каталог локаций — это личное дело издателя, и разные
издатели могут предлагать разный набор.

**Ротация.** `exp` — это и есть окно отзыва. Клиент и так перечитывает подписку
периодически: TTL 24 часа → забаненный юзер отваливается в течение суток. Нужно
быстрее — TTL час, но тогда клиент должен рефрешить чаще, а издатель обязан быть
живым (см. A-06).

## Реестр нод: подписанный gossip, не цепь

У тебя уже есть `publish_peers_list` — плоский `peers.list` статикой. Мутируется
в то же самое, только записи подписаны:

```
{node: "ed25519:c41b...", host: "node-a.example", geo: "DE/FRA", asn: 24940,
 price_per_tb: "2.00", tiers: [100,200,500], exit_policy: ["no-smtp","no-p2p"],
 ts: 1752537600, sig: "..."}
```

Каждый может это перепубликовать, подделать не может никто — подпись. Реестр
получается тот же, что «в блокчейне», но без блокчейна: нет консенсуса, нет газа,
нет финальности. Издатель собирает анонсы, фильтрует по своим критериям и решает,
кому открывать канал.

Единственное, чего не даёт gossip и дала бы цепь, — защита от того, что тебе
показали не весь список (eclipse). Для каталога локаций это терпимо.

## Что ломается по сравнению с сегодня

* `cluster_secret` и `X-Cluster-Auth` уходят целиком.
* `users.db` на транзитной ноде исчезает как класс.
* `regen_subscriptions` переезжает на сторону издателя.
* Кросс-нодовые фичи, которые сейчас работают на общем доверии — сводная
  статистика, `subips`, антиабьюз по кластеру — либо умирают, либо
  переписываются на подписанные отчёты. Это не мелочь: ровно эти фичи и есть
  ценность текущего кластера.

## Первый шаг, независимый от всего остального

Выкинуть общий секрет и подписывать межнодовые запросы Ed25519:
`X-Cluster-Auth: <shared>` → `X-Node-Sig: <ed25519 over method|path|ts|body>`.

Даже без роуминга, ваучеров и денег это убирает «один секрет = все админы» и даёт
идентичность нод, на которую наращивается всё дальнейшее. Обратно совместимо,
делается за вечер, полезно само по себе.
