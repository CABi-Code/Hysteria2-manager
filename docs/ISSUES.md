# Нерешённые проблемы менеджера

Живой список того, что **известно и не починено**. Отдельно от `docs/` по
темам: там написано, как работает то, что работает; здесь — что не работает,
работает не до конца или работает не так, как обещает соседний документ.

## Как вести этот файл

- **Нашёл проблему — сразу строка сюда**, даже если чинить не собираешься.
  Ненаписанная проблема через месяц находится заново и стоит те же часы.
- **Починил — правь здесь же:** статус `✅`, одна строка «чем закрыто» и номер
  коммита. Запись **не удалять** — она объясняет, почему код выглядит так, а
  не иначе.
- Номер `P-NN` стабильный, не переиспользуется.
- Проверенное отличать от предполагаемого. Если проблема выведена из чтения
  кода, но не воспроизведена — так и писать.
- Проблема, у которой есть проект решения, ссылается на него, а не пересказывает.

Статусы: 🔴 ломает работу · 🟡 мешает, но живём · 🟢 мелочь · ✅ закрыто.

<a id="p-01"></a>
## P-01 🔴 TUIC рестартует при любом изменении состава юзеров

У sing-box нет управления составом юзеров: есть только `clash_api`
(`lib/protocols.sh:364`) для статистики и соединений. Состав задаётся в
конфиге, применяется рестартом. Значит **любой новый юзер рвёт TUIC-сессии
всех остальных юзеров ноды**, и так на каждой ноде кластера.

Для Xray это починено (`_proto_xray_hot_apply`, коммит `797352f`), для
Hysteria проблемы не было никогда — у неё внешний auth-скрипт. TUIC остался
единственным.

Обходного пути в рамках sing-box нет. Варианты: батчить рестарты (раз в N
минут вместо каждого юзера), заменить движок TUIC, отказаться от TUIC.
В модели ваучеров TUIC не работает вообще — [11-transition.md](11-transition.md) К-2.

<a id="p-02"></a>
## P-02 🟡 Трафик TUIC считается приближённо

`proto_collect_tuic_traffic` суммирует дельты байт соединений из
`clash_api /connections` раз в минуту: у sing-box 1.13 нет StatsService
(`v2ray_api` убрали в 1.8). Соединения, закрывшиеся между снимками, теряют
хвост. Доминирующий объём (стриминг, загрузки) ловится, короткие запросы
недосчитываются. Hysteria и VLESS/SS считаются точно.

Точный per-user учёт возможен через per-IP nftables-счётчики на порту TUIC —
см. [10-multiprotocol-limits.md](10-multiprotocol-limits.md). Подробности
ограничения — [08-multiprotocol.md](08-multiprotocol.md), «Известные ограничения».

<a id="p-03"></a>
## P-03 🔴 Нельзя снять юзера с одной ноды — только со всего кластера

`cluster_apply_roster` (`lib/cluster.sh:465`) только создаёт и никогда не
удаляет. Единственный путь удаления — `cstate_set deleted` → tombstone в
`cluster_state.dat` → `cluster_delete_local` на **всех** нодах
(`lib/cluster.sh:443`). Локального «убрать только у себя» не существует.

Наивная попытка (позвать `db_remove_user` локально) даёт бесконечный цикл:
через 5 минут `cluster_apply_roster` увидит имя в roster'е владельца и заведёт
юзера обратно, крон снова удалит, и каждая итерация меняет состав `users.db`,
то есть дёргает применение конфигов протоколов.

Это блокирует размещение профилей по нодам — разбор в
[PLACEMENT/PROBLEMS.md](PLACEMENT/PROBLEMS.md) I.2. Нужен отдельный локальный
деприжининг, который **не** пишет в `cluster_state.dat`.

<a id="p-04"></a>
## P-04 🟡 Общий секрет кластера: утечка с одной ноды = доступ ко всем

`cluster.secret` — один общий секрет на весь кластер (`cluster_secret`,
`lib/cluster.sh:12`), проверяется Caddy как строка заголовка `X-Cluster-Auth`
(`lib/caddy.sh:73-78`). Доверие бинарное: у кого секрет — тот видит юзеров,
статистику, IP и лимиты всех нод.

Внутри своего парка это терпимо (все ноды под одной рукой). Становится
блокером в момент, когда появляется чужая нода. Решение — подписывать
**содержимое** публикуемых записей, а не запросы; разбор и обоснование в
[11-transition.md](11-transition.md) К-1.

<a id="p-05"></a>
## P-05 🟡 Манифест содержит пароли юзеров

`publish_manifest` (`lib/sub_links.sh:240`) публикует строки `user<TAB>uri`,
где `uri` — готовая ссылка подключения **с паролем юзера на этой ноде**. То
есть каждая нода кластера знает учётные данные каждого юзера на каждой другой.

Внутри своего контура это осознанная плата за единую подписку без общей базы.
Наружу такой манифест уходить не должен никогда: чужому оператору полагается
ваучер с непрозрачным `sub`, а не строка манифеста. См.
[11-transition.md](11-transition.md) К-3 и Н-3.

<a id="p-06"></a>
## P-06 🟡 Нет паспорта ноды

`publish_peers_list` (`lib/cluster.sh:54`) публикует только `name|host`.
Ёмкость, метка локации, набор протоколов, версия — либо не публикуются вовсе,
либо разбросаны по секциям. Ни один из 17 `publish_*` не отдаёт факты ноды
о себе одним куском.

Из-за этого нода, принимающая решение (например о размещении профиля), не
знает свойств соседей. Класть такие поля в `SETTING_KEYS` нельзя — они
синхронизируются LWW, то есть любая нода перезапишет чужое утверждение о себе.
Нужен single-writer `nodeinfo` — [PLACEMENT/README.md](PLACEMENT/README.md) §3.1.

<a id="p-07"></a>
## P-07 🔴 Детект шаринга имеет потолок и умирает молча

`cluster_active_node_count` (`lib/antiabuse.sh:52`) считает, на скольких нодах
юзер сейчас гонит трафик, `abuse_observe` (`:65`) сравнивает с `pool_cap`
(эффективный лимит устройств). Юзер физически не может быть активен на большем
числе нод, чем ему выдано.

Значит при числе нод профиля меньше `pool_cap` условие `cn > cap` недостижимо
в принципе, и **детект перестаёт срабатывать без ошибок, без логов и без
единого следа**. Сегодня не проявляется (юзер на всех нодах), но сработает в
момент включения размещения профилей.

Правило: `NODES_PER_PROFILE ≥ pool_cap`. Либо перенести сигнал с `cn` (число
нод) на `conn` (`cluster_user_connections`, `lib/publish.sh:129`) — у числа
соединений потолка нет. Разбор — [PLACEMENT/PROBLEMS.md](PLACEMENT/PROBLEMS.md) #11.

<a id="p-08"></a>
## P-08 🟡 Все юзеры на всех нодах

Провижининг через API/бота/мини-апп делает профиль кластерным, и он заводится
на каждой ноде. Следствия: рост упирается в самую слабую ноду вместо «добавить
ещё одну»; понятия ёмкости ноды нет; сигнала «места не осталось, пора покупать
VPS» нет — деградация происходит тихо.

Спроектировано, кода нет: [PLACEMENT/](PLACEMENT/README.md). Реализация
упирается в P-03.

<a id="p-09"></a>
## P-09 🟡 Роль издателя расщеплена между менеджером и webapp

Данные об отношениях с юзером лежат в двух местах: `надстройка` (баланс,
пополнения, рефералка, покупка тарифов, привязка к Telegram) и менеджер
(`tariffs.conf`, `expiry`, free-план, `tgbind`, лимиты юзера, продажа тарифов
ботом через `lib/yoomoney.sh`). Один тариф описан дважды, срок хранится внизу,
деньги за него — наверху.

Пока роль расщеплена, её нельзя расщепить ещё раз на издателя и оператора, то
есть внешний контур недостижим. Это не баг, а нерешённое архитектурное
решение — [11-transition.md](11-transition.md) К-6. Дорожает с каждой фичей,
которая ложится не на ту сторону.

<a id="p-10"></a>
## P-10 🟢 tc-классы привязаны к имени юзера из `users.db`

Ограничение скорости (tc HTB + fq_codel, `lib/perf.sh`,
[10-multiprotocol-limits.md](10-multiprotocol-limits.md)) заводит классы под
конкретного юзера по имени, заранее, пачкой при синхронизации.

Для чужого юзера на моей ноде привязывать не к чему: у него только непрозрачный
`sub`, появляющийся в момент коннекта. Нужен путь «класс заводится на лету по
`sub`, живёт до `exp`, убирается сборкой мусора». Внутреннего контура не
касается — [11-transition.md](11-transition.md) К-7.

<a id="p-11"></a>
## P-11 🟡 Длина ваучера в стоковых клиентах не проверена

Вся схема из [02-architecture.md](02-architecture.md) держится на том, что
~200-символьный ваучер влезает в поле пароля `hysteria2://` и стоковые клиенты
(NekoBox, v2rayN, sing-box, Streisand) его переваривают. Это **предположение,
не факт** — никто не проверял.

Проверка стоит час ручной работы и либо подтверждает, либо отменяет весь план
маркета. `06-roadmap.md` ставит её внутрь Этапа 1, то есть после того, как под
неё уже что-то построено. Делать надо до.

<a id="p-12"></a>
## P-12 🟢 Возможный двойной счёт скорости на релейном трафике

`user_rate_bps` суммирует скорость по пирам. На релейной цепочке один и тот же
трафик может попасть в сумму дважды. Остаточный риск, оставшийся после починки
завышения спидометра (идея 17 мини-аппа, менеджер v4.7.3–4.7.4): корневая
причина там была другая (снимок открытых TUIC-соединений вместо накопительного
счётчика) и она устранена.

Не воспроизведено. Если всплески вернутся — диагностировать логированием
слагаемых суммы, а не гадать.

<a id="p-13"></a>
## P-13 🔴 Удаление профиля на одной ноде не удаляет его в кластере

`delete_user` (`lib/users.sh:121`) ставит tombstone только когда юзер **числится
кластерным**: `was_cluster` вычисляется через `is_cluster_user`, то есть по
roster'у (своему или пира). Юзер вне roster'а исчезает только локально. На пирах
он остаётся живым, его ключи продолжают приходить в манифестах, а
`regen_subscriptions` (`lib/sub_links.sh:282`) пишет ему подписку под ВСЕ токены,
включая старый токен из кэша пира — cstate пуст, значит «пустую подписку» никто
не отдаёт.

**Проверено на node-a** (27.07.2026): `admin`, `user-b`, `user-c`, `user-d`,
`user-e` отсутствуют в `users.db` и `disabled.dat`, но их файлы в
`/var/www/hy2sub/sub/` отдают рабочий набор ключей node-b (hysteria2 + vless +
trojan + tuic), потому что на node-b профили живы (по 4 строки в
`peers/node-b*.manifest`).

Это зеркало [P-03](#p-03): там нельзя снять юзера с ОДНОЙ ноды, здесь удаление с
одной ноды не снимает его НИГДЕ, и оба состояния выглядят для админа одинаково
(«я его удалил»). Пока не решён вопрос локального vs кластерного удаления,
безопасный путь один — удалять кластерных юзеров, а не «просто удалять».

<a id="p-14"></a>
## P-14 🟡 Осиротевшие токены подписки не убираются никогда

Уборка в конце `regen_subscriptions` считает токен валидным, если он есть в
`SUBTOKENS_DB` **или** в кэше `peers/*.subtokens`. Ни один код не вычищает
строку из `SUBTOKENS_DB` при исчезновении юзера мимо `delete_user`, а пир
публикует свой список токенов вечно. Итог: файл подписки не переписывается (юзера
нет в `sub_all_users`) и не удаляется (токен «валиден»).

**Проверено на node-a**: 27 локальных токенов на 13 юзеров (14 сирот, среди них
демо-профили и запись `type` — след давнего бага парсинга), 56 файлов в
`/var/www/hy2sub/sub/` против 13 действующих профилей. Часть файлов пустые, часть
— с рабочими ключами (см. [P-13](#p-13)).

Нужен GC по TTL: токен, чей юзер не встречается ни локально, ни в манифестах
пиров N суток, удаляется вместе с файлом.

<a id="p-15"></a>
## P-15 🔴 Онлайн Xray-протоколов всегда пуст

`proto_online_json` (`lib/protocols.sh:915`) спрашивает у Xray
`statsquery -pattern "online"`, но в генерируемом конфиге (`lib/protocols.sh:325`)
в `policy.levels."0"` включены только `statsUserUplink`/`statsUserDownlink`.
Счётчиков онлайна Xray не заводит вовсе.

**Проверено на node-a**: `xray api statsquery -pattern online` → `{}` при непустых
`user>>>…>>>traffic>>>…`. Значит юзер, сидящий на VLESS/Trojan/SS, **нигде не
считается онлайн**: индикатор в TUI, боте и мини-аппе, `{online}` в подписи
ключа, `cluster_user_connections`, счётчиковый кик `enforce_device_limits`.

По документации Xray лечится флагом `"statsUserOnline": true` в
`policy.levels."0"` (+ рестарт Xray) — но проверять надо на месте, метка менялась
между версиями, как это уже было с ключами REALITY.

<a id="p-16"></a>
## P-16 🔴 Кик — только у Hysteria

`api_post "/kick"` — это API Hysteria (`lib/api.sh`). Для Xray кик не написан
сознательно (комментарий `lib/protocols.sh:952`), у sing-box его нет вовсе.
Поэтому все три энфорсера — счётчиковый (`enforce_device_limits`), traffic-based
жёсткая проверка (`enforce_active_node_limit`) и авто-жёсткая проверка
анти-абуза — режут ТОЛЬКО Hysteria-сессии.

Юзер, чей клиент выбрал VLESS/Trojan/TUIC, при превышении лимита получает строку
в `limit.log` каждую минуту и ничего больше: `get_user_active` считает его
активным (трафик Xray в `collect_activity` подмешивается), решение принимается,
кик уходит в пустоту. То есть POOL_LIMIT/NODE_LIMIT, персональное число
устройств и анти-абуз держатся на протоколе, который клиент выбирает сам.

Кик Xray — это `rmu` по тегам `_proto_xray_tags` + возврат через
`_proto_xray_adu_json`, то есть три строки поверх уже написанного hot-apply.
Для TUIC пер-юзерного кика нет — только рестарт ([P-01](#p-01)).

<a id="p-17"></a>
## P-17 🟡 Трафик и онлайн TUIC читают `metadata.user`, которого может не быть

`proto_collect_tuic_traffic` (`:775`) и TUIC-ветка `proto_online_json` (`:928`)
фильтруют соединения по `.metadata.user != null and != ""`. А
`proto_tuic_activity_lines` (`:876`) в том же файле утверждает обратное:
«sing-box (clash_api) НЕ отдаёт user в метадате соединения (проверено
эмпирически)» — и потому резолвит юзера по `sourceIP` через `ips.dat`.

Оба утверждения одновременно верными быть не могут. Если верно второе, то TUIC
не считается **вообще** (а не «приближённо», как обещает [P-02](#p-02)) и не даёт
онлайна — молча, без ошибок, ровно как в [P-07](#p-07).

Не воспроизведено: на node-a в момент проверки было 0 TUIC-соединений. Проверка —

<a id="p-18"></a>
## P-18 🟡 IP-трекинг только по журналу Hysteria

`collect_ips` (`lib/ip_tracking.sh:43`) парсит `journalctl -u
hysteria-server.service`. Клиент, который ходит по VLESS/Trojan/TUIC, в
`ips.dat` не попадает никогда. `authmap.dat` — тоже чисто Hysteria: его пишет
auth-скрипт на каждое подключение.

Следствия по цепочке:
- карточка юзера показывает только Hysteria-IP (для VLESS-клиента — пусто);
- `klimit_reconcile` (`lib/perf.sh`) берёт связку user→IP из `authmap.dat` +
  `ips.dat`, то есть **персональный тариф скорости не применяется к клиенту,
  который не подключался по Hysteria**: его IP нет ни в одном источнике, пер-IP
  фильтра нет, трафик уезжает в catch-all → глобальный класс (а при `DOWN_MBIT=0`
  — вообще без потолка);
- `proto_tuic_activity_lines` резолвит TUIC-соединение по `ips.dat` и на
  «чистом» TUIC-клиенте не резолвит ничего.

<a id="p-19"></a>
## P-19 🟡 Покупка тарифа обнуляет персональный тариф скорости

`lib/tgbot_client.sh:342`:
`set_user_limits "$user" "$devices" "$(get_user_hardcheck "$user")"` — пятый
аргумент (rate) не передан, а `set_user_limits` (`lib/limits.sh:58`) при пустом
rate пишет `rate=0`. То есть любое продление/покупка через бота и мини-апп
стирает назначенную юзеру скорость, и стирание уезжает по кластеру (ts=now,
LWW).

Правильно — как в обёртках `set_user_devices`/`set_user_hardcheck`: передавать
`"$(get_user_rate "$user")"`. Тот же паттерн проверить в `lib/tgbot_daemon.sh:240`
(там юзер новый, поэтому сейчас безвредно, но третьим аргументом жёстко забит 0 —
жёсткая проверка тоже обнулится, если код переиспользуют).

<a id="p-20"></a>
## P-20 🟡 Двойное зачисление ЮMoney

`ym_settle` (`lib/yoomoney.sh`) защищается от повторной выдачи проверкой
`grep "|ym:${op}$" "$PAYMENTS_LOG"`, но саму строку в журнал пишет
`bot_fulfill_payment` в самом конце (`lib/tgbot_client.sh:349`) — уже ПОСЛЕ
`bot_provision_user`, а он идёт около 18 секунд (внутри — рестарт протоколов).
Всё это окно проверка идемпотентности отвечает «не выдавали».

Попасть в окно легко: `--ym-poll` крутится по крону раз в минуту **без flock**
(единственная блокировка мутаций — `dispatch.sh`, а бот и крон её не берут), а
тот же путь запускает кнопка «Проверить оплату». Итог — два продления за один
платёж.

Лечится либо flock вокруг `ym_poll`, либо резервированием `ym:<op>` в журнале ДО
фулфилмента.

<a id="p-21"></a>
## P-21 🟡 `stats.dat` правится read-modify-write без блокировки

`collect_traffic` (`lib/traffic.sh:40`), `proto_collect_traffic`
(`lib/protocols.sh:755`) и `proto_collect_tuic_traffic` (`:810`) обновляют
`stats.dat` одинаково: `grep` старого значения + `sed -i` по всему файлу. Между
чтением и записью файл может переписать другой процесс — тогда его дельта
теряется целиком.

Это не гипотетика: `--collect` стоит в кроне на `*/30`, `--online-sync` — на
`* * * * *`, значит на минутах :00 и :30 они стартуют одновременно **каждый
час**. Плюс TUI зовёт `collect_traffic` на старте и при входе в список юзеров.
`flock` в менеджере есть только у `--rates-tick` и у мутаций `webapi/dispatch.sh`.

<a id="p-22"></a>
## P-22 🟡 Кластерная сумма трафика немонотонна, а free-план строит на ней разницу

`freeplan_tick` считает расход как `bytes - wkb`, где `bytes` —
`freeplan_user_bytes` = локальный `stats.dat` + сумма по `peers/*.stats`. Эта
сумма умеет **уменьшаться**:

- `publish_stats` (`lib/publish.sh:16`) идёт по `users.db`, поэтому отключённый
  юзер (в том числе отключённый самим free-планом) пропадает из статистики своей
  ноды целиком;
- `cluster_online_sync` (`lib/cluster.sh:805`) при недоступном пире записывает
  **пустой** файл `peers/<name>.stats` — сознательно, «чтобы не залипать на
  старом».

В обоих случаях `bytes` падает ниже базы `wkb`, `wk_used` обрезается в 0, и
`freeplan_tick` считает, что квота свободна: заблокированного юзера впускают
обратно с уведомлением «квота сброшена», а нода, у которой байты на месте,
блокирует его снова — с уведомлением о блокировке. LWW по ts делает это
устойчивым пинг-понгом: сетевой чих пира = пара уведомлений юзеру.

Не воспроизведено, выведено из чтения. Правильное лечение — считать расход по
монотонному кумулятиву (публиковать его в `publish_stats` и хранить базу по
нодам), а не по разнице агрегата, который может исчезнуть.

<a id="p-23"></a>
## P-23 🟢 `abuse.dat` растёт вечно

`abuse_correct` (`lib/antiabuse.sh:117`) пересобирает файл из объединения
`ABUSE_FILE ∪ ABUSE_OBS_FILE`, то есть строка юзера переносится в новый файл
вечно, даже когда профиля давно нет. `abuse_apply` дополнительно тянет её обратно
с пиров. Единственная уборка — `sed` в `delete_user`, но демо-профили удаляет
`cluster_delete_local`, который анти-абуз не трогает (и `remove_user_abuse`
никто не зовёт).

**Проверено на node-a**: 42 строки на 13 юзеров, из них 22 — `demo-*`.

<a id="p-24"></a>
## P-24 🟢 Хвосты удалённого профиля достаются одноимённому новому

`delete_user` чистит 12 файлов, но не `freeplan.dat`, `expiry_ts.dat`,
`cluster_pwreset.dat`, `rates.dat`, `subips.dat`. `cluster_delete_local`
(`lib/cluster.sh:391`) чистит ещё меньше — без `activity*`, `abuse*`, `freeplan`.

**Проверено на node-a**: `expiry_ts.dat` — 18 строк на 13 юзеров, `userlimits.dat`
содержит три давно удалённых `demo-*`, `cluster_state.dat` — записи `type`,

Профиль, заведённый под тем же именем (а имена вида `tg<ID>` выдаёт бот
детерминированно!), наследует: строку free-плана в состоянии `blocked`, старые
метки времени срока и лимитов. Последнее опасно в LWW: чужой ts с пира может
оказаться больше свежей локальной правки. Не воспроизведено.
