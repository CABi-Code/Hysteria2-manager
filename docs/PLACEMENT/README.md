## 1. Зачем

Сегодня **каждый кластерный юзер заводится на каждой ноде**. Пока нод три —
терпимо. Проблема не в дисковом месте, а в трёх вещах:

1. **Новый юзер рвёт чужие сессии.** `db_add_user` (`lib/users.sh:69`) — это
   дописывание строки в `users.db`, оно бесплатно. Дорого то, что за ним идёт:
   `sub_refresh` (`lib/sub_links.sh:402`) зовёт `proto_sync_users`
   (`lib/protocols.sh:454`), тот пересобирает конфиги Xray и sing-box из
   `users.db` и через `_proto_apply_service` (`lib/protocols.sh:441`)
   рестартует сервис, если хэш конфига изменился. Состав юзеров изменился —
   значит рестарт. **Один новый юзер = обрыв VLESS/SS/TUIC-сессий всех
   остальных юзеров на этой ноде.** И так на каждой ноде кластера.
   Hysteria не страдает — у неё внешний auth-скрипт, состав юзеров читается
   на лету.
2. **Рост упирается в самую слабую ноду.** Расти = апгрейдить каждую ноду,
   а не добавлять новую, потому что нагрузка размазана по всем поровну.
3. **Клиент всё равно сидит на одной ноде.** При десятке нод отдавать все
   десять каждому — это раздутая подписка и лишние ключи, из которых
   используется один.

Ёмкость даёт четвёртое, ради чего всё и затевается: **сигнал «пора покупать
VPS»** вместо тихой деградации.

## 2. Как устроено сегодня (проверено по коду)

Схема pull, никакого центра:

1. Провижининг через API/бота/мини-апп зовёт `cluster_share_user`
   (`lib/cluster.sh:490`): `roster_add` + `cstate_set active` + публикация.
2. `CLUSTER_USERS_FILE` — **плоский список имён, по имени в строке, без
   полей и без ts** (`roster_add`, `lib/cluster.sh:265`). Публикуется как есть
   (`publish_roster`, `lib/cluster.sh:457`).
3. Пиры на своём `cluster_sync` (крон каждые 5 мин, `lib/cron.sh:38`)
   забирают чужие roster'ы в `$PEERS_DIR/*.roster` и зовут
   `cluster_apply_roster` (`lib/cluster.sh:465`) — она заводит юзера локально
   со **своим** случайным паролем.
4. Каждая нода публикует манифест `user<TAB>uri` (`publish_manifest`,
   `lib/sub_links.sh:240`).
5. `regen_subscriptions` (`lib/sub_links.sh:282`) собирает подписку: свой ключ
   + `cat "$PEERS_DIR"/*.manifest`, дедуп по `host:port`.

Три инварианта отсюда, на которых стоит вся схема размещения:

- **Владелец профиля уже существует.** Комментарий `lib/cluster.sh:262-264`:
  авто-заведённые юзеры в свой roster **не** добавляются, источник истины
  один — нода, через которую профиль создали. Отдельную сущность «owner»
  изобретать не нужно, она уже есть: владелец = нода, в чьём
  `CLUSTER_USERS_FILE` лежит имя.
- **`cluster_apply_roster` только создаёт, никогда не удаляет.** Удаление
  живёт отдельно: `cstate_set deleted` → tombstone в `cluster_state.dat` →
  `cluster_delete_local` на всех нодах (`lib/cluster.sh:443`). Способа «убрать
  юзера с одной ноды, не убив его в кластере» **сегодня не существует**.
- **Подписка не требует локального аккаунта.** `sub_all_users`
  (`lib/sub_links.sh:275`) — это `users.db` ∪ имена из манифестов пиров.
  Для юзера без локального пароля `regen_subscriptions` просто не добавляет
  свой ключ (`[ -n "$lp" ] &&`), но ключи пиров подмешивает и файл подписки
  пишет. **Раздача подписки и хостинг аккаунта — независимые вещи.**

Последний пункт — самый полезный: он позволяет включить размещение сначала
только на уровне подписки, вообще не трогая провижининг.

## 3. Целевая схема

### 3.1 Данные

| Что | Где | Кто пишет | Синк |
|---|---|---|---|
| `NODE_CAPACITY` | `node.conf` | только сама нода | публикуется в `nodeinfo` |
| `NODE_LEASE_CAPACITY` | `node.conf` | только сама нода | публикуется в `nodeinfo` |
| `NODES_PER_PROFILE` | `SETTING_KEYS` (`lib/node.sh:138`) | любая нода | LWW, механизм готов |
| `placement.dat` | `$DATA_DIR` | нода-владелец профиля | новая секция `placement` |
| `nodeinfo` | `$WEBROOT/cluster/nodeinfo` | только сама нода | забирается как секция |

**`placement.dat`** — формат `user|node1,node2,node3|ts`. Новая секция в
`CLUSTER_SYNC_SECTIONS` (`lib/cluster.sh:122`, сейчас 13 секций — добавление
четырнадцатой это отработанный паттерн), LWW по `ts`.

**`nodeinfo`** — паспорт ноды, `key=value` по строке:

```
name=node-a
label=Finland
capacity=21
proto=hysteria2,vless,ss2022,tuic
ts=1785000000
```

Почему отдельный файл, а не кластерная настройка: `SETTING_KEYS` синхронизируются
LWW, то есть **любая нода может перезаписать значение любой другой**. Ёмкость —
утверждение ноды о самой себе, у него должен быть один-единственный автор.
Ни один существующий `publish_*` паспорт ноды не публикует: `publish_peers_list`
(`lib/cluster.sh:54`) отдаёт только `name|host`. Нужен новый `publish_node_info`.

**`NODE_LEASE_CAPACITY`** — место, отданное наружу, чужим издателям
(см. [../11-transition.md](../11-transition.md), Н-4). Две квоты **не
сообщаются**: сдача не съедает место своих клиентов, свои не съедают
проданное. Пока аренды нет, это ноль и одна проверка; после первой сдачи
ввести его — уже переделка учёта. Чужие профили в `placement.dat` не попадают
никогда, поэтому без отдельной квоты нода, забитая арендаторами, для своей же
системы размещения выглядит пустой.

**Счётчик занятости публиковать не нужно.** Раз `placement.dat` синхронизирован
всем, любая нода считает загрузку любой другой локально — `grep`/`awk` по
своей же копии. Меньше сущностей, меньше рассинхрона.

### 3.2 Правило номер один: fail-open

**Отсутствующая, устаревшая или битая запись placement означает «все ноды»,
никогда «ни одной».**

Это не перестраховка, а следствие устройства синка. `roster` и `placement` —
две независимые секции, приезжают в произвольном порядке. Юзер появится в
roster'е раньше, чем его placement, — гарантированно, для каждого нового
профиля. При fail-closed это значит: человек оплатил тариф и на 5 минут
получил подписку без единого сервера. При fail-open — получил все ноды, а
через синк схлопнулся до трёх, чего он даже не заметит.

Побочная выгода: **миграция становится пустой**. Существующие профили не имеют
записи в `placement.dat`, значит ведут себя ровно как сегодня. Никакого скрипта
переноса, никакого «фича включена, но пока в режиме совместимости».

Ноды старой версии не знают секции `placement`, не забирают её и продолжают
работать как раньше — то же самое поведение. Формат `roster` при этом **не
меняется**: `cluster_apply_roster` валидирует имя регуляркой
`^[a-zA-Z0-9_-]+$` (`lib/cluster.sh:473`), и строка вида `user|nodes|ts` была бы
молча отброшена старой нодой — то есть новые юзера на ней перестали бы
заводиться вообще. Поэтому placement живёт отдельно, а не полем в roster'е.

### 3.3 Выбор нод — `pick_nodes user`

1. Кандидаты — живые ноды: `cluster_peers` + своя.
2. Отбросить переполненные: `placed >= NODE_CAPACITY` (при `NODE_CAPACITY=0`
   нода безлимитна).
3. Гарантировать географию: если есть нода с `label` ближайшей локации —
   она входит в набор обязательно (см. PROBLEMS #7).
4. Сортировать по свободным слотам ↓, тай-брейк по онлайну ↑.
5. Взять `min(NODES_PER_PROFILE, доступно)`.
6. Если набралось меньше — добрать наименее загруженные из переполненных
   (лимит мягкий) и записать событие «кластер переполнен».

Free- и demo-профили получают `NODES_PER_PROFILE = 1`. Это заменяет отдельный
счётчик бесплатных с политикой вытеснения (см. PROBLEMS #1) и заодно срезает
рестарты от самой массовой популяции втрое.

### 3.4 Точки применения

| Где | Что делает |
|---|---|
| `regen_subscriptions` (`lib/sub_links.sh:~330`) | вместо `cat "$PEERS_DIR"/*.manifest` — перечислить только манифесты нод из placement |
| `cluster_apply_roster` (`lib/cluster.sh:465`) | не заводить юзера локально, если этой ноды нет в его placement |
| провижининг (`cluster_share_user`) | посчитать placement и записать **до** публикации roster'а |
| сборка мусора (крон) | снять аккаунт с ноды, выпавшей из placement дольше суток назад |
| `publish_manifest` | без изменений — лишние строки отсекаются на приёме |

Фильтр подписки — буквально замена glob'а на список файлов: манифест это файл
на ноду, значит фильтровать по ноде = фильтровать по файлу. Рядом уже лежит
готовый пример пофайлового/поюзерного фильтра — `sub_filter_protocols`
(`lib/sub_links.sh:204`), который для demo-юзера оставляет только Hysteria.

## 4. Фазы внедрения

Порядок обязателен: Фаза 3 без Фазы 2 даёт бесконечный цикл (PROBLEMS #9).

**Фаза 0 — наблюдение.** `NODE_CAPACITY` в `node.conf`, `publish_node_info`,
секция `nodeinfo`, расчёт и показ загрузки в меню менеджера и в `GET /v1/nodes`.
Ничего не применяется. Риск нулевой, а сигнал «пора покупать VPS» появляется
сразу — это уже половина ценности фичи.

**Фаза 1 — подписка.** `placement.dat`, `pick_nodes`, фильтр манифестов в
`regen_subscriptions`. Аккаунты остаются на всех нодах, рестартов ноль,
откат — снять фильтр. Юзер начинает видеть свои N серверов вместо всех.

**Фаза 2 — провижининг.** `cluster_apply_roster` уважает placement. Действует
только на новых юзеров: экономия рестартов начинается, старые аккаунты
остаются где были.

**Фаза 3 — сборка мусора.** Снятие старых аккаунтов с нод вне placement.
Опасная: нужен **локальный** деприжининг, не пишущий tombstone в
`cluster_state.dat`, иначе профиль умрёт во всём кластере. Батчами, ночью,
не больше M профилей в сутки, чтобы размазать рестарты.

## 5. Задел под маркет локаций

Заметки `docs/01-problem.md` … `docs/07-discovery.md` описывают будущую
пересборку менеджера в открытый рынок нод. Размещение — не побочная фича, а
**недостающий примитив этой пересборки**, и его стоит закладывать под неё сразу.

| Сегодня | Завтра (маркет) |
|---|---|
| `placement.dat`: список нод профиля | набор ваучеров с `aud = pubkey ноды` (`02-architecture.md`) |
| нода-владелец профиля | **издатель** (issuer), `02-architecture.md` |
| `nodeinfo`: `capacity`, `label` | подписанный анонс ноды: `+pubkey`, `geo`, `asn`, `price_per_tb`, `tick_bytes` (`05-examples.md`) |
| `NODE_CAPACITY` | обязательство перед чужим издателем; переподписка = атака **A-07** (`04-attacks.md`) |

Главное: во внешнем контуре «юзер на всех нодах» **перестаёт существовать как
понятие** — ваучер по определению привязан к одной ноде через `aud`. Аренда
чужой ноды без размещения нереализуема: у профиля обязан быть **набор** нод, а
не «все». Внутри своего кластера размещение полезно само по себе — ради
ёмкости и ради того, чтобы новый юзер не рвал чужие сессии на всех нодах
сразу.

Поэтому размещение — это Этап 0.5: единственный из ранних шагов, который
одновременно окупается сегодня и является предусловием внешнего контура.

Размещение вдобавок **форсирует решение проблемы, которую иначе обнаружат
поздно и дорого**: детект шаринга сегодня построен на том, что ноды доверяют
друг другу и складывают статистику (`cluster_active_node_count`,
`lib/antiabuse.sh:52`). В модели маркета ноды не разговаривают друг с другом
вообще, и эта метрика собирается некому. Размещение ломает её раньше и мягче —
на своём кластере, с возможностью откатиться (PROBLEMS #11). Это та же логика,
по которой `06-roadmap.md` ставит федерацию с друзьями раньше контрактов.

`nodeinfo` задуман как single-writer, и это же делает его **прямым предком
подписанного анонса ноды**: добавить отделённую подпись `nodeinfo.sig` — и
получается зеркалируемая подписанная запись, которую требует Этап 5. Лежит он
за `X-Cluster-Auth`, то есть host не становится публичным полем каталога — это
согласуется с выводом `07-discovery.md` («хост арендуется через уже открытый
канал, а не публикуется»).

Полный разбор конфликтов целевой модели с сегодняшним кодом — в
[../11-transition.md](../11-transition.md).

**Точки невозврата** — решения, которые потом менять дорого:

1. **fail-open по умолчанию.** Единственная защита от «пустой подписки».
2. **Ёмкость объявляет сама нода** (один автор), а не кластерная настройка.
   Иначе в маркете любой участник переписывает чужие обязательства.
3. **Placement — намерение, а не факт.** Загрузка считается по `placement.dat`,
   а не по фактическому составу `users.db` на ноде. Факт отстаёт и врёт при
   рассинхроне; намерение — то, за что нода отвечает.
4. **`NODES_PER_PROFILE ≥ pool_cap`** — иначе детект шаринга физически
   перестаёт срабатывать (PROBLEMS #11).

## 7. Чего не хватает

- `NODE_CAPACITY` в `node.conf` + пункт меню, `publish_node_info`, секция `nodeinfo`.
- `placement.dat`, секция `placement`, `pick_nodes()`, пересчёт по триггерам.
- Фильтр манифестов в `regen_subscriptions`, проверка placement в
  `cluster_apply_roster`.
- Локальный деприжининг без tombstone + крон сборки мусора (Фаза 3).
- Поля `capacity`/`placed` в `GET /v1/nodes`, набор нод в `GET /v1/users/{name}`.
- Уведомление админу «свободно меньше 10%» (`lib/notify.sh`).

## 8. Триггеры пересчёта placement

- покупка тарифа (free → платный) — главный момент;
- истечение или отключение профиля — слот освобождается;
- вывод ноды из эксплуатации (ручная команда, PROBLEMS #13);
- суточный крон: добрать профилям, у которых нод меньше положенного.

Смена набора нод дешёвая: пароль и токен подписки не меняются, ключи протоколов
производны от пары `user+pass` (`proto_uuid`, `lib/protocols.sh:91`), поэтому
переезд — это другой список серверов в подписке. Клиент подхватит на следующем
обновлении (`SUB_UPDATE_HOURS`).
