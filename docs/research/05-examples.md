# 05. Примеры: форматы, псевдокод, сценарии

Всё ниже — наброски для обсуждения, не спецификация. Цифры — порядки величин.

## Ваучер

```
payload (CBOR или компактный JSON):
{
  "v":    1,
  "sub":  "u_9f3a2c",
  "iss":  "7f3a1b9c...",        # 32 байта, pubkey издателя
  "aud":  "c41b8e02...",        # 32 байта, pubkey ноды
  "exp":  1752624000,
  "tier": 200
}

voucher = b64url(payload) + "." + b64url(ed25519_sign(issuer_sk, payload))
```

Размер:
```
payload  ~ 60 B  →  b64url  ~ 80 симв.
подпись    64 B  →  b64url   ~86 симв.
итого            ~  170 симв.  → влезает в поле пароля hysteria2:// ✓
```

Как это видит стоковый клиент:

```
hysteria2://eyJ2IjoxLCJzdWIiOiJ1XzlmM2EyYyIs....Xq7Z@node-a.example:443/?sni=cdn.example#🇩🇪%20Frankfurt
             └────────────── ваучер вместо пароля ──────────────┘
```

## Анонс ноды (подписанный gossip, не цепь)

```json
{
  "v": 1,
  "node": "c41b8e02...",
  "host": "node-a.example",
  "geo": "DE/FRA",
  "asn": 24940,
  "price_per_tb": "2.00",
  "tiers": [100, 200, 500],
  "exit_policy": ["no-smtp", "no-port-25", "no-p2p"],
  "tick_bytes": 104857600,
  "chain": "base",
  "payto": "0x71C7...",
  "ts": 1752537600,
  "sig": "..."
}
```

Публикуется статикой — ровно там, где сейчас лежит `peers.list`
(`publish_peers_list` в `cluster.sh`). Кто угодно может перепубликовать, подделать
не может никто.

## Расписка

```
claim = {
  "chan":  "0x9a3f...",          # id канала (issuer, node)
  "cum":   "3.5021",             # КУМУЛЯТИВНО с открытия, USDC
  "nonce": 71
}
sig = ed25519_sign(issuer_sk, claim)
```

Кумулятив — по **всему каналу**, а не по юзеру. Это то, что делает схему
масштабируемой (03): одна подпись на тик на ноду, независимо от числа юзеров.

## Псевдокод: auth-скрипт оператора

Сейчас (`auth.type: command`, аргументы `<addr> <user:pass> <tx>`) скрипт ищет
юзера в `users.db`. Становится:

```bash
#!/bin/bash
# $1 = addr  $2 = auth-string (ваучер)  $3 = tx

voucher="$2"
payload_b64="${voucher%%.*}"
sig_b64="${voucher#*.}"

# 1. подпись
payload=$(b64url_decode "$payload_b64")
iss=$(json_get "$payload" iss)
verify_ed25519 "$iss" "$payload" "$(b64url_decode "$sig_b64")" || exit 1

# 2. это точно мне?
[ "$(json_get "$payload" aud)" = "$(cat /etc/hy2/node.pub)" ] || exit 1

# 3. не протух?
[ "$(json_get "$payload" exp)" -gt "$(date +%s)" ] || exit 1

# 4. канал этого издателя оплачен?
channel_balance_ok "$iss" || exit 1

# id для Hysteria + тариф для tc (см. speed-tariffs)
echo "${iss:0:8}_$(json_get "$payload" sub)"
exit 0
```

Обрати внимание: **никакого `users.db`, никакого обращения к другим нодам, никакого
общего секрета.** Четыре локальные проверки. `channel_balance_ok` читает локальный
счётчик, который обновляет демон расчётов.

Опционально шаг 3.5 — онлайн-чек у издателя (A-09): дороже, но закрывает отзыв
внутри TTL.

Почему это так мало: расписки монотонны, и предъявлять их выгодно только ноде —
она сама выберет максимальную. Значит не нужны ни revocation, ни penalty, ни

закрытие.

## Сценарий 1: обычная сессия

```
t+0.0   юзер коннектится к node-a, пароль = ваучер
t+0.0   node-a: подпись ✓, aud ✓, exp ✓, канал с B оплачен на $3.50, потрачено $3.49
t+0.0   обслуживаем, tc вешает 200 Мбит/с
t+1.6   прошло 100 МБ (тик). node-a → B: "cum должен стать 3.5002"
t+1.6   B подписывает (свой счётчик сходится), шлёт claim nonce=72
t+3.2   следующий тик...
...
раз в неделю   node-a → contract.claim(id, 47.20, sig) — одна транзакция
```

Экспозиция каждой стороны в любой момент: **один тик, $0.0002.**

## Сценарий 2: издатель решил не платить

```
t+0     B открывает канал к 50 нодам по $2  → $100 залочено, $0.50 газа
t+0     B минтит 10 000 ваучеров (бесплатно, это просто подписи)
t+1s    10 000 юзеров ломятся на 50 нод
t+1.6s  каждая нода просит расписку. B не подписывает.
t+3.2s  все 50 нод рвут сессии B
итог    B украл 50 тиков × 100 МБ = 5 ГБ = $0.01
        B потратил $0.50 газа и залочил $100, которые ноды заберут по claim
        Убыток атакующего: $0.49. Прибыль: $0.01.
```

Количество юзеров не повлияло **ни на что**. В этом весь смысл.

## Сценарий 3: атака на grace-период (A-06)

Показывает, почему grace опасен:

```
grace = 5 ГБ («издатель недоступен — обслуживаем в долг»)

атакующий открывает 1000 микроканалов по $0.10 = $100 + $10 газа
"уходит в офлайн" сразу после первого коннекта
каждая нода даёт 5 ГБ в долг → 5 ТБ трафика = $10 по цене $2/ТБ
плюс он заберёт назад $100 из каналов по таймауту

Потратил: $10 газа. Получил: $10 трафика. → на грани.
При grace 50 ГБ: получил $100 при затратах $10 → выгодно ×10.
```

**Правило: grace × число_нод × цена < стоимость газа на открытие каналов.**
На практике это значит grace < ~1 ГБ и только для каналов с историей.

## Сценарий 4: зондирование против завышения (A-04)

```
Издатель B держит эталонный хост probe.b.example.
Раз в час B поднимает обычную клиентскую сессию через node-a
  (обычный ваучер — нода не отличит от юзера) и качает ровно 1 ГБ.
B знает: должно списаться $0.002.

Списалось $0.0022  → коэффициент 1.1  → нода завышает
Три раза подряд    → node-a выводится из подписки, канал закрывается
```

Стоимость обороны: $0.002/час = $1.44/мес на ноду. Дёшево. Ловит именно то, что
не ловится расписками, — систематический множитель.

## Сценарий 5: abuse (A-01), для иллюстрации тупика

```
09:14  u_9f3a издателя B через node-a брутит SSH
11:30  Hetzner → оператору A: 24 часа на ответ
11:31  A знает: iss=B, sub=u_9f3a, время, порт. Кто это — не знает и не узнает.
11:32  A → B: подписанный abuse-репорт
       Вариант 1: B банит u_9f3a за 10 минут. Система сработала.
       Вариант 2: B молчит. A рвёт канал → теряет всех юзеров B (выручку).
       Вариант 3: B и есть атакующий. A рвёт канал, B открывает новый с
                  нового ключа. Ключ бесплатный.
12:00  Хостеру в любом варианте нужен ответ от A, а не от B.
```

Вариант 3 — тот случай, где отсутствие идентичности издателя (главное достоинство
схемы из 03!) оборачивается против системы. Экономически это не страшно (B платит
за трафик), но abuse-то не про деньги.

Это и есть A-01 в чистом виде: **экономика сходится, а оператор всё равно
остаётся один на один с хостером.** Вот здесь стоит подумать дольше всего.
