<a id="p-07"></a>
## P-07 🔴 Детект шаринга имеет потолок и умирает молча

`cluster_active_node_count` (`lib/antiabuse.sh:52`) считает, на скольких нодах
юзер сейчас гонит трафик, `abuse_observe` (`:65`) сравнивает с `pool_cap`
(эффективный лимит устройств). Юзер физически не может быть активен на большем
числе нод, чем ему выдано.

Значит при числе нод профиля меньше `pool_cap` условие `cn > cap` недостижимо
в принципе, и **детект перестаёт срабатывать без ошибок, без логов и без
единого следа**. Сегодня не проявляется (юзер на всех нодах), но сработает в
момент включения размещения профилей.

Правило: `NODES_PER_PROFILE ≥ pool_cap`. Либо перенести сигнал с `cn` (число
нод) на `conn` (`cluster_user_connections`, `lib/publish.sh:129`) — у числа
соединений потолка нет. Разбор — [design/PLACEMENT/PROBLEMS.md](../design/PLACEMENT/PROBLEMS.md) #11.

<a id="p-10"></a>
## P-10 🟢 tc-классы привязаны к имени юзера из `users.db`

Ограничение скорости (tc HTB + fq_codel, `lib/perf.sh`,
[guide/SPEED-LIMITS.md](../guide/SPEED-LIMITS.md)) заводит классы под
конкретного юзера по имени, заранее, пачкой при синхронизации.

Для чужого юзера на моей ноде привязывать не к чему: у него только непрозрачный
`sub`, появляющийся в момент коннекта. Нужен путь «класс заводится на лету по
`sub`, живёт до `exp`, убирается сборкой мусора». Внутреннего контура не
касается — заметки о модели маркета локаций (приватный репозиторий), 11 К-7.

<a id="p-16"></a>
## P-16 🟡 Кик — только у Hysteria

`api_post "/kick"` — это API Hysteria (`lib/api.sh`). Для Xray кик не написан
сознательно (комментарий `lib/protocols.sh:952`), у sing-box его нет вовсе.
Поэтому все три энфорсера — счётчиковый (`enforce_device_limits`), traffic-based
жёсткая проверка (`enforce_active_node_limit`) и авто-жёсткая проверка
анти-абуза — режут ТОЛЬКО Hysteria-сессии.

Юзер, чей клиент выбрал VLESS/Trojan/TUIC, при превышении лимита получает строку
в `limit.log` каждую минуту и ничего больше: `get_user_active` считает его
активным (трафик Xray в `collect_activity` подмешивается), решение принимается,
кик уходит в пустоту. То есть POOL_LIMIT/NODE_LIMIT, персональное число
устройств и анти-абуз держатся на протоколе, который клиент выбирает сам.

Кик Xray — это `rmu` по тегам `_proto_xray_tags` + возврат через
`_proto_xray_adu_json`, то есть три строки поверх уже написанного hot-apply.
Для TUIC пер-юзерного кика нет — только рестарт ([P-01](PROTOCOLS.md#p-01)).

**Закрыто частично** в 4.15.52 — `proto_kick_user` (`lib/protocols.sh`) зовётся
обоими энфорсерами и TUI. «Три строки» оказались неверной оценкой, проверено на
изолированных инстансах (Xray 26.3.27, sing-box 1.13.14):

* `api rmu` **не рвёт установленные соединения** — идущая загрузка пережила
  снятие юзера. Рвать сессию Xray нечем вообще. Поэтому кик здесь —
  «заморозка»: снять на `XRAY_KICK_FREEZE_SEC` (10 с) и вернуть; в это окно
  ни одно новое соединение не проходит (проверено: `curl` через прокси даёт
  пустой ответ), а текущие потоки доживают. Оборванный возврат чинит
  `proto_xray_repair` раз в минуту.
* `rmu`/`adu`/`inbounduser` требуют `HandlerService` в `api.services` — без
  него команды молча отвечают «Removed 0 user(s)».
* TUIC закрывается точечно через clash API (`DELETE /connections/{id}`), но
  соединение там = отдельный поток, а юзер в метаданных пуст (P-17) — рвём
  потоки с адресов, принадлежащих юзеру однозначно. Кред при этом остаётся
  валидным, клиент откроет новые потоки.

Полного паритета с Hysteria не будет: у Xray нет разрыва сессии, у TUIC —
отзыва креда. Что каждый движок может на самом деле —
[guide/DEVICE-LIMITS.md](../guide/DEVICE-LIMITS.md) §5.

<a id="p-23"></a>
## P-23 ✅ `abuse.dat` растёт вечно

`abuse_correct` (`lib/antiabuse.sh:117`) пересобирает файл из объединения
`ABUSE_FILE ∪ ABUSE_OBS_FILE`, то есть строка юзера переносится в новый файл
вечно, даже когда профиля давно нет. `abuse_apply` дополнительно тянет её обратно
с пиров. Единственная уборка — `sed` в `delete_user`, но демо-профили удаляет
`cluster_delete_local`, который анти-абуз не трогает (и `remove_user_abuse`
никто не зовёт).

**Проверено на node-a**: 42 строки на 13 юзеров, из них 22 — `demo-*`.

**Закрыто** в 4.11.30: `abuse_apply` фильтрует слияние по `sub_all_users`
(локальные + манифесты пиров) — призрак не переносится ни из своего файла, ни
с пира; пустой список известных фильтр не включает, чтобы сетевой сбой не снёс
живое состояние. Плюс `cluster_delete_local` (через него уходят демо-профили)
зовёт `remove_user_abuse`. Проверка — `tests/test-abuse-gc.sh`; на node-a первый
же проход оставит 18 строк из 42.

<a id="p-41"></a>
## P-41 ✅ Жёсткая проверка снимает лимит устройств внутри ноды

`enforce_device_limits` (`lib/devlimits.sh:103`) пропускает юзеров с
`get_user_hardcheck_effective = 1` — их «ведёт traffic-based энфорсер». Но
`enforce_active_node_limit` (`:134`) сравнивает `pool_cap` не с числом адресов,
а с числом **нод**, на которых юзер сейчас гонит трафик. На одной ноде это
условие недостижимо (`total=1 > cap≥1` — ложь), поэтому у такого юзера лимит
устройств внутри ноды не применяется вообще.

Попасть в это состояние можно и без админа: анти-абуз при балле ≥ 60 сам
включает окно жёсткой проверки на 6 часов (`lib/antiabuse.sh:117`). То есть чем
активнее человек шарит подписку, тем скорее он получает окно, в котором число
устройств на ноде не ограничено ничем.

Развилка осознанная — счётчиковый кик ломал переезд между нодами (комментарий
`lib/devlimits.sh:95`), — но с продажей устройств в надстройке это уже не
«мягче применяем», а «проданное
ограничение не действует». Выведено из чтения кода, на живых юзерах не
воспроизводилось. Тема целиком — [guide/DEVICE-LIMITS.md](../guide/DEVICE-LIMITS.md).

**Закрыто** в 4.15.51: пропуск убран, ограничения складываются — адреса держит
счётчиковый кик, ноды `enforce_active_node_limit`. Проверка —
`tests/test-device-limits.sh` (юзер с жёсткой проверкой и 3 адресами на лимите 1
теперь кикается наравне с обычным).

<a id="p-42"></a>
## P-42 ✅ Оплата тарифа в боте затирает докупленные устройства

`bot_pay_fulfill` (`lib/tgbot_client.sh:373`) после продления делает
`set_user_devices "$user" "$devices"` — ставит ровно тарифное число, каким бы ни
было текущее. Устройства, докупленные пользователем в надстройке за деньги, при оплате
тарифа через бота менеджера пропадают.

Деньги при этом не теряются: надстройка зажимает свою запись фактическим
лимитом менеджера (продать то, чего нет, нельзя) и восстанавливает
`тарифные + докупленные` при ближайшей покупке у себя. Но между этими двумя
событиями человек платит за устройства, которых у него нет.

Тот же по природе случай, что [P-19](BILLING.md#p-19) (покупка обнуляла тариф
скорости): фулфилмент ставит поле в тарифное значение вместо «не ниже
текущего». Выведено из чтения кода.

**Закрыто** в 4.15.51: `tariff_raise_devices` (`lib/limits.sh`) — тариф
поднимает лимит, но не опускает; `devices=0` у тарифа не трогает юзера вовсе.
Проверка — `tests/test-device-limits.sh`.

<a id="p-44"></a>
## P-44 ✅ При превышении по кластеру кикали все ноды сразу

`enforce_device_limits` (`lib/devlimits.sh`) кикал, как только
`user_over_limit` видел превышение, не спрашивая, кто именно должен уступить.
`user_over_limit` срабатывает и по `cluster_conn > pool_cap` — то есть по
СУММЕ подключений на всех нодах. Юзер с `pool_cap=1` и одной сессией на
каждой из двух нод давал это условие на обеих нодах одновременно, и каждая
рвала свою единственную сессию, хотя в собственный `node_cap` укладывалась.

Суммарное число подключений при этом не убывало: клиент переподключался туда
же за секунды, а через минуту кик повторялся. Не лимит, а бесконечная тряска —
у юзера каждую минуту обрывались все активные потоки.

**Измерено на node-a**: юзер с `pool_cap=1` и `cluster=2 local=1` кикался
каждые 61–70 секунд без единого пропуска; в журнале Hysteria на каждый кик
видно `client disconnected` и через долю секунды `client connected` с того же
адреса. За сутки по всем юзерам — тысячи записей в `limit.log`.

Долгое время это било только по юзерам без жёсткой проверки (остальных
`enforce_device_limits` пропускал). После закрытия [P-41](#p-41) под тряску
попали и они — тогда и заметили.

**Закрыто** в 4.15.54: `node_yields` (`lib/devlimits.sh`) — ноды выстраиваются
в один и тот же порядок (больше сессий → раньше, тай-брейк по хосту), место в
пределах `pool_cap` занимают первые, кикает только тот, кому места не хватило.
Данные у всех нод одни и те же (свой онлайн + кол. 2 из stats-кэшей пиров),
поэтому решение совпадает без переговоров. Собственное превышение
(`localn > node_cap`) режется сразу, без арбитража. Сравнение идёт по ХОСТУ, а
не по имени: в своём `cluster.conf` нода записана под `NODE_NAME`, а пиры — под
хостом, так что имена у каждой ноды свои. Проверка —
`tests/test-device-limits.sh`.

Тряску это ополовинивает, но не убирает: кикнутый клиент переподключается к той
же ноде, и через минуту всё повторяется. Кик в принципе не сходится против
автопереподключения — сходится только отказ на этапе аутентификации (устройство
= свой кред, занятый слот не пускает), см.
[guide/DEVICE-LIMITS.md](../guide/DEVICE-LIMITS.md) §5.

<a id="p-45"></a>
## P-45 ✅ Одно устройство считалось за столько, на скольких нодах видно

`cluster_user_connections` (`lib/publish.sh`) складывала счётчики нод:
`get_user_online_count` + сумма кол. 2 из `peers/*.stats`. Внутри ноды устройства
схлопываются по адресу (P-34), а между нодами адреса не сверялись вовсе.

Клиент замеряет пинг **по всем серверам подписки** — в Hiddify это кнопка
обновления пинга, — и на каждой ноде остаётся его сессия. Она нулевая по
трафику, но живая, и в счётчик ноды попадает. Поэтому один телефон при трёх
нодах в профиле давал `cluster=3`.

Дальше это било по лимиту устройств: `user_over_limit` сравнивает с `pool_cap`
именно кластерное число, и юзер с ОДНИМ устройством на лимите 1 получал кик
каждую минуту. Кик не сходится (клиент возвращается за секунды), так что
человек просто жил в обрывах — а по логам выглядел нарушителем лимита.

**Измерено на node-a**: у юзера с одним устройством `local=1`, `cluster=2`; вторая
сессия висела на fin1 со `speed_tx=0` и `active=0`, последнее подключение —
двумя сутками ранее. Адрес на обеих нодах один и тот же.

**Закрыто** в 4.15.55: считаем **разные адреса по всему кластеру**.
`publish_stats` публикует адреса юзера в кол. 9 `peers/*.stats`,
`refresh_online` держит их в `CACHED_ONLINE_IPS`, `cluster_user_connections`
объединяет и считает уникальные. Нода, ещё не обновлённая, кол. 9 не публикует —
её сессии считаются по-старому, отдельными, поэтому эффект появляется только
после обновления ВСЕХ нод. Сессия, провисевшая дольше `AUTHMAP_RETENTION_DAYS`
(2 суток) без переподключения, отдаёт «адрес неизвестен» — такие между нодами не
схлопываются. Проверка — `tests/test-cluster-devices.sh`.

<a id="p-56"></a>
## P-56 ✅ Исчерпав месячную квоту free, бот обещал возврат доступа через неделю

`freeplan_tick` при блокировке всегда звал `bot_notify_free_blocked` со временем
сброса НЕДЕЛЬНОГО окна (`wks + FREE_WEEK_SEC`), даже когда выбрана была месячная
квота. Человек ждал доступ на три недели раньше, чем он появлялся, и приходил с
претензией.

Закрыто: считаем сброс того окна, которое реально выбрано; выбраны оба — берём
позднее из двух (пока не освободятся оба лимита, юзер всё равно заблокирован).
Проверяется в `tests/test-freeplan.sh`.

**Возвращалось 2026-08-07.** Коммит `1cc5780` (правка про дублирование
сообщения об оплате) лёг поверх устаревшей копии файла и молча откатил эту
правку вместе с двумя соседними. Восстановлено в 4.20.79 — тест на регрессию
был, но упал только на следующем прогоне: правку без своего теста такой откат
съедает бесследно.


<a id="p-70"></a>
## P-70 ✅ Нода без `SHAPE` шейпила один Hysteria — остальные протоколы шли мимо лимита

`klimit.conf`, записанный до появления `SHAPE` (список `протокол:порт` всех
шейпимых протоколов, см. [SPEED-LIMITS](../guide/SPEED-LIMITS.md)), откатывается
на фолбэк `17:$PORT`. Фолбэк задуман как совместимость — «ведём себя как
раньше, пока конфиг не перегенерируют». На деле «пока» не наступало никогда.

Перегенерацию должен был приносить `klimit_sync_port` (`lib/perf.sh`) — он
сверяет запечённый `SHAPE` со свежевычисленным и зовёт `klimit_apply` при
расхождении. Но ветка сверки была закрыта guard'ом `[ -n "$saved_shape" ]`:
сравнение запускалось, только если `SHAPE` **уже есть**. Нода со старым
конфигом под этот guard не попадала — SHAPE ей было взять неоткуда, а без него
сверка не начиналась. Замкнутый круг: чинит только ручной заход в меню лимита
скорости на КАЖДОЙ ноде, а такого шага нигде не написано.

Итог на ноде со старым конфигом: глобальный лимит и персональные тарифы
действуют ровно на один протокол из пяти. VLESS, Trojan, TUIC и SS не попадают
ни в catch-all, ни в пер-IP фильтры — трафик идёт в обход `tc` целиком.

**Измерено** (клиент `sing-box` по ссылкам из манифеста, юзер без
персонального тарифа, скачивание 8 с):

| Нода без `SHAPE` | Hysteria2 | VLESS | Trojan | TUIC |
|---|---:|---:|---:|---:|
| A | 5.4 | 181 | 155 | 294 |
| Б | 5.9 | 396 | 447 | — |

Глобальный лимит на этих нодах — десятки Мбит/с. Шейпится только Hysteria;
разброс сотен Мбит/с по остальным протоколам — это скорость аплинка, а не лимит.
Замер с ноды, где стоит менеджер, на неё саму не годится: трафик к собственному
адресу идёт через `lo` и шейпера на пути не встречает.

Отдельно видно, что цифры **не синхронизируются по кластеру**: `DOWN_MBIT` и
`UP_MBIT` — параметры конкретного железа, их нет в `SETTING_KEYS`
(`lib/node.sh`). Поэтому лимит, выставленный на одной ноде, ничего не говорит
об остальных, и симптом «на соседней ноде в разы больше» читается как поломка,
хотя это две независимые настройки.

**Закрыто** в 4.22.89: отсутствие `SHAPE` тоже считается дрейфом —
`klimit_sync_port` сравнивает `saved_shape` с вычисленным без предварительного
guard'а на непустоту, и нода со старым конфигом лечится сама на ближайшем
`--online-sync`. Заодно ранний выход, если порт Hysteria не читается: раньше
пустой `get_port` уводил в ветку «сменился порт» и пересобирал лимит на пустом
порту. Регрессия — `tests/test-klimit-shape-drift.sh`.

Лимит скорости остаётся пер-нодовым по замыслу, но теперь на каждой ноде он
накрывает все включённые протоколы, а не один.

<a id="p-71"></a>
## P-71 ✅ Глобальный лимит скорости — один на всю ноду, а не на клиента

Меню обещает «↓ 30 · ↑ 30 Мбит/с **на IP клиента**», документация — «шейпинг
пер-IP». Фактически `tc`-путь раздаёт классы **по величине тарифа, а не по
адресу**: `_reconcile_dev` (`lib/perf.sh`) считает `cid` как `0x1000 + rate`,
поэтому все адреса с одним тарифом указывают в ОДИН класс и делят его полосу.
А клиенты без персонального тарифа — то есть почти все — попадают под catch-all
в класс `1:1` и делят между собой один глобальный лимит на всю ноду.

Десять человек в сети на ноде с лимитом 30 — это 3 Мбит/с каждому, а не 30.
Чем успешнее нода, тем медленнее у всех: деградация растёт линейно с числом
онлайна, и снаружи выглядит как «сервер тормозит».

**Замысел был пер-IP** — это видно по запасным путям в том же
`klimit.sh`, которые включаются, когда `tc` недоступен: `nft` использует
`meter hy2dl4 { ip daddr ... limit rate over ... }`, `iptables` —
`--hashlimit-mode dstip`. Оба ограничивают **каждый адрес отдельно**. Пер-IP
потеряли именно в основном, предпочитаемом пути.

**Измерено на стенде** (netns + veth, копия боевых правил шейпера, настоящие
серверы протоколов этой ноды, лимит 30 Мбит/с):

| Что мерили | Результат |
|---|---:|
| один поток, любой из 4 протоколов | 25.7–27.7 Мбит/с |
| два потока одновременно | 13.5 + 12.9 = **26.4 суммарно** |
| то же при RTT 25 мс (netem) | без изменений |

Второй поток не получил свои 30 — он забрал половину у первого. Класс общий.

Заодно снялись две гипотезы, которые выглядели правдоподобно и оказались
неверны. Размер `burst` у HTB (1593 байта, дефолт `tc`) ни при чём: при
единственном клиенте шейпер отдаёт 27 из 30 и при нулевом RTT, и при 25 мс.
Согласование полосы Hysteria тоже ни при чём: клиент с `bandwidth` 30 и клиент,
не заявивший ничего (BBR), в одиночку получают одинаково. Ранние полевые замеры
«5–6 Мбит/с у Hysteria» — это не поломка Hysteria, а его доля общего класса на
ноде, где остальные протоколы шли мимо шейпера ([P-70](#p-70)) и весь онлайн
Hysteria делил одни 30 Мбит/с.

**Важно перед закрытием [P-70](#p-70) на боевых нодах.** Пока VLESS/Trojan/TUIC
идут мимо лимита, они и спасают клиентов от общего класса. Как только P-70
доедет, все протоколы сойдутся в один класс `1:1` — и скорость у всех упадёт до
`лимит / число активных`. Чинить надо в одном заходе с P-70, иначе починка
одного ухудшит сервис.

**Закрыто** в 4.22.90. Дерево классов направления теперь такое:

```
root 1: htb default 9999
 ├ 1:9999  10 Гбит          не-туннельный трафик (SSH, маскировка-сайт)
 └ 1:1     потолок ноды     NODE_MBIT, внутренний класс
    ├ 1:ffff  гарантия/лимит   туннель с адреса вне раскладки (catch-all)
    ├ 1:2001  гарантия/лимит   адрес клиента A
    └ 1:2002  гарантия/тариф   адрес клиента B
```

`klimit_reconcile` раскладывает ВСЕ активные адреса, а не только тарифные:
адрес без тарифа получает свой класс на общий лимит направления. Миноры
пер-IP классов лежат в 0x2001–0x8fff — диапазон ограничен сверху, чтобы уборка
не задела 0x9999 и 0xffff (на этом успел споткнуться первый заход правки).

`NODE_MBIT` в `klimit.conf` — потолок всей ноды на туннельный трафик, 0 = не
ограничивать. Ставится по аплинку ноды и переживает перегенерацию конфига.

**Гарантия класса (`rate`) намеренно меньше потолка (`ceil`)** — десятая доля.
Пока класс укладывается в собственный `rate`, HTB не спрашивает родителя, и
потолок ноды на таких классах не действует вовсе. Замерено: два клиента по 30
при потолке ноды 40 давали 53.7 Мбит/с при `rate = ceil` и 36.8 при
`rate = ceil/10`. Всё сверх гарантии класс занимает у родителя — там потолок и
держит, а одиночный клиент в тишине по-прежнему разгоняется до своего `ceil`.

**Проверено на стенде** (netns + veth, два клиентских адреса, настоящие серверы
протоколов, лимит 30, потолок ноды 2000):

| Модель | Два клиента одновременно |
|---|---:|
| старая (класс по величине тарифа) | 13.0 + 13.7 = 26.7 |
| новая (класс на адрес) | 26.0 + 27.5 = **53.5** |

Источники раскладки — живой онлайн движков плюс `authmap.dat` и `ips.dat`.
Одних файлов не хватало: `authmap` помнит адрес с момента аутентификации, и
долгая сессия выпадает из часового окна, а `ips.dat` ведётся по журналу
Hysteria, так что клиента на Xray/TUIC там нет вовсе ([P-18](PROTOCOLS.md#p-18)).
На боевой ноде из-за этого класс получали два адреса из трёх, а единственный
клиент в сети оставался в общем классе. Онлайн берётся из уже прогретого кэша
(`refresh_online`), лишнего опроса движков нет.

Регрессия — `tests/test-klimit-perip.sh`: класс на каждый адрес, все под
потолком ноды, гарантия меньше потолка, уборка не трогает чужие миноры, адрес
клиента в сети попадает в раскладку помимо файлов.

<a id="p-100"></a>
## P-100 ✅ Проданное устройство продолжало работать по своей ссылке

**Симптом.** Человек докупает устройство, получает под него ссылку, продаёт
устройство обратно (лимит опускается) — и продолжает сидеть по этой ссылке
неделями. Воспроизведено на боевой ноде: устройства проданы 6 августа, слот
проданной ссылки аутентифицировался 21 августа (`slotmap.dat`).

**Причина.** Лимит проверялся **один раз, при выдаче** ссылки
(`sub_link_add`). Дальше ссылка ничем не удерживалась: токен оставался в
`subtokens.db`, файл подписки — в вебруте, пароль слота — в `slotpass.db`, а
аутентификация про число устройств не знает вовсе (`guide/DEVICE-LIMITS.md`
§4.1). Опустить лимит могли все — TUI, бот, Web API надстройки, синхронизация
кластера — и ни один из путей ссылок не трогал.

**Чем закрыто.** `sub_links_prune` (`lib/sub_links.sh`) снимает лишние ссылки,
начиная с самой новой; зовётся из `set_user_limits` (`lib/limits.sh`) —
единственного места записи лимита, поэтому действует на все четыре пути разом.
Основную ссылку не трогает никогда, чужие токены оставляет их ноде. Пароль
слота убивается сразу (`write_slotpass_db`), а не ближайшим `sub_refresh`:
файл подписки удалён, но у устройства ключ сохранён локально, и пускает его
именно справочник. Регрессия — `tests/test-slots.sh`, раздел «лимит ссылок».

<a id="p-101"></a>
## P-101 🟡 У каждой ноды свой основной токен: подписка живёт по N ссылкам

Основной токен заводит **каждая** нода кластера самостоятельно
(`sub_token_for` внутри `regen_user_subscription`), а обслуживают все ноды все
токены — чтобы уже розданная ссылка не ломалась. Следствия при N нодах:

- у юзера **N рабочих ссылок** на подписку вместо одной, и все на базовом
  пароле, то есть без слота: [P-100](#p-100) их не режет, отказ на занятом
  слоте (`guide/SLOTS.md` §5) на них не действует, а счётчиковый кик
  (`guide/DEVICE-LIMITS.md` §4.2) за домашним NAT не срабатывает — адрес один.
  Практически это одно бесплатное устройство на каждую лишнюю ноду;
- до этой правки они ещё и **считались устройствами**: `sub_link_add` сравнивал
  с лимитом все токены по кластеру, поэтому оплаченное устройство не
  добавлялось («лимит ссылок исчерпан» при одной ссылке на руках), а в кабинете
  висела вторая карточка, которую человек не покупал. Счёт исправлен —
  `sub_links_used` (bash) и `sub_tokens(user)` (`webapi/wa_payload.py`) считают
  свои токены плюс **доп.** токены пиров, основные копии пропускают.

Осталась сама раздача бесплатных копий. Лечится только общим основным токеном
на кластер (публикация + LWW, как у остальных полей подписки) — это меняет
формат обмена и требует переходного периода, когда старые токены ещё
обслуживаются. Пока живём: в кластере из двух нод это одно лишнее устройство на
человека, и оно не продаётся, а просто есть.
