# Проблемы: Кластер, подписка, состояние профиля

Обмен между нодами, точка правды жизненного цикла юзера, манифесты и токены
подписки, кластерные суммы трафика.

Реестр и правила ведения — [README.md](README.md). Номера `P-NN` сквозные
по всему реестру и не переиспользуются.

Здесь только **открытые** записи. Закрытые (✅) лежат отдельно — они объясняют, почему код
выглядит так, но не требуют работы: [CLUSTER-CLOSED-1.md](CLUSTER-CLOSED-1.md), [CLUSTER-CLOSED-2.md](CLUSTER-CLOSED-2.md).

<a id="p-03"></a>
## P-03 🔴 Нельзя снять юзера с одной ноды — только со всего кластера

`cluster_apply_roster` (`lib/cluster.sh:465`) только создаёт и никогда не
удаляет. Единственный путь удаления — `cstate_set deleted` → tombstone в
`cluster_state.dat` → `cluster_delete_local` на **всех** нодах
(`lib/cluster.sh:443`). Локального «убрать только у себя» не существует.

Наивная попытка (позвать `db_remove_user` локально) даёт бесконечный цикл:
через 5 минут `cluster_apply_roster` увидит имя в roster'е владельца и заведёт
юзера обратно, крон снова удалит, и каждая итерация меняет состав `users.db`,
то есть дёргает применение конфигов протоколов.

Это блокирует размещение профилей по нодам — разбор в
[design/PLACEMENT/PROBLEMS.md](../design/PLACEMENT/PROBLEMS.md) I.2. Нужен отдельный локальный
деприжининг, который **не** пишет в `cluster_state.dat`.

<a id="p-04"></a>
## P-04 🟡 Общий секрет кластера: утечка с одной ноды = доступ ко всем

`cluster.secret` — один общий секрет на весь кластер (`cluster_secret`,
`lib/cluster.sh:12`), проверяется Caddy как строка заголовка `X-Cluster-Auth`
(`lib/caddy.sh:73-78`). Доверие бинарное: у кого секрет — тот видит юзеров,
статистику, IP и лимиты всех нод.

Внутри своего парка это терпимо (все ноды под одной рукой). Становится
блокером в момент, когда появляется чужая нода. Решение — подписывать
**содержимое** публикуемых записей, а не запросы; разбор и обоснование в
заметки о модели маркета локаций (приватный репозиторий), 11 К-1.

<a id="p-05"></a>
## P-05 🟡 Манифест содержит пароли юзеров

`publish_manifest` (`lib/sub_links.sh:240`) публикует строки `user<TAB>uri`,
где `uri` — готовая ссылка подключения **с паролем юзера на этой ноде**. То
есть каждая нода кластера знает учётные данные каждого юзера на каждой другой.

Внутри своего контура это осознанная плата за единую подписку без общей базы.
Наружу такой манифест уходить не должен никогда: чужому оператору полагается
ваучер с непрозрачным `sub`, а не строка манифеста. См.
заметки о модели маркета локаций (приватный репозиторий), 11 К-3 и Н-3.

<a id="p-06"></a>
## P-06 🟡 Нет паспорта ноды

`publish_peers_list` (`lib/cluster.sh:54`) публикует только `name|host`.
Ёмкость, метка локации, набор протоколов, версия — либо не публикуются вовсе,
либо разбросаны по секциям. Ни один из 17 `publish_*` не отдаёт факты ноды
о себе одним куском.

Из-за этого нода, принимающая решение (например о размещении профиля), не
знает свойств соседей. Класть такие поля в `SETTING_KEYS` нельзя — они
синхронизируются LWW, то есть любая нода перезапишет чужое утверждение о себе.
Нужен single-writer `nodeinfo` — [design/PLACEMENT/](../design/PLACEMENT/README.md) §3.1.

<a id="p-08"></a>
## P-08 🟡 Все юзеры на всех нодах

Провижининг через API/бота/мини-апп делает профиль кластерным, и он заводится
на каждой ноде. Следствия: рост упирается в самую слабую ноду вместо «добавить
ещё одну»; понятия ёмкости ноды нет; сигнала «места не осталось, пора покупать
VPS» нет — деградация происходит тихо.

Спроектировано, кода нет: [design/PLACEMENT/](../design/PLACEMENT/README.md). Реализация
упирается в P-03.

<a id="p-13"></a>
## P-13 🔴 Удаление профиля на одной ноде не удаляет его в кластере

`delete_user` (`lib/users.sh:121`) ставит tombstone только когда юзер **числится
кластерным**: `was_cluster` вычисляется через `is_cluster_user`, то есть по
roster'у (своему или пира). Юзер вне roster'а исчезает только локально. На пирах
он остаётся живым, его ключи продолжают приходить в манифестах, а
`regen_subscriptions` (`lib/sub_links.sh:282`) пишет ему подписку под ВСЕ токены,
включая старый токен из кэша пира — cstate пуст, значит «пустую подписку» никто
не отдаёт.

**Проверено на node-a** (27.07.2026): `admin`, `user-b`, `user-c`, `user-d`,
`user-e` отсутствуют в `users.db` и `disabled.dat`, но их файлы в
`/var/www/hy2sub/sub/` отдают рабочий набор ключей node-b (hysteria2 + vless +
trojan + tuic), потому что на node-b профили живы (по 4 строки в
`peers/node-b*.manifest`).

Это зеркало [P-03](#p-03): там нельзя снять юзера с ОДНОЙ ноды, здесь удаление с
одной ноды не снимает его НИГДЕ, и оба состояния выглядят для админа одинаково
(«я его удалил»). Пока не решён вопрос локального vs кластерного удаления,
безопасный путь один — удалять кластерных юзеров, а не «просто удалять».

<a id="p-14"></a>
## P-14 🟡 Осиротевшие токены подписки не убираются никогда

Уборка в конце `regen_subscriptions` считает токен валидным, если он есть в
`SUBTOKENS_DB` **или** в кэше `peers/*.subtokens`. Ни один код не вычищает
строку из `SUBTOKENS_DB` при исчезновении юзера мимо `delete_user`, а пир
публикует свой список токенов вечно. Итог: файл подписки не переписывается (юзера
нет в `sub_all_users`) и не удаляется (токен «валиден»).

**Проверено на node-a**: 27 локальных токенов на 13 юзеров (14 сирот, среди них
демо-профили и запись `type` — след давнего бага парсинга), 56 файлов в
`/var/www/hy2sub/sub/` против 13 действующих профилей. Часть файлов пустые, часть
— с рабочими ключами (см. [P-13](#p-13)).

Нужен GC по TTL: токен, чей юзер не встречается ни локально, ни в манифестах
пиров N суток, удаляется вместе с файлом.

<a id="p-22"></a>
## P-22 🟡 Кластерная сумма трафика немонотонна, а free-план строит на ней разницу

`freeplan_tick` считает расход как `bytes - wkb`, где `bytes` —
`freeplan_user_bytes` = локальный `stats.dat` + сумма по `peers/*.stats`. Эта
сумма умеет **уменьшаться**:

- `publish_stats` (`lib/publish.sh:16`) идёт по `users.db`, поэтому отключённый
  юзер (в том числе отключённый самим free-планом) пропадает из статистики своей
  ноды целиком;
- `cluster_online_sync` (`lib/cluster.sh:805`) при недоступном пире записывает
  **пустой** файл `peers/<name>.stats` — сознательно, «чтобы не залипать на
  старом».

В обоих случаях `bytes` падает ниже базы `wkb`, `wk_used` обрезается в 0, и
`freeplan_tick` считает, что квота свободна: заблокированного юзера впускают
обратно с уведомлением «квота сброшена», а нода, у которой байты на месте,
блокирует его снова — с уведомлением о блокировке. LWW по ts делает это
устойчивым пинг-понгом: сетевой чих пира = пара уведомлений юзеру.

Не воспроизведено, выведено из чтения. Правильное лечение — считать расход по
монотонному кумулятиву (публиковать его в `publish_stats` и хранить базу по
нодам), а не по разнице агрегата, который может исчезнуть.

<a id="p-24"></a>
## P-24 🟢 Хвосты удалённого профиля достаются одноимённому новому

`delete_user` чистит 12 файлов, но не `freeplan.dat`, `expiry_ts.dat`,
`cluster_pwreset.dat`, `rates.dat`, `subips.dat`. `cluster_delete_local`
(`lib/cluster.sh:391`) чистит ещё меньше — без `activity*`, `abuse*`, `freeplan`.

**Проверено на node-a**: `expiry_ts.dat` — 18 строк на 13 юзеров, `userlimits.dat`
содержит три давно удалённых `demo-*`, `cluster_state.dat` — записи `type`,
`zzclustercheck`, `tg*`.

Профиль, заведённый под тем же именем (а имена вида `tg<ID>` выдаёт бот
детерминированно!), наследует: строку free-плана в состоянии `blocked`, старые
метки времени срока и лимитов. Последнее опасно в LWW: чужой ts с пира может
оказаться больше свежей локальной правки. Не воспроизведено.

<a id="p-32"></a>
## P-32 🟡 Нода с самоподписанным сертификатом не лечится сама

Наблюдалось на одной из нод кластера. Если во время выпуска сертификата нода
недоступна снаружи по своему домену (типично — нет A-записи, см. P-31, или
закрыт :80 для проверки HTTP-01), ACME-проверка Let's Encrypt не проходит и
Caddy откатывается на внутренний CA — самоподписанный сертификат с чужим CN и
сроком в десять лет.

Ключевое: **после починки DNS сертификат сам собой не переоформляется**. Нода
выглядит живой (порт отвечает, TLS-рукопожатие проходит), но для клиентов не
работает ничего поверх TLS — ни выдача подписки по HTTPS, ни VLESS/Trojan/TUIC.
Кластерная синхронизация с ней тоже стоит: `curl -fsS` отвергает такой
сертификат.

Диагностика — с любой другой ноды, по IP и с явным SNI, чтобы результат не
зависел от DNS:

```
openssl s_client -connect <IP>:443 -servername <домен-ноды> </dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

`issuer`, совпадающий с `subject`, и срок в 10 лет — признак внутреннего CA.
Здоровая нода показывает `issuer` Let's Encrypt.

Лечение — на самой проблемной ноде: убедиться, что её домен резолвится в её же
адрес и что :80 открыт, затем `systemctl restart caddy`; если не помогло —
смотреть `journalctl -u caddy` и вычистить кэш сертификатов Caddy
(`/var/lib/caddy/.local/share/caddy/certificates`).

Автоматически это состояние теперь видно в шапке менеджера (P-31): проба
отличает невалидный сертификат от лежащей ноды и от неверного секрета.

**Частично закрыто** в 4.38.170 (`a89a763`): нода без доверенного сертификата
пишет это в справку о себе (`cert_days=none`, [guide/NODE-HEALTH.md](../guide/NODE-HEALTH.md))
и раз в час перезапускает Caddy — но только если запрос к собственному домену
действительно падает на проверке цепочки. **На живом случае не проверено:** такой
ноды в кластере сейчас нет. Чистка кэша сертификатов Caddy по-прежнему ручная.

<a id="p-80"></a>
## P-80 🟡 Имя профиля нельзя сменить: в кластере оно ничем не переносится

Запрошено из кабинета: человек видит, под каким именем живёт его доступ, и
хочет его сменить — имя приходит из его ника в мессенджере и тем самым связывает
профиль с личностью. Сделать это сейчас нечем, и дело не в объёме работы.

**Что мешает.** Профиль с этим именем заведён на КАЖДОЙ ноде кластера
([P-08](#p-08)), а удалить профиль на соседней ноде менеджер не умеет
([P-13](#p-13)). Значит любая «смена имени» — это создать новый профиль и
оставить старый живым на всех остальных нодах: его пароль, его ссылки и его
слоты продолжат работать. Приватности это не добавляет вовсе, зато добавляет
второй рабочий доступ, о котором владелец не знает. Это ухудшение
безопасности, а не улучшение.

Дальше по списку, даже если удаление починить:

- именем ключуются `stats.dat`, `ips.dat`, `expiry.dat`, `abuse.dat`,
  `freeplan.dat`, `userlimits.dat`, слоты и tc-классы ([P-10](LIMITS.md#p-10)),
  плюс те же файлы в кэшах пиров. Перенос — это миграция полутора десятков
  файлов на трёх машинах, атомарности между которыми нет;
- счётчик трафика на новом имени начинается с нуля. На бесплатном тарифе это
  сброс квоты — то есть смена имени становится способом обнулять лимит;
- подписка у человека на руках содержит ключи всех нод: пока переименовались не
  все, часть ключей отваливается.

**Что сделано вместо.** Кабинет показывает имя профиля и объясняет, почему
кнопки нет и куда написать, если сменить всё-таки нужно (делается руками, с
переносом остатка срока). Запись висит здесь до [P-13](#p-13): пока удаление не
доезжает до соседей, безопасной смены имени не существует.

<a id="p-113"></a>
## P-113 🟡 Устройства и приложения видит только та нода, с которой качали

`subapps.dat` заполняется разбором access-лога **своего** Caddy
([SUB-CLIENTS.md](../guide/SUB-CLIENTS.md)): нода знает лишь те скачивания,
которые обслужила сама. По кластеру раздел не ездит — в `CLUSTER_SYNC_SECTIONS`
его нет, `publish_*` для него не написан.

Следствия, обе стороны одинаково реальны:

* **Карточка и кабинет неполны.** Человек с ссылкой соседней ноды выглядит
  «без устройств» на этой, хотя качает подписку каждый час. Проверено: у юзера,
  чья основная ссылка выдана соседом, на нашей ноде видно только те заходы, что
  случайно пришли по нашему токену.
* **Счёт устройств для тревоги занижен** ([SUB-ALERTS.md](../guide/SUB-ALERTS.md)
  правило 3): условие «устройств больше, чем оплачено» считается по локальным
  записям, поэтому утечка, целиком живущая на соседней ноде, не заметна здесь
  вовсе. Ошибка в сторону молчания — ложной тревоги она не даёт.

Сделано так сознательно: первый заход собирает и показывает данные на одной
ноде, чтобы фича проверилась на живом трафике, а не отлаживалась сразу в трёх
местах. Починка — раздел `subapps` в `CLUSTER_SYNC_SECTIONS` плюс
`publish_subapps` (копия `publish_subips`, `lib/publish.sh`) и объединение
локальных строк с `peers/*.subapps` в `get_user_apps`.

Внимание при починке: ключ строки — токен, а токены у нод разные
([P-101](LIMITS.md#p-101)), поэтому одно устройство приедет с соседа под другим
токеном и тем же `hwid`. Объединять надо по `hwid`, иначе один телефон станет
двумя устройствами и поднимет ложную тревогу — ровно то, чего вся конструкция
уведомлений избегает.

<a id="p-185"></a>
## P-185 🟢 Чистка удалённого профиля написана дважды, и списки файлов разошлись

`delete_user` (`lib/users.sh`) и `cluster_delete_local` (`lib/cluster.sh`) делают
одно и то же — снять токен, убрать из базы, вычистить строки из файлов данных, —
каждая своим `sed -i` по своему списку. В `delete_user` в списке 11 файлов, в
`cluster_delete_local` — 7: `activity.dat`, `activity_prev.dat` и `abuse_obs.dat`
удаление, пришедшее от соседа, не чистит. Следствие — хвосты удалённого профиля
на нодах, где его удалили не руками (родня [P-24](#p-24)). Сводить в одну функцию
с одним списком; не сделано, потому что обе ветки стоят на пути удаления
профилей и требуют теста на обе.
