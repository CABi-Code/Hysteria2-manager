<a id="p-01"></a>
## P-01 ✅ TUIC рестартует при любом изменении состава юзеров

У sing-box нет управления составом юзеров: есть только `clash_api`
(`lib/protocols.sh:364`) для статистики и соединений. Состав задаётся в
конфиге, применяется рестартом. Значит **любой новый юзер рвёт TUIC-сессии
всех остальных юзеров ноды**, и так на каждой ноде кластера.

Для Xray это починено (`_proto_xray_hot_apply`, коммит `797352f`), для
Hysteria проблемы не было никогда — у неё внешний auth-скрипт. TUIC остался
единственным.

Обходного пути в рамках sing-box нет. Варианты: батчить рестарты (раз в N
минут вместо каждого юзера), заменить движок TUIC, отказаться от TUIC.
В модели ваучеров TUIC не работает вообще — [research/11-transition.md](../research/11-transition.md) К-2.

**Закрыто** в 4.12.42 первым вариантом — `proto_tuic_apply` (`lib/protocols.sh`)
вместо немедленного рестарта:

* сервис лежит → применяем сразу, рвать нечего;
* активных TUIC-соединений нет → применяем сразу (обычный случай: соединения
  короткие, список пустеет сам);
* иначе ждём, но не дольше `TUIC_APPLY_MAX_DELAY_SEC` (600 с).

Конфиг всё это время уже на диске, повторную попытку делает минутный крон
`--online-sync`. Десять новых юзеров подряд дают ОДИН рестарт вместо десяти, а
провижининг больше не ждёт рестарта sing-box (см. памятку про ~18 с).

Цена: TUIC у нового юзера заработает не мгновенно (остальные протоколы — сразу),
и простаивающую QUIC-сессию мы всё же можем оборвать — в списке соединений её не
видно, клиент переподключится сам. Проверки — №11 в `tests/test-xray-hotapply.sh`.
Корневой потолок (нет управления юзерами на лету) никуда не делся: это смягчение,
а не устранение.

<a id="p-02"></a>
## P-02 ✅ Трафик TUIC не считается вообще (не «приближённо»)

`proto_collect_tuic_traffic` суммирует дельты байт соединений из
`clash_api /connections` раз в минуту: у sing-box 1.13 нет доступного
StatsService (он за тегом сборки `with_v2ray_api`, которого в релизах нет). Соединения, закрывшиеся между снимками, теряют
хвост. Доминирующий объём (стриминг, загрузки) ловится, короткие запросы
недосчитываются. Hysteria и VLESS/SS считаются точно.

**Исправлено по итогам проверки [P-17](#p-17) (4.11.33):** формулировка выше
была слишком доброй. Соединения фильтруются по `.metadata.user`, а этого поля у
sing-box НЕТ — значит TUIC-байты не попадают в `stats.dat` ВООБЩЕ, тихо и без
ошибок. Потолок остаётся: атрибутировать TUIC по `sourceIP` (как сделано для
онлайна) в квоты нельзя — на общем CGNAT-IP байты запишутся не тому юзеру.
Настоящее лечение — per-IP nftables-счётчики на порту TUIC
([guide/SPEED-LIMITS.md](../guide/SPEED-LIMITS.md)) либо смена движка.

Точный per-user учёт возможен через per-IP nftables-счётчики на порту TUIC —
см. [guide/SPEED-LIMITS.md](../guide/SPEED-LIMITS.md). Подробности
ограничения — [guide/MULTIPROTOCOL.md](../guide/MULTIPROTOCOL.md), «Известные ограничения».

**Закрыто** в 4.12.42 — в тех рамках, которые движок вообще позволяет.

Сначала перепроверен потолок: у официального релиза sing-box StatsService живёт
за тегом сборки `with_v2ray_api`, которого в сборке нет (в бинарнике 1.13.14
лежит строка «v2ray api is not included in this build, rebuild with -tags
with_v2ray_api», а `Tags:` в `sing-box version` его не перечисляет). Значит
per-user счётчиков нет и не будет без своей сборки — остаётся clash_api.

Возражение «резолв по IP запишет байты не тому юзеру» снято сужением правила:
`_proto_ip_sole_owner_lines` отдаёт адрес, только если за ним в `ips.dat` +
`authmap.dat` (+ файлы пиров) за `TUIC_IP_OWNER_WINDOW_DAYS` (7) стоит РОВНО
ОДИН юзер. Общий адрес не резолвится ни в кого, и его байты просто не
засчитываются: недосчитать безопаснее, чем списать чужую квоту. На живой ноде
из 43 адресов недели однозначны 41, общих — 2.

Фильтр по несуществующему `metadata.user` убран, снимок `id→байты` теперь
пишется по ВСЕМ соединениям (раньше он был всегда пуст, и механизм дельт не
работал вовсе). Остаточный недосчёт прежний и неустранимый на clash_api:
соединения, закрывшиеся между минутными снимками, теряют хвост. Проверки — №10
в `tests/test-xray-hotapply.sh`.

<a id="p-15"></a>
## P-15 ✅ Онлайн Xray-протоколов всегда пуст

`proto_online_json` (`lib/protocols.sh:915`) спрашивает у Xray
`statsquery -pattern "online"`, но в генерируемом конфиге (`lib/protocols.sh:325`)
в `policy.levels."0"` включены только `statsUserUplink`/`statsUserDownlink`.
Счётчиков онлайна Xray не заводит вовсе.

**Проверено на node-a**: `xray api statsquery -pattern online` → `{}` при непустых
`user>>>…>>>traffic>>>…`. Значит юзер, сидящий на VLESS/Trojan/SS, **нигде не
считается онлайн**: индикатор в TUI, боте и мини-аппе, `{online}` в подписи
ключа, `cluster_user_connections`, счётчиковый кик `enforce_device_limits`.

По документации Xray лечится флагом `"statsUserOnline": true` в
`policy.levels."0"` (+ рестарт Xray) — но проверять надо на месте, метка менялась
между версиями, как это уже было с ключами REALITY.

**Закрыто** в 4.11.32, флага оказалось мало. Проверено на node-a (Xray 26.3.27):
после включения `statsUserOnline` и рестарта `statsquery -pattern "online"`
по-прежнему отдаёт `{}` при непустом `user>>>…>>>traffic` — счётчики онлайна
живут в ОТДЕЛЬНОМ реестре и достаются только командой `api statsonline -email`
по одному юзеру, причём при нуле сессий поля `value` в ответе просто нет
(protobuf-JSON). Поэтому в `proto_online_json` ветка Xray переписана на обход
`users.db` с `statsonline` (13 юзеров + TUIC ≈ 2,9 с, крон раз в минуту).
Первый живой замер на node-a: `{"user-a": 1}` — до этого там всегда было
пусто. Регресс закрыт проверкой №8 в `tests/test-xray-hotapply.sh`.

<a id="p-17"></a>
## P-17 ✅ Трафик и онлайн TUIC читают `metadata.user`, которого нет

`proto_collect_tuic_traffic` (`:775`) и TUIC-ветка `proto_online_json` (`:928`)
фильтруют соединения по `.metadata.user != null and != ""`. А
`proto_tuic_activity_lines` (`:876`) в том же файле утверждает обратное:
«sing-box (clash_api) НЕ отдаёт user в метадате соединения (проверено
эмпирически)» — и потому резолвит юзера по `sourceIP` через `ips.dat`.

Оба утверждения одновременно верными быть не могут. Если верно второе, то TUIC
не считается **вообще** (а не «приближённо», как обещает [P-02](#p-02)) и не даёт
онлайна — молча, без ошибок, ровно как в [P-07](LIMITS.md#p-07).

**Проверено на node-a** (sing-box 1.13.14, 10 снимков за 50 с, 44 живых
TUIC-соединения): поля `metadata.user` НЕТ ни у одного. Верно второе
утверждение — фильтр по `user` отбрасывает всё.

**Закрыто в 4.11.33 наполовину, по частям:**

* **Онлайн** — починен: ветка TUIC в `proto_online_json` больше не фильтрует по
  `metadata.user`, а резолвит соединения в юзера по `sourceIP` тем же путём, что
  и активность. Дублирования нет: `proto_tuic_activity_lines` получила режим
  `conns` (считать соединения вместо байт) и используется обеими. Первый живой
  замер на node-a: `{"user-a": 4}` (1 сессия Xray + 3 соединения TUIC).
  Регресс закрыт проверкой №9 в `tests/test-xray-hotapply.sh`.
* **Трафик** — НЕ починен намеренно, см. исправленный [P-02](#p-02): резолв по
  IP в квоты не пускаем (на общем CGNAT-IP байты запишутся не тому юзеру), а
  другого источника у sing-box нет.

<a id="p-18"></a>
## P-18 🟡 IP-трекинг только по журналу Hysteria

`collect_ips` (`lib/ip_tracking.sh:43`) парсит `journalctl -u
hysteria-server.service`. Клиент, который ходит по VLESS/Trojan/TUIC, в
`ips.dat` не попадает никогда. `authmap.dat` — тоже чисто Hysteria: его пишет
auth-скрипт на каждое подключение.

Следствия по цепочке:
- карточка юзера показывает только Hysteria-IP (для VLESS-клиента — пусто);
- `klimit_reconcile` (`lib/perf.sh`) берёт связку user→IP из `authmap.dat` +
  `ips.dat`, то есть **персональный тариф скорости не применяется к клиенту,
  который не подключался по Hysteria**: его IP нет ни в одном источнике, пер-IP
  фильтра нет, трафик уезжает в catch-all → глобальный класс (а при `DOWN_MBIT=0`
  — вообще без потолка);
- `proto_tuic_activity_lines` резолвит TUIC-соединение по `ips.dat` и на
  «чистом» TUIC-клиенте не резолвит ничего.

<a id="p-33"></a>
## P-33 ✅ Онлайн Xray считал историю IP, а не устройства в сети

Ветка Xray в `proto_online_json` (`lib/protocols.sh`) брала число из
`xray api statsonline -email <user>`. Это НЕ число текущих сессий: значение —
размер карты онлайн-IP юзера, а карту Xray сам не чистит.

**Проверено на живой ноде** (Xray 26.3.27): `statsonlineiplist` для одного
профиля отдал 11 IP с метками `last_seen` возрастом от 13 минут до 137 часов, и
`statsonline` для него же вернул ровно 11. То есть счётчик рос на КАЖДЫЙ новый
IP за последние сутки-неделю. На мобильном операторе (CGNAT, IP меняется каждые
несколько часов) один телефон превращался в 5–11 «устройств»: в замере по ноде
семь профилей из семи онлайн показывали 2…11 при фактически одном-двух
устройствах у каждого.

Последствия шли дальше индикатора: то же число уходило в `publish_stats` →
`cluster_user_connections` и в счётчиковый кик `enforce_device_limits`, то есть
юзера с одним телефоном могло кикать за превышение лимита устройств.

**Закрыто** в 4.12.37. `proto_online_json` спрашивает `statsonlineiplist` (та же
одна локальная команда на юзера, цена не изменилась) и считает только IP свежее
`XRAY_ONLINE_WINDOW_SEC` (дефолт 120 с при кроне раз в минуту). Тот же замер
после правки: два профиля по 1 устройству. Регресс закрыт проверкой №8 в
`tests/test-xray-hotapply.sh` (карта с 3 свежими и 2 протухшими IP → 3).

Остаточная неточность — в безопасную сторону: если клиент держит одно длинное
соединение и не открывает новых, его IP в карте не обновляется и он выпадает из
счёта раньше времени (недосчёт → лишних киков не будет). Индикатор «онлайн» в
мини-аппе от этого не зависит вовсе — он строится на трафике (`active`), см.
[guide/ONLINE.md](../guide/ONLINE.md).

<a id="p-34"></a>
## P-34 ✅ Онлайн складывался по протоколам — один клиент считался трижды

`refresh_online` брал число сессий Hysteria из `/online` и ПРИБАВЛЯЛ к нему
онлайн Xray и TUIC (`_proto_merge_online` суммировал значения по ключу). Но
клиент держит подписку на всех протоколах сразу и пингует их для замера
латентности — [«Зачем»](../guide/ONLINE.md) в документе про онлайн описывает
ровно это. Значит одно устройство давало +1 в каждом движке, и «устройств» у
юзера выходило втрое больше, чем есть. Вместе с [P-33](#p-33) (история IP
вместо текущих сессий) это и давало числа вроде 11 у человека с одним телефоном.

Число уходило не только в индикатор: `publish_stats` → `cluster_user_connections`
и счётчиковый кик `enforce_device_limits` считают по нему же лимит устройств.

**Закрыто** в 4.12.38. Каждый источник отдаёт теперь строки «user|ip», а
`refresh_online` считает РАЗНЫЕ адреса юзера: общий для протоколов IP схлопывается
в одно устройство. Адреса Hysteria-сессий — из `authmap.dat` (auth-скрипт пишет
их на каждое подключение), столько последних разных, сколько сессий в `/online`;
нет записей — засчитываем одно устройство, а не ноль. Живой замер до правки:
семь профилей со значениями 2…11; после — все по 1. Регресс закрыт проверкой №10
в `tests/test-xray-hotapply.sh`.

Остаточная неточность в обе стороны, но в разы меньше прежней: устройства за
одним NAT считаются за одно, а клиент со «старой» Hysteria-сессией и новым
мобильным адресом — за два. Точнее без per-session IP в API Hysteria не выйдет.
