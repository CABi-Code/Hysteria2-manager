## P-133 ✅ Крючок обновления требует Web API на ЦЕЛИ, и об этом никто не говорит

`cluster_update_peers` стучится в `/v1/cluster/update` соседа, то есть в его
**Web API**. А блок, который этот маршрут вообще создаёт, генерируется в
`setup_caddy` (`lib/caddy.sh`) под условием:

```bash
local api_block=""
if type -t webapi_enabled >/dev/null 2>&1 && webapi_enabled; then
    api_block="    handle_path /api/* { reverse_proxy 127.0.0.1:$(webapi_port) }"
fi
```

Web API на ноде выключен (`webapi.conf` без `ENABLED=1`) → блока в Caddyfile
нет → любой `/api/*` проваливается в финальный `handle {}` и получает **200 с
текстом заглушки подписки**. Крючок видит не то тело, которого ждёт, и
рапортует отказ.

**Почему это не замечают годами.** Web API включают там, где он кому-то нужен —
на ноде с кабинетом. На остальных нодах его включать незачем: клиентам он не
нужен, менеджер работает и без него. Никакой связи «нет API → нельзя обновить
удалённо» ни в меню, ни в подсказке крючка не сказано, а сообщение об отказе
перечисляет три причины сразу («старая версия, Web API не отвечает снаружи или
другой секрет») — и админ идёт проверять версию, потому что это первый пункт.

**Проверено 04.09.2026 на живом кластере.** Обе соседние ноды обновлены вручную
до текущей версии и публикуют её в `cluster/version`; обе продолжают отвергать
`--cluster-update`. Пробы снаружи заведомо несуществующим маршрутом
`/api/v1/nosuchroute` разделяют случаи однозначно:

| Нода | Версия | Ответ | Что это значит |
|---|---|---|---|
| эталон (Web API включён) | 4.28.128 | `404` от демона | запрос дошёл до Web API |
| сосед A | 4.28.128 | `200`, заглушка подписки | блока `/api` нет вовсе |
| сосед B | 4.28.128 | `200`, заглушка подписки | блока `/api` нет вовсе |

Разбор именно по этому ответу, а не по `/v1/info`: у `handle /api/*` (старая
форма, которую чинит `migrate_caddy_api_prefix`) запрос ушёл бы в демон и вернул
`404`; у лежащего демона `reverse_proxy` отдал бы `502`. Заглушка означает
ровно одно — маршрута нет ни в каком виде.

**Лечится на ноде, одним пунктом меню:** главное меню → `6. Web API` →
`1. Включить API`. `webapi_enable` ставит юнит, поднимает демон и **сам
пересобирает Caddyfile** с блоком `/api/*`. После этого крючок работает.

### Что здесь стоит поправить в коде

1. **Сказать вслух про зависимость.** Отказ крючка сейчас — список из трёх
   догадок. Отличить их можно ровно той пробой, что в таблице выше: заглушка
   вместо `404` = «у соседа выключен Web API», и это надо печатать прямо,
   вместе с пунктом меню, которым чинится.
2. **Публиковать факт в паспорте ноды.** Включён ли Web API — свойство ноды,
   которое сейчас не публикуется никак (см. [P-06](CLUSTER.md#p-06)), поэтому здоровье
   кластера не может показать «сосед недостижим для обновления» заранее, до
   первой неудачной попытки.
3. `migrate_caddy_api_prefix` к этой проблеме отношения не имеет: она чинит
   ноду, у которой блок есть, но в старой форме. Здесь блока нет вообще.

Пока Web API не включён на соседях, любая правка, доехавшая до одной ноды, на
них не работает, а выглядит рабочей — то самое, о чём правило про кластер в
корневом `CLAUDE.md`. Из свежего: резервный инбаунд VLESS+XHTTP
([MULTIPROTOCOL.md](../guide/MULTIPROTOCOL.md#второй-vless-xhttp-как-резерв-а-не-замена))
доехал кодом до обеих нод, но включать его там всё равно придётся на самой
ноде: удалённого управления протоколами в API нет, `protocols.conf` — файл ноды.

**Чем закрыто** (4.28.130): просьба обновиться больше не команда по Web API, а
**объявление в файловом канале** — раздел `updatereq` со строкой «версия|ts».
`cluster_update_peers` не зовёт `cluster_post` вовсе, разбирать чужие ответы не
нужно (их нет), и вместо ложного «💚 запущено» админ видит «заберут на своей
синхронизации». Устройство и оговорки — [guide/CLUSTER-CHANNELS.md](../guide/CLUSTER-CHANNELS.md#как-теперь-устроено-обновление),
проверки — `tests/test-cluster-updatereq.sh` плюс сторож «Web API из этого пути
ушёл» в `tests/test-cluster-strand.sh`.

Ручка `POST /v1/cluster/update` осталась рабочей как альтернативный путь
«обнови себя»; кластер от неё больше не зависит.

**Осталось осознанно:** `nudge` по-прежнему ходит через Web API, и это
правильно — его смысл в том, чтобы обогнать крон, а объявление в файле читается
тем самым кроном. Его отказ стоит минут задержки, а не потери, поэтому
зависимость допустима. Общее правило выбора канала — в
[CLUSTER-CHANNELS.md](../guide/CLUSTER-CHANNELS.md#коротко).

Что стоит сделать отдельно (не закрыто): печатать в отказе конкретную причину
вместо списка догадок и публиковать состояние Web API в паспорте ноды
([P-06](CLUSTER.md#p-06)), чтобы недостижимость соседа была видна заранее.

## P-134 ✅ Имя пира из gossip становилось путём записи от root

**Проверено в песочнице целиком** (04.09.2026), не выведено из чтения.

Файловый канал наполняет реестр пиров по gossip: `cluster_sync` тянет чужой
`/cluster/peers.list` и скармливает каждую строку `cluster_add_peer`. То есть
**имя пира — это недоверенные данные**. Дальше `cluster_peer_name` отдавала имя
из реестра как есть (санитайз стоял только на запасном пути, где имя выводится
из хоста), а имя подставляется в путь файла кэша.

Цепочка, воспроизведённая по шагам:

```
сосед отдаёт peers.list:  ../../../../etc/logrotate.d/pwn|attacker.example
cluster_add_peer          -> строка легла в реестр без проверок
cluster_peers             -> хост попал в опрос
cluster_peer_name         -> вернула имя со слэшами
cluster_sync              -> запись в /etc/logrotate.d/pwn.manifest
```

Содержимое файла при этом целиком контролирует атакующий: это тело ответа его
же раздела. Через ту же функцию шли **все пять** мест записи кэша и `rm -f` в
`cluster_remove_peer`, то есть и произвольное удаление.

Суффикс ограничен именем раздела (`.manifest`, `.state`, …), поэтому это не
любой файл. Но `logrotate` разбирает в `/etc/logrotate.d/` файлы с такими
суффиксами (`tabooext` по умолчанию их не отсекает — на ноде проверено, что
своего `tabooext` нет), а `postrotate` исполняется root'ом. Оценка пути до RCE
здесь **выведена, а не воспроизведена**: конфиг logrotate на боевой машине не
подкладывался.

Для атаки нужен секрет кластера и живой HTTPS-хост — то есть одна уже
скомпрометированная нода. Что усугубляло: секрет читался кем угодно локально
([P-135](OPS-CLOSED-2.md#p-135)).

**Чем закрыто** (4.28.129): `_cluster_safe_name` и санитайз в ДВУХ местах — на
входе в реестр (`cluster_add_peer`) и при чтении из него (`cluster_peer_name`,
вторая линия для реестра, отравленного до обновления). Хост проверяется на вид
имени: слэш, двоеточие, пробел, `@`, `?`, `#` больше не проходят. Пустое имя
больше не сводит все пиры в один файл. `cluster_remove_peer` перестал парсить
реестр своим awk.

**Чистятся только разделители пути** — не «всё, кроме `[a-zA-Z0-9_.-]`». Первая
версия правки была именно такой и переименовала бы «Finnish Noda 2» в
«Finnish_Noda_2»: файл кэша сменил бы имя, старый остался бы лежать, а читаются
они глобом `peers/*.stats` — нода считалась бы **дважды**, с двойным трафиком и
онлайном и сорванными квотами. Поймано тестом до попадания на ноды. Без слэша
«..» в имени файла каталог не меняет, вычищать её отдельно незачем.

Проверки — `tests/test-cluster-channel-security.sh`: отравленное имя, негодные
хосты, отравленный реестр, сохранность человеческих имён, режим Caddyfile.
Модель угроз канала целиком — [guide/CLUSTER-CHANNELS.md](../guide/CLUSTER-CHANNELS.md#безопасность).

## P-138 ✅ Токен подписки из данных пира становится путём записи от root

Тот же класс, что [P-134](#p-134), но на другом пути: недоверенная строка из
файлового канала подставляется в путь файла без проверки формы.

`regen_user_subscription` (`lib/sub_links.sh`) собирает список токенов юзера из
двух источников — своей базы и кэша пиров:

```
awk -F: -v u="$user" '$1==u{print $2}' "$PEERS_DIR"/*.subtokens
```

и дальше каждый токен **становится именем файла**:

```
printf '%s' "$tokcontent" > "$WEBROOT/sub/$tok"
```

Раздел `subtokens` приезжает от пира как есть (`cluster_sync` кладёт тело
ответа в `peers/<имя>.subtokens` без разбора содержимого), а `pwgen`-форма
токена нигде не проверяется. Строка вида `юзер:../../../<путь>` в чужом разделе
даёт запись файла от root в произвольном месте: перевыпуск подписок крутит
крон, то есть под root. Содержимое — base64 подписки, но одной перезаписи
хватает, чтобы снести конфиг или юнит.

Те же токены идут в `rm -f` (`sub_link_remove`, `reset_subscription` в
`lib/sub_links.sh`, `cluster_delete_local` в `lib/cluster.sh`) — там это
удаление произвольного файла. В `sub_link_remove` путь прикрыт проверкой
`grep -qxF` по списку токенов, но список — тот же отравленный.

**Выведено из чтения кода, в песочнице не воспроизводилось.**

Для атаки нужен секрет кластера — то есть одна скомпрометированная нода
([P-04](CLUSTER.md#p-04)) либо чтение секрета из конфига Caddy под пользователем `caddy`.
Чинится там же, где P-134: санитайз на входе (при укладке раздела в кэш) и
вторая линия при чтении — токен обязан быть `^[A-Za-z0-9]{16,64}$`, всё
остальное пропускается молча.

**Закрыто** в 4.38.164 (`111364e`). Данные пира ложатся в кэш в одном месте —
`peer_pull` (`lib/cluster.sh`): строка раздела, у которой имя или токен не подошли
под форму (`valid_name`, `valid_token` в `lib/config.sh`), в кэш не попадает. Вторая
линия — та же проверка токена перед записью файла в `regen_user_subscription`.
Уточнение к описанию: `rm -f` в `sub_link_remove`, `reset_subscription` и
`cluster_delete_local` берут токены только из СВОЕЙ базы, кэш пиров туда не
доходил. Проверка — `tests/test-peer-pull.sh`.

## P-139 ✅ Имя профиля из кластерного состояния уходит в `sed` без экранирования

`cluster_apply_state` (`lib/cluster.sh`) читает `/cluster/state` пиров и на
каждую строку зовёт `cluster_delete_local "$u"`, где `$u` — **имя из чужого
раздела**. Внутри:

```
sed -i "/^${user}|/d" "$DISABLED_FILE" "$STATS_FILE" "$IPS_FILE" ...
```

Имя не проверяется на форму нигде по дороге (`^[A-Za-z0-9_-]+$` стоит только в
интерактивном заведении юзера, `lib/users.sh`). Слэш в имени закрывает адрес
`sed`, и остаток строки исполняется как команды `sed` над списком боевых баз —
`users.db`, `disabled.dat`, `stats.dat`, `ips.dat`, `expiry.dat`, `userlimits`.

Проверено на копии файла в песочнице: имя `x/d;s/^.*$/PWNED/;/` переписывает
**все** строки файла. Профили и лимиты кластера стираются одной публикацией.

Тот же необработанный `$u` идёт в `db_add_user`, `roster_add` и ветку `active`
выше по функции. Условие эксплуатации — как у [P-138](#p-138): секрет кластера.

Чинить одной проверкой на входе в `cluster_apply_state` (и в `cluster_apply_roster`):
имя не подошло под `^[A-Za-z0-9_-]{1,64}$` — строка пропускается. Валидатор
просится общий, рядом с `_cluster_safe_name`: мест, где кластерное имя идёт в
путь или в регулярку, больше одного.

**Закрыто; запись была неточной уже в момент заведения.** Проверка формы имени
(`^[a-zA-Z0-9_-]+$`) стоит в `cluster_apply_state` и `cluster_apply_roster` с июня
2026 (`e813f15`, `2fe77f9`) — за три месяца до этой записи; слэш она не пропускает,
так что описанная подстановка в `sed` через эти две функции не воспроизводилась.
Сверено 12.11.2026 чтением кода. В 4.38.164 добавлены две линии поверх: фильтр на
входе в кэш (`peer_pull`, см. [P-138](#p-138)) и `valid_name` в самом
`cluster_delete_local`.

## P-181 ✅ Данные пира писались в кэш в семи местах: без проверки, неатомарно, по рукопожатию на раздел

`cluster_sync`, `cluster_online_sync`, `cluster_rates_sync`, `cluster_stats_live` и
`cluster_pull_settings` (`lib/cluster.sh`) каждая сама забирала раздел и сама писала
`peers/<имя>.<раздел>` через `printf > файл`. Три следствия: содержимое не
проверялось нигде ([P-138](#p-138)); читатель мог увидеть полфайла; каждый раздел
стоил отдельного процесса `curl` и TLS-рукопожатия — 23 на пира за полную
синхронизацию.

**Закрыто** в 4.38.164 (`111364e`): единственный вход — `peer_pull`. Один `curl`
на все разделы пира по одному соединению, фильтр формы по разделам, запись через
временный файл и `mv`. Замер на живом пире: 21 раздел 2,0 с -> 0,5 с. Устройство —
[guide/CLUSTER-CHANNELS.md](../guide/CLUSTER-CHANNELS.md), тест `tests/test-peer-pull.sh`.

## P-184 ✅ Сосед знал о ноде одно: отвечает ли её :443

`peer_probe` судит о пире по ответу `/cluster/manifest`. Нода с упавшим Xray,
вставшим кроном или сертификатом, который не продлевается, отвечала исправно и
считалась здоровой, пока не напишет клиент.

**Закрыто** в 4.38.165 (`67f157f`): нода публикует справку о себе разделом
`health` (юниты, свежесть кронов, сертификат, диск), соседи разбирают её в беды и
показывают в меню, в `--health`, в суточном отчёте и живым сообщением `--watch`.
Юнит в состоянии `failed` нода поднимает сама. Устройство и пороги —
[guide/NODE-HEALTH.md](../guide/NODE-HEALTH.md). Потолок: тревогу шлёт только та
нода, где настроена доставка; лежит она — молчат все.
